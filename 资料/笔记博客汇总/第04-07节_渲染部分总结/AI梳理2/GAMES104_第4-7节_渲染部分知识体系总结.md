## 🧭 先导章：一张图看懂1024渲染知识全景（必读）

如果你对渲染感到"迷迷糊糊"，请先读本章。它不罗列技术细节，而是**把四节课的所有知识串成一条逻辑链**。

### 一、一切从一句话开始

> **"屏幕上的每一个像素，都要回答一个问题：从相机这个方向看过去，这个点有多亮？"**

这个问题的数学表达就是 **Kajiya 渲染方程**（1986年）：

```
该点的颜色 = 自发光 + ∫(半球面所有入射光 × 材质的反射率) dω
```

方程本身完美。但**工程上无法直接求解**，因为有三个致命困难：

| 难题              | 含义                                   | 为什么难                                   |
| ----------------- | -------------------------------------- | ------------------------------------------ |
| ① 光从哪来？     | 任意一点能"看见"光源吗？被挡住了多少？ | 空间关系复杂，远近距离都要考虑             |
| ② 材质怎么反应？ | 光入射后，有多少反射到眼睛？           | 需要在半球面上积分（相当于无数个方向求和） |
| ③ 间接光怎么办？ | 光照到墙面，墙面又照亮地面……无限循环 | 每次弹射都在传递能量，理论上递归无限次     |

> 这三个难题，就是整个渲染技术史的**三条主线**。每一条主线都经历了一条清晰的演进路径。

### 三、主线一：光照从哪来？——从"拍脑袋"到"算清楚"

**第一层：经典方案（第5节前半部分）——能跑就行**

```
主光(Directional Light) + 环境光(Ambient, 一个常数) + 环境贴图(CubeMap)
                │
                └── 把复杂光场简化成三个东西，粗暴但有效
```

- 环境光 ≈ 球面上所有光取个平均 → 场景不会死黑，但扁平无层次
- CubeMap ≈ 在光滑表面反射一下环境 → 给了一点高频细节

> 这一层的核心思想：**把通用方程参数特例化，求出近似解析解**

**第二层：预计算方案（第5节后半部分）——提前算好**

> ⚠️ **关键澄清**：这里出现了两种"预计算"，但目标完全不同。先搞清楚区别，再看具体技术。

**Lightmap 是什么光的？**

- Lightmap 存的是**全局光照** = 直接光照 + 间接光照（多次弹射后所有光路的综合结果）
- 它**不区分光来源**：墙上被主光照到的亮斑、地面反弹的彩色光（Color Bleeding）、物体之间的软阴影、天空环境光——全部"烘焙"进一张2D纹理
- 光源被锁死（太阳角度固定、场景90%静态），离线算几小时 → 运行时直接采样，几乎零成本

**CubeMap 环境贴图的"预计算"和 Lightmap 的关系？**

这是两种本质不同的"预计算"，目标不同。

> **直接回答：Lightmap 不包含 CubeMap。** 它们是两个独立的东西，在渲染管线中**并行叠加**，不存在包含关系。

|                          | CubeMap 环境贴图 → IBL                                                          | Lightmap + Light Probe                                                     |
| ------------------------ | -------------------------------------------------------------------------------- | -------------------------------------------------------------------------- |
| **存的是什么？**   | 空间中某一点的**球面光照信号**（所有方向来的光记录在一张Cube纹理上）       | 场景中每个表面点的**最终GI结果**（所有光路算完后到达该表面的总能量） |
| **解决什么问题？** | "周围环境是什么？光滑物体应该反射什么？"                                         | "这个角落到底有多亮？"                                                     |
| **覆盖哪些光？**   | 只负责**环境光照**这一项——主光打不到的地方、暗部的反射层次               | 负责**全局光照**——直射光 + 间接光（多次弹射）全部算在一起          |
| **在经典三件套中** | 作为 Hack：只取一个方向的反射颜色                                                | 不存在（经典方案还没有 GI）                                                |
| **在现代方案中**   | →**演进成 IBL**（Irradiance Map + Specular 预滤波），体系化所有方向的反射 | → 成为 GI 标准方案                                                        |
| **能否互相替代？** | **不能。** IBL 只管"环境反射"，Lightmap 管"所有光"                         | **不能。** Lightmap 不区分光源类型，IBL 只覆盖环境光                 |

> **关系总图**：
>
> ```
>  像素最终颜色 = 直接光照(主光)
>                + 环境光照(IBL — 源自 CubeMap 的数学体系化)
>                + 全局光照(Lightmap/Light Probe — 包含所有弹射)
>                + 天空光照(大气散射)
>                + 后处理(AO/Bloom/ToneMapping/ColorGrading)
> ```
>
> IBL 和 Lightmap 是**两个独立的加数**，各管各的，互不包含。

**那现代方案中，光到底分几层叠加？**

每一帧渲染时，像素的最终光照 = 以下各项相加：

```
最终颜色 = 直接光照（主光 × PBR 材质 × Shadow Map 可见性，实时计算）
          + 环境光照（IBL：CubeMap 预卷积 → Irradiance Map + Specular LUT）
          + 间接光照（Lightmap 烘焙的间接反弹 + Light Probe 的动态环境光）
          + 天空光照（大气散射计算 / 预计算 LUT）
          + 后处理（AO / Bloom / Tone Mapping / Color Grading）
```

> ⚠️ **关键澄清：Lightmap 不是"包含全部光照"吗，为什么还要加直接光照？**
>
> 这是一个极易混淆的点。Lightmap 在**离线烘焙时**确实把所有光（直接+间接）一起算出来了。但如果在运行时直接使用完整 Lightmap：
>
> 1. **主光不能动态变化了**——太阳角度必须锁死，光源移动就全失效
> 2. **Shadow Map 无法使用**——因为阴影已经被"烧死"在 Lightmap 里了，无法根据实时遮挡更新
> 3. **PBR 材质无法正确响应**——材质对直射光和漫反射的响应不同，需要分离计算
>
> 所以现代引擎的实际做法是：
>
> - **Lightmap 只烘焙间接光照**（多次弹射后到达表面的光），不包含主光直射
> - **主光直接光照实时计算**（PBR × Shadow Map × 光源强度）
> - 两者相加 = 完整的全局光照效果
>
> 一个简单类比：Lightmap ≈ 环境的"底色"（间接光照氛围），主光 ≈ 画上去的"高光"（实时动态），各管各的，互不冲突。

#### 📎 补充：间接光不就依赖主光吗？主光变了 Lightmap 不该跟着变吗？

> 这个疑问在物理上是**完全正确的**——间接光确实来自主光的多次弹射，主光变了间接光理论上也会变。但 Lightmap 冻结间接光是一个**有意识的工程近似**，不是在声称"间接光和主光无关"。
>
> 关键在于两者对主光变化的**敏感程度完全不同**：
>
> - **直接光** 对主光方向极度敏感：太阳转 10°，阴影整体移位，明暗交界线明显变化，玩家立刻能感知
> - **间接光** 经过 2~3 次弹射后，方向信息已被"磨平"扩散为低频环境氛围光：太阳转 10°，角落的间接光变化幅度约 5%，人眼几乎感知不到
>
> 所以 Lightmap 的逻辑是：**承认误差存在，但误差小到可以接受**——而实时重算全场景间接光（路径追踪）单帧需要数分钟，完全无法用于游戏。
>
> 极端情况（昼夜循环）的工程应对：
>
> - **多张 Lightmap 插值**：分别烘日出/正午/黄昏/夜晚，运行时在几张间混合（代价是显存倍增）
> - **动态 GI**：UE5 的 Lumen 实时重算间接光，是近年才实用化的高成本方案
> - **接受不精确**：大多数游戏昼夜循环中间接光就是静态的，大多数玩家不会在意
>
> **一句话**：间接光确实依赖主光，Lightmap 是接受"冻结间接光"这个近似——因为间接光低频化后对主光变化不敏感，近似误差在游戏场景下可以接受。

> 可以看到：CubeMap 环境贴图的思想在 IBL 中得到了完整的数学体系化——不再只是一个 Hack，而是预计算整个球面的反射积分。

#### 📎 补充：Lightmap 间接光 vs CubeMap 环境光——到底有什么区别？

> 两者都不包含主光直射（都是计算非主光的其他光），容易被当成"同一件事"，但本质不同：一个是**计算后的结果**，一个是**未积分的原料**。

**核心区别：结果 vs 原料**

- **Lightmap 间接光** = 已经算完的答案：*"经过多次弹射，最终有多少光落在这块表面上？"*

  路径追踪把所有弹射路径积分完，留下一个 RGB 值，且这个值**已经考虑了周围所有遮挡**（墙、天花板、柱子都参与了计算）。换个角度看表面，颜色不变。
- **CubeMap 环境光** = 还没和任何表面发生关系的原料：*"从这个空间位置向四面八方看，能看到什么颜色的光？"*

  是一张全景图，不知道你要把它用在光滑金属还是粗糙水泥上，不知道反射方向是什么，不知道周围有没有遮挡——这些都留给渲染时计算。

**最关键的差异：遮挡关系**

|                    | 知道周围遮挡吗 | 举例                                                     |
| ------------------ | -------------- | -------------------------------------------------------- |
| **Lightmap** | ✅ 完全知道    | 墙角背光处烘焙后就是暗的，因为离线计算时天花板遮挡已参与 |
| **CubeMap**  | ❌ 不知道      | 探针捕获的是开阔全景，不知道旁边那堵墙会挡住反射         |

这也是 CubeMap 反射在室内有时会穿帮的根本原因——玻璃桌可能反射出被墙挡住的室外景色，因为 CubeMap 只有全景，没有当前表面点的局部遮挡信息。

**类比**

- Lightmap ≈ 对着墙面打的"效果灯"，直接拍出墙面在复杂光照下的最终颜色，墙角有多暗全烘进去了
- CubeMap ≈ 在房间中央架一台 360° 全景摄像机，只拍"从这里能看到什么"，不关心任何一面具体的墙

**为什么两者都需要**

| 需求                                 | 用哪个                 | 原因                      |
| ------------------------------------ | ---------------------- | ------------------------- |
| 墙角有多暗（漫反射间接光，静态表面） | Lightmap               | 有精确的局部遮挡信息      |
| 镜面应该反射什么                     | CubeMap / IBL          | 有方向性的全景光场数据    |
| 动态物体（角色）的环境光             | CubeMap（Light Probe） | Lightmap 只能用于静态表面 |

两者叠加才能还原出完整的视觉效果，缺一不可。

=》一般场景中主光是动态的，而非主光的其他光（如环境光、间接光都是认为静态的，虽然其物理上严格受主光影响，但游戏渲染中可以认为不受动态主光影响，而是静态的，见“补充：间接光不就依赖主光吗？主光变了 Lightmap 不该跟着变吗？”）；lightmap和cubemap都是计算场景中静态的非主光的其他光，即一般都是静态的；主光动态变化时一般lightmap和cubemap不变化。

#### 📎 补充：Lightmap 与 CubeMap 的数据结构辨析

> 上面讲清了两者"职责不同"，但初学时还有一层更基础的困惑：**它们的数据到底存在哪、存成什么样、为什么数据量不爆炸**。这一节补充这部分。

> ✅ **先看结论（TL;DR）**
>
> 一张 CubeMap 对应世界空间中的**一个探针位置**，记录从该位置向四面八方看到的光。场景里**离散放置几十到几百个探针**，渲染时用表面点（uv点）的**世界坐标**就近查找、按权重插值。同一张 CubeMap 会被**预处理成两份**：积分后的 Irradiance 给漫反射，按粗糙度预模糊的 Mip 链给镜面反射。静态表面的漫反射间接光一般由精度更高的 **Lightmap** 提供，探针主要服务**镜面反射和动态物体**。
>
> 下面五个小节把这段结论逐条展开。

**补充一：两者绑定的坐标系完全不同**

这是最容易混的地方，也是把两者搞成"同一个东西"的根源：

|                           | 绑定在哪                         | 坐标系                  | 数据形态                   |
| ------------------------- | -------------------------------- | ----------------------- | -------------------------- |
| **Lightmap**        | 绑在**物体表面**上         | UV 空间（2D 纹理坐标）  | 每个 texel 一个 RGB        |
| **CubeMap / Probe** | 悬浮在**空间**中的探针位置 | 世界空间（3D 坐标 xyz） | 6 张正方形纹理拼成的立方体 |

CubeMap 是在世界空间某个 3D 位置（比如房间正中央、离地 1.5 米那个点）架一台 360° 相机拍下来的，**那个位置通常是空的，压根不在任何物体表面上**。

所以不存在"某个 UV 点的 CubeMap"这种说法，只有"某个世界空间位置的 CubeMap"。使用时是反过来查的：

```
❌ 错误理解：UV点(0.3, 0.7)          → 它自己的 CubeMap
✅ 正确理解：表面点世界坐标(120,5,88) → 找最近的探针 → 借用探针的 CubeMap
```

**补充二：Lightmap 的 texel 里到底存了什么**

一句话：**每个 texel 存一个 RGB，表示该表面微小区域接收到的「间接光漫反射辐照度」**。

需要精确两点：

1. 是 **UV 空间**的 texel，不是屏幕像素。一面墙把自己的表面展开成一张 2D 贴图，每个 texel 对应墙上一小块物理区域——跟你从哪个角度看无关，跟表面本身有关。
2. 现代引擎里存的**不是"全部光照"，而是"间接光"**（见上文关键澄清）。主光直射由实时 PBR + Shadow Map 计算。

**补充三：CubeMap 的数据结构与数据量**

CubeMap 就是字面意思——把一个立方体的 6 个面各拍一张正方形照片：

```+Y（顶）-X
      （左   前    右    后）
       -Y（底）
```

采样时用一个 3D 方向向量决定查哪张面的哪个像素。存储量：

```
6 × 分辨率² × 通道数
256×256 的 CubeMap ≈ 6 × 256 × 256 × 3 bytes ≈ 1.1 MB
```

**为什么数据量不爆炸？——因为探针是离散放置的**

"如果每个表面点都存一整个球面光场"确实会爆炸。但引擎不这么做，而是用 **Reflection Probe（反射捕获点）**：

- 场景里手动或自动放几十到几百个探针，每个探针在自己的位置捕获一张 CubeMap
- 渲染某个表面时，用该点的**世界坐标**找最近的（或按包围盒/距离权重最高的）几个探针，插值混合
- 代价：远离探针的地方反射不精确，这是精度与成本的权衡

```
50 个探针 × 256×256 CubeMap ≈ 56 MB —— 完全可接受
```

**漫反射部分还能极致压缩**：漫反射只关心低频信息（整体冷暖和亮度），不在乎"墙面精确反射远处的树叶"，因此整个球面漫反射光场可以用 SH 压到 **9 个基函数 × RGB = 27 个浮点数（约 108 字节）**。这正是上文 SH 一节的实际落地场景。

**补充四：同一张 CubeMap，被预处理成两份数据**

"漫反射和镜面反射都用 CubeMap"——方向正确，但运行时用的**不是原图**，而是从同一次捕获派生出的两份预处理结果：

```
        原始 CubeMap 捕获（入射光 Radiance 全景图）
                       │
     ┌─────────────────┴─────────────────┐
     ▼                                   ▼
对整个半球做余弦加权积分            按粗糙度逐级预模糊
     │                                   │
Irradiance Map / SH 27个数         Prefiltered Env Map（多级 Mip）
「低频、与视线方向无关」            「高频→低频、与视线方向强相关」
     │                                   │
     ▼                                   ▼
   给漫反射用                   给镜面反射用（配合 BRDF LUT）
```

- **漫反射**：材质把入射光向四面八方均匀散射，只关心"半球方向来的光的总和"，与视线无关 → 积分结果极平滑，低分辨率或 SH 就够
- **镜面反射**：按反射定律弹出，`R = reflect(-V, N)`，与视线强相关 → 完美镜面直接采样方向 R；粗糙表面靠预滤波 Mip 链模拟模糊反射

```
Mip0（最清晰）→ Roughness = 0   （完美镜面）
Mip1          → Roughness ≈ 0.2
Mip2          → Roughness ≈ 0.4
...
Mip5（最模糊）→ Roughness = 1   （接近漫散射）
```

渲染时按材质粗糙度选对应 Mip 层采样，就得到了不同的光泽感。两者本质上都是"对 CubeMap 做积分"，区别只在积分范围：漫反射积整个半球，镜面反射积一个按粗糙度展宽的高光叶瓣。

**补充五：静态与动态物体的实际分工**

工程实践中还有一层分工，理解这个才能对上引擎里的实际选项：

| 物体类型                         | 漫反射间接光来源                  | 镜面反射来源                |
| -------------------------------- | --------------------------------- | --------------------------- |
| **静态物体**（墙、地面）   | Lightmap（逐 texel 烘焙，精度高） | Reflection Probe 的 CubeMap |
| **动态物体**（角色、载具） | Light Probe（SH 系数插值）        | Reflection Probe 的 CubeMap |

静态表面位置确定，可以逐 texel 精确烘焙，比"借用附近探针"精确得多；动态物体位置不定，只能靠探针插值。

**不同材质下两者的贡献占比**（帮助建立直觉）：

- 粗糙水泥地面：几乎全靠 Lightmap，CubeMap 贡献接近零
- 光滑金属桌面：Lightmap 贡献很小，CubeMap / IBL 占主导
- 半光滑木地板：两者都有贡献，按粗糙度分配

> **一句话收束**：Lightmap 回答"这个**表面点**有多亮（能量总量，UV 空间）"，CubeMap 回答"从这个**空间位置**往某方向看是什么颜色（方向分布，世界空间）"。前者给出漫反射暗部的层次，后者让光滑表面知道反射方向上有什么。

---

**回到预计算的主线**：

```
球谐函数(SH) → 把球面光场压缩成12个参数
       │
       ├── Lightmap：把整个场景的全局光照"烘焙"到2D纹理
       │      └── 离线算几个小时 → 运行时直接采样，几乎零成本
       │
       └── Light Probe：在空间中撒采样点，动态物体插值获取环境光
              └── 也能在运行时更新，支持动态场景
```

- Lightmap = 静态场景的"完美GI"（软阴影、Color Bleeding 全有）
- Light Probe = 动态物体的"够用GI"（采样稀疏，但灵活）

> 这一层的核心思想：**空间换时间** —— 预计算 + 查表。SH 的价值在于把球面积分变成了参数向量的点积。

**第三层：大气和天空（第6节下）——从物理出发，而不是拍脑袋**

```
天空渲染 ≠ 画一个蓝色球
       │
       ├── 物理模型：瑞利散射(蓝光散射强→天空蓝) + 米氏散射(方向性→雾/日晕)
       │      └── 需要解辐射传递方程(RTE)
       │
       ├── 经典方法：预计算大气散射(Bruneton 2006)
       │      └── 把 RTE 解预先算成 4D 查找表 → 运行时查表+插值
       │
       └── 前沿方案(UE在用)：假设多次散射各向同性，降维到2D实时计算
              └── 支持动态天气、异星大气、多太阳
```

> 这一层的核心思想：**从物理第一性原理出发建模，再用近似和预计算落地**

### 四、主线二：材质怎么反应？——从"随便调"到"物理正确"

**第一层：Blinn-Phong（第5节前半部分）——看着像就行**

```
Diffuse项(漫反射) + Specular项(高光，用幂函数调宽窄)
```

- 问题①：能量不守恒 → 光线追踪多次弹射后"黑腔变亮"
- 问题②：所有材质都像塑料

**第二层：PBR（第5节后半部分）——物理正确**

```
微平面理论 → Cook-Torrance 模型 (D·G·F 三项)
    │
    ├── D项(法线分布)：用 GGX 模型，一个Roughness参数同时驱动 D 和 G
    ├── G项(几何遮挡)：微表面自遮挡 + 互遮挡
    └── F项(菲涅尔)：视线越斜反射越强（柏油马路远处有倒影）
```

> **PBR = 一个Roughness参数 + 一个Fresnel参数，就物理正确地描述了所有材质**

- SG模型：灵活但容易设错 → 适合小团队
- MR模型：用"金属度"锁定物理范围 → 防呆设计，适合大团队

**第三层：IBL（第5节后半部分）——PBR的"另一半"**

```
PBR 告诉材质"怎么反射"，IBL 告诉材质"环境光是什么样子"
    │
    ├── Diffuse部分：预计算 Irradiance Map → 查表
    └── Specular部分：利用CubeMap的Mipmap层级(不同粗糙度≈不同模糊程度)
            └── 再加一个2D LUT查表(Fresnel项的积分)
```

> PBR + IBL = 暗部也有丰富的反射层次。这是画面从"还行"到"真实"的关键一跃。

### 五、主线三：阴影与间接光——从"简单判断"到"全局计算"

**第一层：Shadow Map（第5节前半部分）——最简单的可见性判断**

```
从光源视角渲染深度图 → 正常渲染时比深度 → 更深=在阴影中
```

- 问题一箩筐：自遮挡(Bias)、远处精度不足、地平线附近阴影拉极长

**第二层：Cascade Shadow + 软阴影（第5节末尾）**

```
Cascade Shadow Map：视锥体分多层，近处高精度，远处低精度
      └── 用有限的纹理内存覆盖极大的场景范围

PCF/PCSS/VSSM：让阴影边缘过渡柔和
```

**第三层：全局光照 GI（第5节）**

```
Lightmap(静态烘焙) + Light Probe(动态采样) = 光不止一次弹射
      └── 画面出现软阴影、Color Bleeding、层次丰富的暗部
```

**第四层：后处理（第7节）——最后一层"美颜"**

```
AO(环境光遮蔽) → 小凹槽更暗，小突出更亮 → 场景立刻立体
  └── SSAO → HBAO → GTAO → Ray-Traced AO（演进路线）

Bloom → 强光源周围光晕 → 画面更"有光感"

Tone Mapping → HDR数据正确曝光 → 亮部暗部都看清
  └── Filmic Curve → ACES（电影学院标准）

Color Grading → LUT调色 → 情绪化表达
  └── 性价比最高的渲染技术
```

### 六、贯穿一切的地基：第4节 + 第7节的管线

```
┌─────────────────────────────────────────────────────┐
│                    硬件层                            │
│  GPU SIMT架构：几千个小核心同时算，但换参数代价极大      │
│  缓存命中 > 一切，数据连贯性 > 一切                    │
│  原则：单向传输，尽量不从GPU回读                       │
├─────────────────────────────────────────────────────┤
│                    数据组织层                         │
│  Mesh → Submesh(按材质切分) → 资源池(相同数据只存一份)   │
│  Instancing：一份定义，生成千个实例(小兵/树/草)          │
│  Drawcall尽量少：按材质排序分组，一次DC画一堆             │
├─────────────────────────────────────────────────────┤
│                    裁剪层                             │
│  包围盒(AABB/OBB/BVH) → 只绘制看得见的                 │
│  PVS思想 → 区域划分 + 按需加载                         │
│  GPU遮挡查询 + Early-Z → 硬件帮你判断                  │
├─────────────────────────────────────────────────────┤
│                    管线层（第7节）                     │
│  Forward → Deferred → Tile/Cluster → Visibility Buffer│
│  Render Graph：把所有算法组织成DAG，自动管理资源和同步   │
└─────────────────────────────────────────────────────┘
```

### 七、一张终极总图：一次完整的渲染帧

把以上所有知识串起来，GPU 绘制一帧画面的完整流程如下：

```
【前置】CPU 端
  1. 可见性裁剪(BVH/PVS/GPU Query) → 只保留可见物体
  2. 按材质排序、Instancing 分组 → 减少 Drawcall
  3. 数据单向推送到 GPU → Mesh Pool + Texture Array

【GPU 端 — Forward 或 Deferred 管线】

  4. Shadow Pass → 从光源视角渲染 Cascade Shadow Map
       └── 加上 PCF/PCSS 软阴影

  5. Geometry Pass → 顶点着色 → 光栅化 → G-Buffer(Deferred)
       └── 如果是地形：四叉树 LOD + Stitching + Virtual Texture 采样

  6. Lighting Pass → 对屏幕像素逐点计算:
       ├── 直接光照: PBR(D·G·F) × 光源强度 × Shadow Map 可见性
       ├── 环境光照: IBL(采样 Irradiance Map + Specular预滤波LUT)
       └── 全局光照: Lightmap(静态) + Light Probe(动态)

  7. 天空 & 云:
       ├── 大气散射: 查预计算 LUT(或实时两维计算)
       └── 体积云: Weather Texture + 噪声函数 → Ray Marching

  8. 后处理 Post-Process:
       ├── SSAO → HBAO → GTAO(环境光遮蔽)
       ├── 雾效(Height Fog / 体积雾)
       ├── 抗锯齿 TAA / FXAA
       ├── Bloom(泛光)
       ├── Tone Mapping(ACES 曲线)
       └── Color Grading(LUT 调色)

  9. V-Sync → 显示器输出
```

### 八、最核心的五个"元思想"（理解这些，就理解了渲染）

| 思想                     | 一句话                                 | 出现的地方                                                                  |
| ------------------------ | -------------------------------------- | --------------------------------------------------------------------------- |
| **空间换时间**     | 提前算好，存下来，运行时查表           | Lightmap、LightProbe、IBL预积分、Virtual Texture、预计算大气散射、AO烘焙    |

# 第零章：渲染系统的四大工程挑战 — 第4节(上)

## 0.1 渲染系统的四大挑战

课程开篇便指出：**游戏引擎的绘制系统 ≠ 图形学理论**。差别在于四个工程挑战：

**挑战一：复杂性（Complexity）**

- 一个场景有成千上万物体，每个物体渲染算法完全不同（水体、植被、毛发、皮肤、地形材质）
- 还要加上大量后处理（光照运算等），所有计算集成在一个循环里

**挑战二：硬件深度适配**

- 必须运行在真实硬件上（PC、Switch、PS5、手机），深入理解南桥/北桥、显卡-CPU通信
- 不是"理论上证明对就行"，而是"在所有设备上高效运行"

**挑战三：性能预算**

- 无论场景多大，必须在33ms（30fps）甚至更短时间内完成
- FPS游戏要求60帧以上，电竞屏要求120帧
- 分辨率从1080P→4K→8K持续增长

**挑战四：时间预算分配**

- 绘制系统只能用10%~20%的CPU时间，剩余给Gameplay、网络等
- 不满足预算则功能无法上线
- 自动化Profiling（性能分析）每天运行，超预算自动预警

# 第一章：渲染基础设施 — 第4节(下) GPU、网格与裁剪

## 1.1 渲染的核心工作：计算

**基本流程**：顶点→三角形→投影→光栅化→像素着色→纹理采样

**数据规模**（现代游戏）：

- 百万级顶点和三角形
- 千万级像素
- 10亿级ALU和纹理运算

> "The men and women behind pixel" — 每一帧壮丽画面都是计算机逐像素计算拼接的。

## 1.2 纹理采样：容易被忽略的性能杀手

- 一次纹理采样需**8个像素点 + 7次插值运算**
- 砖墙由近及远时需Mipmap滤波，否则发生走样（抖动）
- 纹理采样是绘制过程中最昂贵的运算之一

## 1.3 理解GPU硬件

### SIMD 与 SIMT

- **SIMD**（单指令多数据）：一条指令同时处理多个数据（已被现代CPU广泛使用）
- **SIMT**（单指令多线程）：GPU核心设计哲学——很多小核心同时执行同一条指令
  - 100个核心 × 4维向量 = 400倍效能放大

### FLOPS：算力差距

- 现代显卡：10+ TFLOPS（如Xbox/PS5）
- 现代CPU：<1 TFLOPS
- **差距超过一个数量级**

### Fermi架构（NVIDIA，约10年前）

- 图形处理集群(GPC) → 流式多处理器(SM) → CUDA核心(ALU) + SFU(特殊函数) + 共享内存
- 现代Ampere架构新增：**Tensor Core**（AI计算）、**RT Core**（光线追踪BVH加速）

### 数据流动成本

- **冯·诺依曼架构**：计算和数据分开，数据搬移极慢
- CPU→GPU数据上传慢，**回读（Back Force）更致命**—可能导致半帧到一帧延迟
- **原则**：数据单向传输，尽量不从显卡回读

### 缓存（Cache）的重要性

- CPU一次数学运算 = 1个时钟周期
- 从内存读取数据 = **100+个时钟周期等待**（缓存未命中）
- **数据连贯性**对缓存命中至关重要

### 性能黑话

- **ALU Bound**：数学计算太多，其他操作等待
- **Fill Rate Bound**：写入缓存太慢，数据传输堵塞
- **"Bounds"** = 瓶颈 = 只要一个环节卡住，整个流水线被卡

## 1.4 平台差异

| 平台             | 架构特点                         |
| ---------------- | -------------------------------- |
| PC               | 独显+CPU分离，通过PCIe总线通信   |
| 主机（PS5/Xbox） | UMA共享内存架构                  |
| 手机             | Tile-Based Rendering（功耗敏感） |

## 1.5 可渲染物体的数据组织

### 网格（Mesh）

- **Mesh Primitive**：顶点(位置+法线+UV) + 三角形
- **索引数据**优化：顶点存数组，三角形只存三个顶点索引 → 存储量可节约6倍
- UV坐标在不同表面交接处（如立方体折线）**必须各自独立存储顶点法向**

### 材质（Material）与纹理（Texture）

- **视觉材质** ≠ **物理材质**：前者管"看起来像什么"，后者管"摩擦系数/反弹系数"
- 材质模型：从Phong → PBR → SSS（次表面散射）
- 纹理是关键表达：金属vs生锈的视觉区分更多靠纹理（Roughness贴图）而非参数

### 着色器（Shader）的特殊性

- Shader = **代码，但在引擎中被当作数据处理**
- 绘制一次物体 = 传入网格 + 纹理 + 材质参数 + **一段编译好的Shader二进制Block**
- **Shader Graph**：艺术家可视化搭积木→自动生成Shader代码→编译成Block

### 子网格（Submesh）

- 一个物体有多个材质时，**按材质切成子网格**
- 顶点/三角形存于大缓冲区，每Submesh只存**偏移值（Offset）**
- 每个Submesh独立应用材质+纹理+Shader

### 资源池（Pool）与实例化（Instancing）

- **池化思想**：将Mesh、Texture、Shader分别集中管理（多个物体共用同一资源）
- **Instancing**：一份数据定义，生成多个实例（1000个小兵共享一套网格+材质）
- "Object Definition vs Object Instance" — 贯穿引擎各模块的核心概念

### GPU Batch Rendering

- GPU切换参数（改贴图/Shader）代价极大 → 所有32个小核都要停下来等待
- **优化策略**：按材质排序分组，相同材质的物体一次性Drawcall解决
- DX12/Vulkan：抽象为**Render State Object**，预设状态，尽量不变动
- 现代GPU-Driven：一次Drawcall + 一列数据 = 成百上千个物体

## 1.6 可见性裁剪（Visibility Culling）

> **核心哲学**：最优化的最高境界&#x662F;**"Do Nothing"**——通过算法让计算机尽可能少做事。

### 包围盒（Bounding Box）

- **包围球**（Bounding Sphere）：最简单
- **AABB**（轴对齐包围盒）：最常用，两个顶点即可定义，计算效率最高
- **OBB**（定向包围盒）：与物体局部坐标对齐
- **凸包**（Convex Hull）：常用于物理运算
- 包围盒是绘制/AI/逻辑/物理等模块的通用基础设施

### 空间划分与裁剪算法

| 算法                        | 核心思想                              | 特点                                                |
| --------------------------- | ------------------------------------- | --------------------------------------------------- |
| **BVH**（层次包围盒） | 包围盒逐层向上合并为树结构            | 构建速度快，适合动态场景                            |
| **PVS**（潜在可见集） | 预计算每个房间能看到的其他房间        | John Carmack发明，思想影响至今（区域加载/资源调度） |
| **GPU遮挡查询**       | 显卡并行判断物体可见性                | 现代硬件主流方案                                    |
| **Hi-z / Early-z**    | 先渲染深度图，被遮挡像素/物体直接跳过 | 高效利用GPU并行能力                                 |

### PVS的现代意义

- 直接用于裁剪的越来越少，但**思想广泛用于开放世界区域划分和资源加载调度**
- "玩家行走在设计师预先设计好的Chunks/Zone中"

## 1.7 纹理压缩

- 不能用JPEG/PNG（无法随机访问）
- **Block-Based压缩**：切成4×4小方块
- **DXT系列（BC7）**：每个Block存最亮点+最暗点，其余点插值 → CPU可实时压缩/解压
- **ASTC**（手机）：不限形状，压缩效果最好，但压缩速度慢
- 加载到显卡的图片基本都是压缩格式

## 1.8 建模工具链

| 方式       | 工具                 | 特点                             |
| ---------- | -------------------- | -------------------------------- |
| 传统建模   | 3DS Max/Maya/Blender | 卡关键点，由粗到细               |
| 雕刻       | ZBrush               | 自由度大，艺术家友好             |
| 3D扫描     | 手机APP/专业扫描仪   | 精度可达十几亿面，需提前拥有实物 |
| 程序化生成 | Houdini/AI算法       | 自动生成细节，解放艺术家         |

## 1.9 前沿：Cluster-Based Pipeline

- 来源：2015年《刺客信条·大革命》精细建筑物
- **核心思想**：将模型切成固定大小的Meshlet（如64三角形）
- 每个Meshlet独立高效计算（完全匹配GPU SIMT架构）
- 可精细裁剪（如怪物手臂不可见部分被单独裁剪）
- **虚幻5 Nanite** = 此思想的极致工业化实现（像素级网格密度）

# 第一章：渲染的理论原点 — 从Kajiya方程说起

## 1.1 渲染方程：一切的开端

1986年，James Kajiya提出了**渲染方程（Rendering Equation）**，用一个六维方程描述了"场景中任意一点在所有光照路径下最终到达观察者的光能总量"。这是渲染问题的终极数学描述。

方程的核心结构：

- **自发光项**：该点自身发出的光
- **反射光积分项**：所有入射光经表面BRDF反射后，在观察方向的出射总和
- 积分中包含 $\sin\theta$ 因子：光斜射时表面接收的能量更低（类比：赤道热、极地冷）

## 1.2 渲染的三大核心挑战

课程从工程角度将Kajiya方程拆解为三大实际难题：

**挑战一：光的可见性（Visibility / Shadow）**

- 任意一点能否"看见"光源？这决定了该点是否被照亮
- Shadow是图形学里最难做好的效果之一，"解决了A，B、C、D就出问题"

**挑战二：光与材质的卷积积分**

- BRDF是一个四维函数，需要在整个半球面上对入射光和材质响应做积分
- 实时渲染中不可能逐像素做数值积分

**挑战三：光的无限弹射（全局光照）**

- 真实世界中每个被照亮的表面都成为新的光源（Color Bleeding）
- 这意味着无限递归：第一次计算结果成为第二次的输入
- Cornell Box是衡量GI算法的"标准答案"（Ground Truth）

> **核心思想—空间换时间**：这三大挑战贯穿了整个渲染技术发展史。几乎所有"高级"技术的本质都是：**提前算好，存下来，运行时查表**——用存储空间换取实时计算的性能。

# 第二章：经典渲染"三件套" — 最朴素的Hack方案

在理解现代渲染之前，先掌握最基本的方案。这套方案简单、高效，至今在低配/移动端仍有应用价值。

## 2.1 光场简化

| 组件                                         | 作用               | 本质                                 |
| -------------------------------------------- | ------------------ | ------------------------------------ |
| **主光（Directional / Point / Spot）** | 主要光照来源       | 把复杂光场简化为1~3个光源            |
| **环境光（Ambient Light）**            | 模拟间接光照       | 用一个常数替代整个半球面的光场平均值 |
| **环境贴图（CubeMap）**                | 模拟光滑表面的反射 | 用六面体贴图捕捉环境高光             |

> 这个方案虽然简陋，但从数学上确实符合渲染方程——它是将通用方程参数特例化后求得的"解析解"。

## 2.2 材质模型：Blinn-Phong

Blinn-Phong属于**经验派**材质模型——不研究物理本质，只根据观察现象建模：

- **Diffuse项**：漫反射，光均匀向各方向散射，乘以能量反弹率
- **Specular项**：高光/镜面反射，用幂函数（Power）调整反射波瓣的宽窄
- 基于**光可叠加原理**，两项相加即得最终颜色

**两个致命缺陷**：

1. **能量不保守**：入射100份能量，出射可能101份。在做光线追踪多次弹射时，这种误差会被放大（黑腔变亮）
2. **像塑料**：无论怎么调参数，木头、石头、金属看起来都像塑料，无法表达材质的本质差异

## 2.3 阴影：Shadow Map

**核心思想**：从光源视角渲染一张深度图 → 正常渲染时反向投影，比较深度 → 若当前深度 ＞ 最近遮挡物深度，则在阴影中

**经典问题与Hack**：

- 采样率不匹配 → 各种Artifact
- 自遮挡（Shadow Acne） → 加Bias偏移
- Bias过大 → 人脚浮空（阴影离地5~10cm）
- 光源靠近地平线 → 阴影拉极长，最难处理

## 2.4 三件套总结

| 挑战       | 解决方案                 |
| ---------- | ------------------------ |
| 光照复杂性 | 主光 + Ambient + CubeMap |
| 材质卷积   | Blinn-Phong多项式        |
| 可见性     | Shadow Map               |

配上好的美术资产，效果"还行"（如Doom 3）。这是理解渲染的**入门必备**。

# 第三章：现代光照系统 — 预计算全局光照(GI)

## 3.1 为什么需要全局光照？

- **仅直接光照**：房间内光只照到窗口附近，其他地方死黑
- **加Ambient**：整体均匀变亮，但失去层次感，非常"平面"
- **有GI**：光在地上反弹照亮天花板和墙壁，有软阴影和Color Bleeding，场景饱满真实

> GI的本质 = 直接光照 + 间接光照（光的多次弹射）

## 3.2 数学工具：球谐函数（Spherical Harmonics, SH）

在球面上存储光照信号面临两个困难：数据量巨大、卷积积分昂贵。**球谐函数**提供了解决方案。

- **本质**：球面上的"傅里叶变换"——一组正交基函数，将球面信号压缩为几个参数
- **低阶近似**：游戏中的环境光多为低频信号，只需用到1阶（4个参数 × RGB = 12个参数）
- **核心优势**：将球面卷积积分转化为参数向量的简单点积，只需24 bit存储一个点的光场
- 类似氢原子电子轨道的形状，数学性质优美（正交、光滑）

## 3.3 Lightmap（光照贴图）

**思想**：空间换时间 + 场景参数化到2D纹理

**流程**：

1. 几何简化 → 参数化展开（三维几何投影到2D纹理Atlas，保证分辨率均匀）
2. 用Light Farm（计算集群）离线烘焙全局光照（几十分钟到几小时）
3. 运行时直接采样，成本极低

**优点**：效果极佳（软阴影、Color Bleeding细节好），运行时开销低

**缺点**：

- 烘焙时间长，迭代慢
- 仅限静态物体+静态光源
- 动态物体用Lightmap采样会出bug（人走进阴影区域突然变黑）
- 占用几十到几百MB存储

> 思想遗产：参数化到低维空间 + 空间换时间，这两个思想比Lightmap本身更重要。

## 3.4 Light Probe（光照探针）

**思想**：在空间中撒采样点，动态物体通过邻近Probe插值获取光照

> ⚠️ **易混淆点：Light Probe ≠ Lightmap，也不等同于 CubeMap**
>
> "Light Probe"这个词在引擎里其实指代两类不同的东西，用途和存储格式完全不同：

| 类型                                   | 存储格式                                | 解决什么问题                                       | 用于谁               |
| -------------------------------------- | --------------------------------------- | -------------------------------------------------- | -------------------- |
| **Light Probe（GI探针）**        | SH系数（9个基函数 × RGB = 27个浮点数） | 动态物体的漫反射间接光（周围环境把多少光反弹过来） | 角色、载具等动态物体 |
| **Reflection Probe（反射探针）** | CubeMap（6面贴图）                      | 高频镜面反射（光滑表面该反射出什么画面）           | 两者都用             |

两者的工作流程：

```
场景中预先放置 N 个探针（空间中的采样点）
          │
          ├── GI 探针：把360°渲染结果压缩成 SH 系数
          │     → 27 个浮点数，只保留低频漫反射信息
          │     → 角色走到附近时插值这些系数，得到环境光颜色
          │
          └── 反射探针：把渲染结果保存为完整 CubeMap
                → 6 张正方形图，保留高频方向信息
                → 光滑材质采样它来知道"反射方向上有什么"
```

- **自动化生成**：根据玩家可达区域和几何自动均匀分布，避免手动放置的痛苦
- **运行时更新**：可以隔几帧或在空闲帧更新，支持动态场景

**优点**：支持动态物体，可运行时更新

**缺点**：采样稀疏（几万 vs Lightmap的几百万），效果不如Lightmap

## 3.5 经典光照方案：Lightmap + Light Probe + Reflection Probe

三者分工叠加，共同构成完整的 GI 效果：

| 层次   | 技术                                  | 负责内容                                            |
| ------ | ------------------------------------- | --------------------------------------------------- |
| 第一层 | **Lightmap**                    | 静态墙面/地面的精确间接光和软阴影（预烘焙，高质量） |
| 第二层 | **Light Probe（SH）**           | 动态角色身上的漫反射环境光（运行时插值，够用）      |
| 第三层 | **Reflection Probe（CubeMap）** | 场景里光滑表面的镜面反射（预捕获或实时更新）        |

三者各管各的，叠加在一起才是完整的光照结果。两者互补：Lightmap负责静态场景的高质量GI，Light Probe负责动态物体的环境光照。这套组合在过去十几年里是标准方案。

> **数学工具（SH）+ 预计算思想（Lightmap/Probe）→ 近似解决了球面光场的存储和积分难题**

# 第四章：PBR材质系统 — 物理为王

## 4.0 概念先导：BRDF、PBR、IBL 是什么？

> 这三个词贯穿第四、五章，先建立直觉再看细节。

### BRDF — 材质"反射行为"的数学描述

全称 Bidirectional Reflectance Distribution Function（双向反射分布函数）。

**它回答一个问题**：一束光从某个方向打到表面，有多少会反射到眼睛的方向？

```
BRDF = f(入射光方向, 视线方向) → 输出：反射了多少
```

两个极端例子：

- **镜子**：只有入射角 = 反射角那一束光才进眼睛，其他方向几乎没有
- **哑光墙壁**：光打过来四面八方均匀散射，从任何角度看亮度差不多

不同材质有不同的 BRDF，BRDF 就是把这个差异用数学函数表达出来。

### PBR — 用物理规律推导 BRDF，而不是靠猜

全称 Physically Based Rendering（基于物理的渲染）。

**它解决的问题**：BRDF 函数怎么定？

早期做法（Blinn-Phong）是靠经验拍脑袋——给金属调一个"shininess"参数，但这个参数没有物理意义，换个光照环境就穿帮，不同材质要各自手调。

PBR 的做法：从物理出发，假设表面由无数微观小平面组成，用物理定律推导出反射行为，最终得到：

```
BRDF = 漫反射 + D(法线分布) × G(几何遮挡) × F(菲涅尔) / 归一化系数
```

**好处**：艺术家只需调两个直觉参数就能覆盖所有材质：

- **Roughness（粗糙度）**：0 = 镜面，1 = 完全哑光
- **Metallic（金属度）**：0 = 塑料/皮肤，1 = 金属

换光照环境也不会穿帮，因为公式本身是物理正确的。

### IBL — 把"整个环境"当作光源

全称 Image-Based Lighting（基于图像的光照），见第五章。

**它解决的问题**：PBR 的 BRDF 定义好了，但光从哪来？

点光源好算：一个方向，代入 BRDF 算一次就行。但现实里光从四面八方来（天空、地面反光、旁边的墙……），要对半球面上无数方向都积分，实时算不过来。

IBL 的答案：**提前算好，存成图，运行时查表**。

```
环境CubeMap → 离线预计算积分 → 存成 Irradiance Map + 预滤波Map + LUT
                                         ↓ 运行时查两次贴图即可
```

### 三者关系

```
BRDF         ← 数学工具：描述"一束光如何被反射"
  ↑
PBR          ← 用物理规律推导出 BRDF，并把参数直觉化
  ↑
IBL          ← 用 BRDF 高效处理"来自整个环境的所有光"
  ↓
三者合在一起 = 游戏里金属像金属、皮肤像皮肤的技术基础
```

---

## 4.1 微平面理论（Microfacet Theory）

**核心假设**：物体表面由无数微观尺度的微小平面构成

- 法线分布集中 → 表面光滑（镜面反射）
- 法线分布发散 → 表面粗糙（漫反射）
- 用一个参数（Roughness）统一描述所有宏观光学现象

## 4.2 Cook-Torrance BRDF模型（DFG三项式）

PBR材质 = **Lambert漫反射** + **Cook-Torrance镜面反射**

镜面反射部分由三个物理项组成：

### D项：法线分布函数（Normal Distribution Function）

- 描述微平面法线的统计分布
- 主流选择：**GGX模型**（2007年）
- 特点：波峰高而尖（清脆高光）+ 拖尾长（柔和过渡），不像Phong那样硬边界
- 参数：Alpha = Roughness

### G项：几何遮挡函数（Geometry Function）

- 计算微表面自遮挡（视线方向被挡住）+ 互遮挡（光线方向被挡住）
- 基于Smith方程，与D项共享Roughness参数
- 设一个参数即可同时驱动D和G

### F项：菲涅尔效应（Fresnel）

- 视线越接近表面切线方向，反射率越高
- 现象：远处路面看到车的倒影（类似海市蜃楼）
- 用5次方经验公式拟合，区分金属/非金属的F0值

## 4.3 MERL BRDF数据库 — 用真实测量校准理论

Cook-Torrance 公式推导出来了，但问题随之而来：**参数值填多少才对？** Roughness = 0.3 是什么感觉？金属的 F0 该是多少？这些数字不能靠拍脑袋。

MERL 数据库的做法是：用专业仪器把真实材质（钢铁、橡胶、皮革、丝绸……）在各种入射/出射角度组合下的反射率全部实际测量出来，积累成一个庞大的参考数据库。

**它的作用有两个**：

1. **验证理论**：拿 Cook-Torrance 公式的输出与真实测量值对比，看拟合得好不好
2. **给艺术家参考锚点**：钢铁的 Roughness 大概是 0.1，橡胶大概是 0.8，有了真实数据就有了可靠的起点

> 可以理解为：Cook-Torrance 是模型，MERL 是考试答案——用答案来验证模型、校准参数。

## 4.4 Disney Principled BRDF（迪士尼信条）— 让艺术家能用

Cook-Torrance + MERL 验证之后，PBR 在理论上已经完备，但参数对艺术家来说仍然太抽象。迪士尼的贡献是：**制定一套设计原则，重新包装参数的暴露方式**，让复杂的物理公式变成艺术家能直觉操作的滑条。

四条原则背后只有一个核心逻辑：**艺术家不是物理学家，参数必须符合直觉、不能出错**。

| 原则                 | 背后的工程考量                                         |
| -------------------- | ------------------------------------------------------ |
| 参数符合直觉         | "Roughness=0 是镜面"比"alpha=0.001"更好理解            |
| 参数尽量少           | 参数越多，调参时间越长，出错可能越大                   |
| 值域 0~1             | 有界范围让艺术家知道边界在哪，不会调出物理上不可能的值 |
| 任意组合不出诡异结果 | 防止两个参数互相干涉产生黑色/爆白等 bug                |

这套原则后来成为行业标准——今天 UE/Unity 的材质编辑器里那些滑条，本质上就是 Disney 原则的具体实现。

> **引擎的本质是工具**：把复杂留给程序员，把简单留给艺术家。

## 4.5 两种主流PBR模型 — 参数怎么组织

有了 Disney 原则之后，具体参数怎么定还有两派做法：

### Specular-Glossiness（SG模型）

给艺术家三张贴图：

- **Diffuse**：漫反射颜色（比如皮肤的橙黄色）
- **Specular**：高光颜色（直接控制菲涅尔 F0，即反射光的颜色）
- **Glossiness**：光泽度（粗糙度的反向）

**问题在 Specular 图**：物理上非金属的高光必须接近灰白色、金属的高光应该和底色相同。但 SG 模型允许艺术家随便填任何颜色，一旦填错 Specular，渲染结果就会"炸掉"——出现物理上不可能的效果（过亮、色彩奇异）。

### Metallic-Roughness（MR模型）

给艺术家三张贴图：

- **BaseColor**：基础颜色
- **Roughness**：粗糙度
- **Metallic**：金属度（0~1 的一个数）

关键在 **Metallic** 这个参数——系统根据它自动决定 Specular 颜色，艺术家根本不需要手动设：

```
Metallic = 0（非金属）→ Specular 自动设为灰白色（~0.04）
Metallic = 1（金属）  → Specular 自动从 BaseColor 里取
```

这背后有物理依据：非金属（塑料、皮肤、木头）的镜面反射率普遍很低且接近无色；金属的镜面反射率很高且颜色就是金属本身的颜色（金子反射金色的光）。把这条物理规律直接编进系统，就消灭了艺术家手动出错的可能。

**代价**：牺牲了少量灵活性（无法手动控制 Specular 颜色），换来大团队协作时的稳定性。金属/非金属过渡处偶尔会出现小白色边缘，属于已知 trade-off。

> MR模型更受工业界青睐，核心原因是**为大规模团队协作提供了"防呆"保障**。

### 两种模型对比

|          | SG 模型                    | MR 模型                       |
| -------- | -------------------------- | ----------------------------- |
| 灵活性   | ✅ 高，可直接控制高光颜色  | ⚠️ 稍低，高光颜色由系统决定 |
| 出错风险 | ⚠️ 高，Specular 填错就炸 | ✅ 低，系统保证物理合理       |
| 团队协作 | ⚠️ 需要艺术家有物理知识  | ✅ 防呆，新手也难出大错       |
| 行业使用 | 部分传统流程               | UE、Unity 默认标准            |

### 4.3~4.5 的整体逻辑

```
4.2 推导出 BRDF 公式（理论正确）
    ↓
4.3 用真实测量验证并校准参数（数据支撑）
    ↓
4.4 Disney 原则：重新包装参数，让艺术家看得懂（可用性）
    ↓
4.5 两种具体参数方案：SG（灵活但易错）vs MR（防呆但稍受限）
```

从"物理正确"到"艺术家能用"，这是一条完整的工程化路径。

## 4.6 PBR总结

PBR = Cook-Torrance微平面模型 + 能量保守 + 美术友好的参数化。世界材质表达从此"一统江湖"。

# 第五章：IBL（基于图像的光照）— PBR的孪生兄弟

## 5.1 核心思想

用一张CubeMap表达环境光场 → 预计算PBR材质与环境的卷积 → 运行时查表

**与SH的区别**：SH只能表达低频（全局明暗），IBL能保留高频细节（环境反射的层次感和凹凸感）

## 5.2 Diffuse部分：Irradiance Map

- 对CubeMap进行漫反射卷积预计算
- 结果存储为一张小纹理
- 运行时根据表面法向直接采样 = 空间换时间

## 5.3 Specular部分：预滤波 + LUT

**预滤波环境贴图**：

- 利用CubeMap的Mipmap层级
- 不同Roughness对应不同Mip层级（粗糙 = 低Mip = 模糊）
- 注意：每层需**独立计算**，不能直接Mipmap合并

**BRDF LUT（查找表）**：

- 二维LUT：横轴Roughness，纵轴sinθ（视线与法线夹角）
- 预先算好Fresnel项的积分结果
- 运行时只需两次纹理采样

## 5.4 IBL效果

PBR定义材质如何响应光照，IBL告诉材质"环境光是什么"。两者配合，暗部也有丰富的层次和细节。这是3A游戏画面真实感的关键一跃。

# 第六章：阴影技术演进 — 从Shadow Map到Virtual Shadow Map

## 6.0 基础概念：Shadow Map 是什么

Shadow Map 是判断"一个点是否在阴影里"的基础方案：

1. 从**光源视角**渲染整个场景，把每个点到光源的距离存进一张深度纹理
2. 渲染画面时，把每个像素变换到光源空间，比较它的深度和 Shadow Map 里存的深度
3. 比存的深 → 前面有东西挡着 → 在阴影里

```
Shadow Map = 一张2D 深度纹理（每个 texel 存一个 float 深度值）
             从光源视角渲染，覆盖整个场景
```

> ⚠️ **关键：Shadow Map 是从光源视角渲染的，不是从摄像机视角**。
>
> 太阳不知道也不关心哪些东西离摄像机近、哪些远——它只是把整个场景一视同仁地压进一张图里。

### 6.0.1 它在渲染流程中的位置：为实时直接光照提供可见性

第六章讲的阴影技术，主要解决的是实时直接光照中的一个问题：**当前表面点能否看见光源，以及能看见多少光源**。课程重点以太阳这类主方向光为例，因此可以把它理解成“实时计算主光时使用的阴影系统”；但它通常分成前后两个阶段，并不是等到计算主光颜色时才临时生成 Shadow Map。

```text
CPU/GPU 可见性裁剪
        ↓
Shadow Pass（阴影阶段）
从主光视角绘制场景，生成 Shadow Map / CSM / Virtual Shadow Map
        ↓
Geometry Pass（延迟渲染时写入 G-Buffer）
        ↓
Lighting Pass（光照阶段）
计算主光直接光照，并查询 Shadow Map 得到阴影可见性
        ↓
环境光照 / GI / 天空与体积效果 / 后处理
```

**阶段一：Shadow Pass 生成阴影数据**

- 从光源视角绘制可能投射阴影的几何，只记录深度和遮挡关系，通常不计算最终表面颜色
- 普通 Shadow Map 生成一张光源空间深度图
- CSM 将相机视锥分段，为每段分别生成方向光深度图，使近处获得更高精度
- Virtual Shadow Map 在这一阶段完成所需页面的标记、分配、缓存更新和深度绘制

**阶段二：Lighting Pass 使用阴影数据**

计算某个表面点的主光贡献时，把该点变换到光源空间，与 Shadow Map 中记录的深度比较，得到阴影可见性系数 $V_{shadow}$：

$$
L_{direct}=L_{light}\,f_{BRDF}\,\max(0,\mathbf{N}\cdot\mathbf{L})\,V_{shadow}
$$

- $V_{shadow}=1$：没有遮挡，获得完整的直接光
- $V_{shadow}=0$：完全遮挡，没有该光源的直接光贡献
- $0<V_{shadow}<1$：位于软阴影过渡区，只获得部分直接光

PCF、PCSS、VSSM 等技术主要改进的就是这个“查询并估算 $V_{shadow}$”的过程：PCF 对邻域深度比较结果取平均；PCSS 先搜索遮挡者，再动态决定滤波范围；VSSM 利用深度统计量估算可见比例。Virtual Shadow Map 主要改进阴影数据的组织、缓存和按需生成方式，最终仍由光照阶段查询。

**在不同渲染管线中的位置**：

```text
Forward： Shadow Pass → 绘制物体时同时计算材质、直接光照和阴影 → 后处理

Deferred：Shadow Pass → Geometry Pass 写 G-Buffer
                     → Lighting Pass 读取 G-Buffer 与 Shadow Map → 后处理
```

所以“Shadow Pass → Geometry Pass → Lighting Pass”是延迟渲染中最直观的表达；在前向渲染中，材质着色、光照和阴影查询通常发生在同一次物体绘制中。

> **适用范围**：课程主要讨论主方向光，但 Shadow Map 原理也可用于其他实时光源。聚光灯通常使用一张透视 Shadow Map；点光源通常需要 Cube Shadow Map 的六个方向；面光源则需要更复杂的软阴影近似或光线追踪。它们共同解决的都是**实时直接光照的可见性**。Lightmap、IBL、Light Probe 等间接或环境光照一般不会直接套用同一张主光 Shadow Map，而由各自的 GI、探针、遮蔽或 AO 方案处理。

## 6.1 Cascade Shadow Map（级联阴影）

**问题**：大场景精度不够——为什么手枪离摄像机很近，影子还是锯齿？

这是最容易混淆的地方。假设用一张 2048×2048 的 Shadow Map 覆盖整个场景（2km 视野）：

```
2048 个像素 ÷ 2000 米 = 每个像素代表 ~1 米见方的范围
```

手枪虽然离**摄像机**很近（0.5m），但 Shadow Map 是从**太阳**视角渲染的。太阳俯视整个2km×2km 的场景，手枪在太阳眼里只是场景里一个3cm 宽的小点——对应到Shadow Map 不足一个像素，精度完全不够。

```
太阳视角（俯视整个场景）
↓
[整个2km×2km → 压进 2048×2048 的图]
    ├── 远处的山（覆盖很多像素）
    └── 近处的手枪（离摄像机近，但在太阳眼里依然只是小点，不足1像素）
```

类比：用一台相机从高空俯拍整座城市。路边的自行车虽然就在某个行人旁边（对行人来说"很近"），但在俯拍照里依然只有几个像素。Shadow Map 的精度问题就是这张"俯拍照"分辨率不够。

**方案**：不用一张覆盖全场景，改用多张各自覆盖不同距离范围：

```
CSM0（0~10m）：   2048×2048 覆盖 10m  → 每 texel ≈ 0.5cm  [精细，手枪阴影清晰]
CSM1（10~50m）：  2048×2048 覆盖 50m  → 每 texel ≈ 2.5cm  [较精细]
CSM2（50~200m）： 2048×2048 覆盖 200m → 每 texel ≈ 10cm   [中等]
CSM3（200m~2km）：2048×2048 覆盖 2km  → 每 texel ≈ 1m    [粗糙，远处山体够用]
```

渲染时根据像素到摄像机的距离，自动选对应层采样。

**数据结构**：

```
CascadeShadowMap {
    depth_texture[4]      // 4 张独立的深度纹理（通常 2048×2048 each）
    light_view_proj[4]    // 每层各自的光源投影矩阵（决定覆盖范围）
    split_distances[4]    // 每层的距离分界：[10, 50, 200, 2000] 米
}
```

**挑战**：层级间过渡需要插值，否则出现硬边界

## 6.2 软阴影技术 — 边缘质量问题

硬阴影（只判断在/不在）在现实中不存在——因为光源有面积，遮挡物边缘总有半影区（penumbra，即阴影逐渐变淡的过渡带）。以下三种算法是越来越精确的软化方案。

| 算法           | 全称                           | 核心思想                                   |
| -------------- | ------------------------------ | ------------------------------------------ |
| **PCF**  | Percentage-Closer Filtering    | 对Shadow Map采样点周围做滤波，产生柔和过渡 |
| **PCSS** | Percentage-Closer Soft Shadows | 根据遮挡物距离动态调整滤波核大小           |
| **VSSM** | Variance Soft Shadow Map       | 利用方差和切比雪夫不等式快速估计阴影百分比 |

### PCF — 最简单：固定范围滤波

**做法**：判断某点是否在阴影里时，不只采样 Shadow Map 上对应的那一个点，而是采样周围 N×N 个邻居点，把"判断为在阴影里"的比例作为阴影系数。

```
例：采样 5×5 邻域，25 个点里有 18 个判断为"在阴影里"
→ 阴影系数 = 18/25 = 72%（半影过渡，边缘柔和）
```

**数据结构**：与普通 Shadow Map 完全一样（一张深度纹理），只是采样的 shader 里多了一个循环，增加采样次数。

**问题**：滤波核大小固定，无法区分遮挡物近/远产生的不同软硬程度。现实里手边的墙产生清晰硬影，天上的云产生极柔和的软影——PCF 对两种情况一视同仁，软化程度不符合物理。

### PCSS — 动态核：先量距离再滤波

**做法**：分两步走。

**第一步（Blocker Search）**：在 Shadow Map 上搜索一片区域，找到遮挡物的平均深度，根据遮挡物到被照表面的距离，算出理论上半影区应该有多宽：

```
半影宽度 ≈ 光源尺寸 × (遮挡物到表面的距离 / 光源到遮挡物的距离)
```

**第二步**：用这个动态宽度做 PCF 滤波。

**例子**：

- 地上的石头（距地面 1cm）→ 半影宽度极小 → 几乎硬阴影 ✅
- 高空云层（距地面 500m）→ 半影宽度极大 → 非常柔和 ✅

**数据结构**：同 Shadow Map，但 shader 分两 pass 执行（Blocker Search pass + 动态核 PCF pass），运算量比 PCF 大得多。

### VSSM — 用统计加速 PCSS

**问题**：PCSS 每帧要对大量样本循环采样，性能开销很高。

**核心思想**：如果已知某片区域深度的**均值**和**方差**，可以用切比雪夫不等式直接估算"有多少比例的点比当前深度浅"——不用真的逐一采样。

```
已知深度均值 μ 和方差 σ² → 切比雪夫不等式 → 直接估算遮挡比例（O(1)）
```

**数据结构**：Shadow Map 从 1 通道扩展为 2 通道：

```
VSM_Texture {
    channel_R: depth    // 深度值
    channel_G: depth²   // 深度的平方（与 R 结合可算出方差）
}
```

存了这两个通道后，任意矩形区域的均值和方差可以通过 **Summed Area Table（二维前缀和）** 在 O(1) 时间查出，彻底消除循环采样开销。

**代价**：切比雪夫不等式是近似估算，在某些遮挡关系复杂的场景会出现轻微漏光（light bleeding）瑕疵。

## 6.3 Virtual Shadow Map — 空间利用率问题

**Cascade Shadow Map 的隐患**：每层的深度纹理里，有大量 texel 对应摄像机看不到的区域或被遮挡的区域，白白占用显存和计算资源。

**类比操作系统虚拟内存**：Virtual Shadow Map 用同样的思路解决 Shadow Map 的浪费问题。

1. 概念上维护一张巨大的 Shadow Map（如 16K×16K）
2. 把它切成小 Page（如 128×128 的小块）
3. 每帧先跑一个可见性判断 pass，标记哪些 Page 当前帧实际需要
4. 只为需要的 Page 分配物理显存并计算深度
5. 通过 Page Table 把虚拟地址映射到实际物理内存

```
Virtual Shadow Map {
    page_table[]       // 虚拟 Page → 物理 Page 的映射表
    physical_pool[]    // 实际分配的物理显存页池
    visibility_pass    // 每帧先跑一遍，标记哪些虚拟 Page 需要计算
}
```

**效果**：摄像机正前方、需要高精度阴影的区域 → 分配密集 Page；摄像机背后、远处低精度区域 → 不分配或极低密度。整体资源利用率远高于 Cascade 固定分层方案。这是 UE5 Nanite 配套的核心阴影方案。

### 6.2~6.3 整体演进逻辑

```
基础 Shadow Map（1张深度图）
    ↓ 问题：大场景精度不够
6.1 Cascade Shadow Map（多张分层，近细远粗）
    ↓ 问题：阴影边缘太硬，不真实
6.2 PCF（固定核软化）→ PCSS（动态核，物理正确）→ VSSM（统计加速）
    ↓ 问题：固定层级浪费显存和算力
6.3 Virtual Shadow Map（按需分配 Page，极致利用率）
```

# 第七章：地形渲染(上) — 几何表达

## 7.0 先导：地形与通用光照、材质和阴影系统是什么关系？

地形通常**不是脱离普通物体、独自完成全部绘制的一套渲染体系**。更准确地说，地形是一种特殊的 Renderable：它在几何生成、LOD、材质混合和纹理流送方面有自己的专用子系统，但生成几何和材质参数以后，通常仍会接入引擎通用的 PBR、直接光照、阴影、IBL、GI 和后处理管线。

```text
                    地形专用部分
        ┌────────────────────────────────┐
        │ 第7章：地形几何                 │
        │ 四叉树裁剪、LOD、Heightfield    │
        │ Stitching、Tessellation/Mesh Shader │
        └───────────────┬────────────────┘
                        ↓
        ┌────────────────────────────────┐
        │ 第8章：地形材质                 │
        │ Splat Map、Height Blend         │
        │ Texture Array、Virtual Texture  │
        │ 输出BaseColor、Normal、         │
        │ Roughness、Metallic、AO等参数   │
        └───────────────┬────────────────┘
                        ↓
                    通用渲染部分
        ┌────────────────────────────────┐
        │ PBR直接光照 + Shadow Map        │
        │ IBL/CubeMap + Lightmap/Probe/GI │
        └───────────────┬────────────────┘
                        ↓
             雾、AO、AA、Bloom、Tone Mapping
```

因此，第7、8章主要回答的是：

```text
第7章：哪里有三角形？当前视角需要多少三角形？
第8章：这些三角形是草、泥土还是岩石？应输出什么PBR参数？

PBR：这些材质参数面对光线时怎样反射？
阴影：光源能否到达这个地形点？
IBL/GI：天空与其他表面反弹过来的环境光有多少？
```

### 7.0.1 地形与 PBR 材质公式

第8章的材质混合不是用来代替 PBR，而是先为 PBR 准备输入。假设某个地形像素由 70% 草地、20% 泥土和 10% 岩石组成，地形材质 Shader 会先结合权重与高度混合规则，计算最终的材质属性：

```text
70% 草地材质 ─┐
20% 泥土材质 ─┼→ 地形材质混合 → BaseColor、Normal、Roughness、Metallic、AO
10% 岩石材质 ─┘                                      ↓
                                         送入通用PBR光照函数
```

以 BaseColor 和 Roughness 为例，最简单的示意是：

```text
BaseColor ≈ 0.7×草地颜色 + 0.2×泥土颜色 + 0.1×岩石颜色
Roughness ≈ 0.7×草地粗糙度 + 0.2×泥土粗糙度 + 0.1×岩石粗糙度
```

实际的法线和基于高度的材质混合会比直接线性相加复杂，但最终目的相同：生成一套标准的 PBR 材质参数。随后，地形和普通 Mesh 一样参与直接光照计算：

$$
L_{direct}=L_{light}\,f_{BRDF}(BaseColor,Normal,Roughness,Metallic,\ldots)\,
\max(0,\mathbf{N}\cdot\mathbf{L})\,V_{shadow}
$$

这里还要区分两种容易混淆的 Height Map：

- **Terrain Heightfield**：决定山体、坡地等宏观几何的位置和高度，主要在顶点/几何阶段使用
- **Material Height Map**：表示岩石、泥土等材质内部的微观高低关系，主要用于材质混合或表面细节

### 7.0.2 地形与阴影技术

地形既是**阴影投射者**，也是**阴影接收者**。

**作为投射者**：在 Shadow Pass 中，从主光方向重新绘制地形的 LOD 网格，把山峰、山坡等几何深度写入 Shadow Map。这样山峰才能在山谷或其他物体上投下阴影。该阶段通常只需要 Heightfield、LOD 后的顶点位置和必要的位移/裁剪信息，不需要完整计算草地、泥土和岩石的 PBR 颜色。

**作为接收者**：在主相机绘制或 Lighting Pass 中，地形像素查询 Shadow Map，得到 $V_{shadow}$，再用它衰减主光的直接贡献：

```text
向阳山坡：Vshadow = 1     → 接收完整太阳直接光
背阴山谷：Vshadow = 0     → 没有太阳直接光
软阴影边缘：0<Vshadow<1   → 接收部分太阳直接光
```

因此，第六章的 CSM、PCF、PCSS、VSSM、Virtual Shadow Map 都可以直接作用于地形。开放世界地形面积巨大、距离跨度大，恰好是 CSM 和 Virtual Shadow Map 等技术最典型的应用对象。

### 7.0.3 地形与 IBL / CubeMap

阴影只会削弱被遮挡光源的**直接光照**。背阴山坡虽然看不见太阳，但仍会受到天空和周围环境的照明，因此地形也会正常接受 IBL：

```text
环境CubeMap
├── Diffuse Irradiance → 照亮草地、泥土、岩石的漫反射暗部
└── Prefiltered Specular → 提供随粗糙度变化的环境镜面反射
```

不同地表对 IBL 的表现不同：

- 粗糙泥土：镜面环境反射较弱，但仍接受漫反射天空光
- 潮湿泥路：粗糙度较低，天空反射会更明显
- 积水地面：可能强烈反射天空、山体和周围环境
- 雪地或岩石：根据其法线和粗糙度呈现不同的环境高光

所以 CubeMap/IBL 不只服务镜子或金属；粗糙非金属地形也需要环境照明，只是它的贡献更多表现为低频漫反射 Irradiance。

### 7.0.4 地形与 Lightmap、Light Probe、GI

地形可以参与 Lightmap 和 GI，但具体选用哪种方案取决于场景规模、光源是否动态以及引擎设计。

**小型静态关卡**可以将地形的间接光，甚至某些静态直接光与阴影烘焙到 Lightmap：

```text
固定地形 + 固定建筑 + 固定光源
                ↓ 离线烘焙
地形Lightmap：保存山谷暗部、反弹光等预计算光照
                ↓ 运行时
与实时主光/阴影配合，或按烘焙模式直接使用
```

**大型开放世界**使用高分辨率地形 Lightmap 会面临数据量大、烘焙慢、昼夜循环不匹配和流式加载复杂等问题，因此也常改用天空 IBL、Irradiance Volume、Light Probe、动态 GI、SDF/Voxel 方案或 Lumen 等系统。

Light Probe 通常主要服务站在地形上的动态物体，例如角色和车辆：角色从阳光草地进入山洞时，通过附近探针插值得到逐渐变化的漫反射间接光。地形静态表面本身则根据项目选择 Lightmap、IBL、探针体积或实时 GI。

在完整 GI 中，地形还可能同时扮演多个角色：

- 接收太阳等光源的直接光
- 把草地、沙地等颜色反弹到岩石、建筑或角色底部
- 接收其他表面反弹回来的间接光
- 作为巨大的几何体遮挡间接光传播

例如太阳照亮绿色草地后，草地反射的绿色间接光可能使旁边岩石底部轻微泛绿；选择 Lightmap、Probe、Lumen 或光线追踪，只是计算这种传输的不同工程方案。

### 7.0.5 它在完整渲染流程中的位置

地形专用处理主要集中在场景准备和 Geometry/Main Pass，随后进入通用光照与后处理：

```text
CPU/GPU 场景准备
├── 四叉树视锥裁剪
├── 根据距离、FOV和屏幕误差选择LOD
├── 请求Heightfield与Virtual Texture页面
└── 组织可见的草木、道路、悬崖等实例
        ↓
Shadow Pass
└── 绘制地形几何，使其投射主光阴影
        ↓
主相机 Geometry/Main Pass
├── 第7章：生成/选择地形三角形
│   ├── Heightfield、四叉树LOD
│   ├── Stitching
│   └── Tessellation / Mesh Shader
│
└── 第8章：计算地形材质
    ├── Splat Map
    ├── Height Blend
    ├── Texture Array
    └── Virtual Texture
        ↓
通用光照
├── PBR直接光照
├── 查询Shadow Map
├── IBL / CubeMap
└── Lightmap / Probe / 实时GI（按项目选择）
        ↓
天空、雾、AO、AA、Bloom、Tone Mapping等
```

**延迟渲染（Deferred）中的地形**：

```text
Shadow Pass
→ 地形Geometry Pass
   → 第7章确定顶点和三角形
   → 第8章计算材质参数
   → 写入与普通物体相同的G-Buffer
→ Lighting Pass读取G-Buffer、Shadow Map、IBL和GI
→ 后处理
```

地形写入 G-Buffer 后，通常同样表现为 BaseColor、Normal、Roughness、Metallic、Depth、AO 等数据。Lighting Pass 多数时候不再关心该像素来自地形还是普通 Mesh，而使用统一的光照函数；只有特殊 Shading Model 才需要额外分支。

**前向渲染（Forward）中的地形**：

```text
Shadow Pass
→ 地形Main Pass
   → 生成地形几何
   → 混合地形材质
   → 同时计算PBR、阴影、IBL/GI
   → 直接输出HDR颜色
→ 后处理
```

前向渲染中常会使用专门的 Terrain Shader，但该 Shader 内部仍可复用引擎的通用 PBR、阴影和 IBL 函数。因此，“地形有自己的 Shader”不等于“地形有一套完全独立的渲染理论”。

> **一句话总结**：地形专用系统负责高效地产生三角形、混合大量地表材质并流送巨大纹理；产生标准几何和 PBR 参数以后，地形通常与普通 Mesh 一样参与主光、阴影、IBL、Lightmap/Probe、GI 和后处理。

## 7.1 高度图（Heightfield）

最基本的地形表达：一张灰度图存储高度信息，顶点按高度位移。配合材质和光照仍能有出色表现（至今仍是主力方法）。

**问题**：开放世界1km×1km = 200万三角形，更大则无法承受。

## 7.2 LOD（细节层次）

**两个原则**：

1. **近密远疏 + FOV相关**：近处密集，远处稀疏；FOV越窄（如倍镜），远处也需要高精度
2. **视相关误差界限**：保证屏幕空间误差不超过1像素

## 7.3 二叉三角形细分

- 每次将等腰直角三角形最长边切一刀 → 得到两个新等腰直角三角形
- 形成二叉树结构
- **T-Junction问题**：相邻三角形细分不一致时产生裂缝 → 强制切分对齐

## 7.4 四叉树（QuadTree）— 主流方案

**为什么四叉树胜出**：

- 符合人类直觉（切豆腐块）
- 与纹理/磁盘数据块对齐
- 天然暗含资源管理逻辑（一个Block包含高度图+贴图+植被+建筑）
- 与Virtual Texture无缝结合

**T-Junction的优雅解决：Stitching（吸附）**

- 将多余的顶点吸附到邻居边上
- 产生退化三角形（面积=0），保证水密性（Watertight）
- 比强制切分简单得多

## 7.5 GPU驱动的地形

### DX11 Tessellation管线

- Hull Shader → Tessellator → Domain Shader → Geometry Shader
- 命名被课程吐槽为"反人类"

### Mesh Shader（新一代）

- 一个Shader完成所有几何生成工作
- 需DX12以上/Vulkan
- 灵活度极高

### 可变形地形（Deformable Terrain）

- 基于GPU实时细分 + Deformation Texture
- 实现：拖拉机压痕、炮弹弹坑、脚印（如虚幻5演示）

## 7.6 复杂结构处理

- **悬崖**：传统做法直接放模型
- **隧道/洞穴**：顶点标记NaN → GPU自动剔除三角形 → 插入隧道模型
- **体素化+Marching Cubes**（前瞻）：三维空间采样，自然支持任意结构（洞、悬崖、拱门），类似《Minecraft》的创造自由度

# 第八章：地形渲染(下) — 材质与系统工程

## 8.1 材质混合基础

- **Splat Map**：存储各材质的权重（RGB通道各一种材质）
- 简单Alpha混合 → 效果不自然（沙子浮在石头上）

## 8.2 改进：基于高度的混合

- 利用Height Map，高处的材质权重下降慢（如石头突出），低处的快速退去（如沙子填充缝隙）
- 再加扰动（Blend）平滑过渡区域，避免硬切换和远处抖动

## 8.3 Texture Array

- 将几十上百种材质打包成纹理数组（按Index采样，层间无插值）
- 区别于3D Texture（三线性插值，层间有关系）
- Splatting Map同时存储权重和材质Index

## 8.4 Virtual Texture（虚拟纹理）— 行业标准

**核心思想**（John Carmack提出）：

- 将整个地形材质预烘焙到巨大的虚拟纹理
- 运行时只加载当前视角需要的Tile到显存缓存
- 类比：修车时只带当前需要的工具包，而不是拎一屋子工具

**两个巨大优势**：

1. **显存占用有上限**：无论世界多大，级数收敛
2. **运行时开销极低**：只需采样已烘焙好的Tile，不再逐像素混合多种材质

**配套硬件技术**：

- **DirectStorage**：压缩数据直接在GPU解压
- **DMA**：数据直接从SSD读到显存，跳过CPU和内存

> Virtual Texture = 学院派（Texture Array混合）→ 实战派的分水岭

## 8.5 浮点数精度问题

**现象**：远离原点（2~3km以上）时物体开始抖动（Z-fighting、顶点位置跳动）

**原因**：float32位在小数部分精度不够（IEEE 754限制）

**解决方案：Camera Relative Rendering**

- 将相机位置临时设为世界原点
- 所有物体坐标变为相对于相机的小数值 → 精度完全利用
- Unreal和Unity的标准做法

## 8.6 地形细节系统

- **树木渲染**：近处模型 → 中距离插片 → 远处Billboard（SpeedTree中间件）
- **Decorator**：草、灌木、碎石，用于增加环境多样性
- **道路系统**：样条曲线（Spline）生成 → 对高度场进行切割和腐蚀
- **Decal系统**：枪眼、弹孔等贴片，全部可烘焙到Virtual Texture

# 第九章：天空渲染 — 大气散射的物理与数学

## 9.0 先导：大气在渲染流程中做什么？

大气通常不是像地形、建筑那样具有真实反射表面的 Mesh，而是充满一片空间的**参与介质**。引擎有时会绘制一个天空球或全屏三角形，但它们只是限定绘制范围的代理几何，并不表示大气是一个球壳表面。

```text
普通物体：光碰到表面 → 使用PBR/BRDF计算反射
大气介质：光在空间中传播 → 沿途不断被吸收和散射
```

因此，把大气简单称为“透明物体”并不准确。普通透明物体仍有玻璃等明确表面，而大气主要使用体积渲染方程、介质密度、散射系数和相位函数描述光在空间中的变化。

### 9.0.1 大气影响两段光路

```text
太阳 → 大气 → 物体表面
```

大气决定到达地面的太阳光还剩多强、是什么颜色。傍晚时太阳光在大气中传播的路径更长，蓝光被更多地散射到其他方向，直接到达地面或眼睛的光便更偏红、更弱。

```text
物体表面 → 大气 → 相机
```

大气还会削弱物体原本的颜色，同时把沿途的天空散射光加入视线。远山距离越远，原有颜色和对比度越弱，大气贡献越强，因此会逐渐发蓝或发灰：

```text
相机看到的远山
= 远山经过PBR计算的颜色 × 大气透射率
 + 相机与远山之间的大气散射光
```

- **发蓝**：空气分子把较多蓝色天空光散射进相机
- **发灰**：雾、灰尘、水滴等气溶胶加入近似灰白的散射光，并降低远山的对比度和饱和度

### 9.0.2 它在渲染流程中的位置

大气不只属于一个 Pass，而是同时参与光照和最终画面合成：

```text
更新/预计算大气LUT
        ↓
Shadow Pass
        ↓
Geometry/Main Pass：绘制地形和普通物体
        ↓
Lighting Pass：PBR + 主光 + 阴影 + IBL/GI
        │          └── 主光强度和颜色可受大气透射影响
        ↓
Sky Pass：在没有不透明物体的背景像素上绘制天空
        ↓
Aerial Perspective：根据深度给远处物体叠加大气透射与散射
        ↓
云、雾、透明物体与后处理
```

所以第9章主要承担三个任务：

1. 计算天空本身的颜色
2. 改变太阳光穿过大气后的颜色和强度
3. 给远处物体添加空气透视效果

#### 补充：天空本身的颜色是怎么画出来的？

天空颜色不是某个天空表面经过 PBR 反射得到的，而是**太阳光在大气中散射后进入相机的结果**。太空背景近似为黑色；白天抬头看到蓝色，是因为太阳光进入大气后，空气分子更容易散射蓝光，其中一部分恰好向相机方向传播。

```text
太阳光进入大气
→ 空气分子和气溶胶散射光
→ 一部分散射光沿观察方向进入相机
→ 形成该方向上的天空颜色
```

Sky Pass 会为每个背景像素取得一条从相机出发、穿过大气的观察射线，并求这条射线上所有采样点散射到相机的光：

```text
相机
  └── 当前背景像素的观察方向
      ├── 采样点1：累积被太阳照亮后散射向相机的光
      ├── 采样点2：继续累积散射光
      └── 采样点3：继续累积散射光

天空颜色 ≈ 沿观察射线累积的大气内散射光
```

为了避免每个像素都做昂贵的完整 Ray Marching，实时引擎通常预先计算或动态更新低分辨率大气 LUT：

```text
大气参数 + 相机位置 + 太阳方向
→ 计算/更新大气LUT
→ Sky Pass按当前像素的观察方向查LUT
→ 输出HDR天空颜色
```

虽然大气本身没有真实表面，GPU 仍需要产生覆盖背景的像素来运行天空 Shader。常见做法是绘制一个全屏三角形、包围相机的天空球/天空盒，或者只处理深度缓冲中没有不透明物体的像素。这些三角形只是触发天空 Shader 的**代理几何**，不代表大气真的有一个参与 PBR 反射的球壳表面。

```text
先绘制地形和普通物体
→ 深度缓冲标记已有物体的像素
→ Sky Pass处理剩余背景像素
→ 根据观察方向查询大气LUT
→ 写入天空HDR颜色
```

三种颜色来源可以这样区分：

```text
地形/建筑：PBR表面光照

天空背景：沿观察射线累积的大气散射光

远处物体最终颜色：PBR表面颜色 × 大气透射率
                  + 物体与相机之间的大气散射光
```

天空 CubeMap 也可由同一个大气模型生成：从捕获点朝六个方向计算或查询 Sky Pass 本会得到的天空颜色，保存为 CubeMap，再预处理后提供给 IBL。

### 9.0.3 与 PBR、阴影、IBL 和 Lightmap 的关系

**与 PBR**：PBR 负责计算草地、岩石等表面如何反射入射光；大气负责改变光到达表面前，以及离开表面到达相机前的传播过程。二者前后衔接：

```text
太阳光穿过大气
→ PBR计算表面反射
→ 反射光再穿过大气到达相机
```

**与阴影**：大气透射率与 Shadow Map 解决不同问题：

```text
大气透射率：太阳光被空气吸收、散射掉多少
Shadow Map：太阳与表面点之间是否被山或建筑挡住
```

即使某个地形点没有被遮挡（$V_{shadow}=1$），傍晚的太阳光仍可能因为大气路径很长而变弱、变红。

**与 CubeMap / IBL**：大气系统能够计算“从某个位置朝某个方向看，天空是什么颜色和强度”。引擎可以在一个天空捕获位置向六个方向采样这些结果，生成少量 Sky CubeMap，再预处理成漫反射 Irradiance 和镜面预滤波贴图供 IBL 使用：

```text
大气散射模型
→ 各方向的天空颜色与强度
→ Sky CubeMap
├── 漫反射卷积 → Irradiance Map / SH
└── 镜面预滤波 → Prefiltered Environment Map
```

通常不会在整个大气中密集放置点并为每个点生成 CubeMap。普通地面场景常使用一张全局天空 CubeMap，或直接查询大气 LUT；室内外差异较大的场景则放置少量 Reflection Probe，它们捕获的 CubeMap 可以同时包含建筑、地形和天空大气。

**与 Lightmap / GI**：天空光和太阳光可以作为光源参与 Lightmap 烘焙和表面 GI。Lightmap 是表面上的预计算结果，大气则提供其中一部分入射光；如果天空间接光已经烘焙进 Lightmap，运行时就需要避免再次无条件叠加同一份漫反射天空光。昼夜循环场景则更常结合动态天空、动态 IBL、Light Probe 或实时 GI。

#### 补充：看得见天空盒，不等于天空一定参与光照

天空盒或大气天空的 HDR 颜色和强度可以同时成为 Lightmap 与 CubeMap/IBL 的输入，但是否参与、参与多少取决于引擎的环境光和烘焙设置：

```text
天空盒 / 大气天空
├── 作为烘焙环境光源 → 天空光照到静态表面并参与反弹 → 写入Lightmap
└── 被Sky Light或Reflection Probe捕获 → 生成CubeMap
                                      ├── 漫反射Irradiance / SH
                                      └── 镜面预滤波环境贴图
```

烘焙 Lightmap 时，蓝色天空可以让室外背阴面略微偏蓝；窗户、屋檐和墙体会遮挡天空光，所以室内和墙角通常更暗。Lightmap 最终存仅间接光，还是直接光与间接光的组合，取决于具体烘焙模式。

CubeMap/IBL 则保存天空与周围环境的方向分布：潮湿地面、金属和玻璃会产生明显的天空镜面反射；粗糙非金属表面主要获得漫反射天空照明。

很多引擎会把“天空显示亮度”和“环境光照强度”分成两个设置，因此可能出现“背景天空很亮，但没有照亮 Mesh”的情况。只有启用了 Sky Light、Environment Lighting、Reflection Capture、Bake Lighting 等相应功能，天空才会成为 PBR、Lightmap 或 IBL 的有效光源。

还要避免重复计光。例如天空间接漫反射已经烘焙进静态物体的 Lightmap 后，运行时再给这些物体叠加一份完整的漫反射 IBL，可能重复计算同一份天空光。一种常见分工是：

```text
静态表面的漫反射间接光 → Lightmap
动态物体的漫反射间接光 → Light Probe / Irradiance Volume
静态与动态物体的镜面环境反射 → CubeMap / Reflection Probe
```

### 9.0.4 光柱（丁达尔效应）如何产生？

光柱属于同一套参与介质理论，但游戏中明显的局部光柱通常由第12章的**体积雾**系统实现。它需要两个条件：空气中存在可散射粒子，并且光被建筑、山体或树木部分遮挡。

实现时沿相机视线做 Ray Marching：

```text
相机 ── 采样点1 ── 采样点2 ── 采样点3 ──→ 场景
```

对每个采样点执行：

1. 读取该处介质密度
2. 查询太阳或灯光方向的 Shadow Map
3. 能看见光源的空气计算并累积散射光
4. 被几何挡住的空气贡献较小或没有贡献
5. 将所有采样点的散射和透射累积到相机

```text
被光照亮的空气       → 明亮
位于几何阴影中的空气 → 较暗
明暗区域形成可见光柱
```

因此 Shadow Map 不仅能判断地面是否处于阴影，也可以在体积采样点判断空气是否被光源照亮。第9章提供大气散射的物理基础，第12章体积雾则更侧重在局部场景中高效实现明显的光柱、雾和体积阴影。

> **一句话总结**：大气没有普通物体那样的反射表面，它通过吸收和散射改变光的传播；它既影响到达表面的太阳光，也生成天空 IBL，并在表面完成 PBR 光照后为远处物体添加空气透视。光柱则是”参与介质散射 + 光源遮挡”的结果。

### 9.0.5 补充：天空/云/雾的Pass机制、渲染本质与双向关系总表

#### 三者都没有真实 PBR Mesh

天空、云、雾与实物几何体的本质区别：

|               | 实物（建筑/地形）   | 天空                                    | 云                  | 雾                     |
| ------------- | ------------------- | --------------------------------------- | ------------------- | ---------------------- |
| 有 mesh？     | ✅ 顶点+三角形      | ⚠️ 只有代理 mesh（天空球/全屏三角形） | ❌                  | ❌                     |
| 用 PBR BRDF？ | ✅                  | ❌                                      | ❌                  | ❌                     |
| 颜色来源      | 材质参数 + 光照方程 | 大气散射 LUT                            | 体积密度 + 散射方程 | 深度公式 / 3D 纹理查表 |

天空的代理 mesh 只是”告诉 GPU 对这些像素跑天空 Shader”，它没有材质、不走 PBR，不代表大气真的有球壳表面。云和雾连代理 mesh 都没有，完全靠 Shader 和 Depth Buffer 驱动。

#### 三者是独立 Pass，按顺序合成到屏幕

```text
① GBuffer 填充（PBR 材质写入）
② 光照计算（直接光×ShadowMap + IBL/Lightmap）→ Scene Color
③ 天空 Pass   ← 只处理 depth=1.0 的背景像素，查大气 LUT
④ 云 Pass     ← 全屏低分辨率 Ray March，alpha blend 叠加
⑤ 雾 Pass     ← 全屏，读 Depth → 公式或查 3D Texture
⑥ 后处理（AO、AA、Bloom、Tone Mapping）
```

Depth Buffer 是协调员：天空 Pass 靠 depth=1.0 找背景像素，雾 Pass 靠深度值计算每像素距离。

**三者计算方式的关键差异：**

| Pass   | 处理哪些像素              | 有无 Ray March    | 计算方式                                     |
| ------ | ------------------------- | ----------------- | -------------------------------------------- |
| 天空   | 只有背景像素（depth=1.0） | ❌                | 查预计算大气 LUT                             |
| 云     | 全屏（低分辨率后放大）    | ✅ 逐像素         | Ray March 云体积密度场                       |
| 简单雾 | 全屏                      | ❌                | 读深度 → lerp 公式                          |
| 体积雾 | 全屏                      | ⚠️ 预计算阶段有 | Compute Pass 体素化 3D Texture，像素阶段查表 |

#### 物理现实 vs 游戏渲染的差异

物理上，光从太阳出发到进入眼睛是一个统一路径积分，大气、云、雾同时参与：

```text
太阳 ──[大气]──[云]──[雾]──→ 地面 PBR ──[雾]──[云]──[大气]──→ 眼睛
                    所有介质耦合在同一个积分里
```

游戏渲染将其拆解为独立 Pass 串联近似：

| 物理过程          | 游戏近似方式                   | 忽略的误差                 |
| ----------------- | ------------------------------ | -------------------------- |
| 光穿大气到表面    | 大气预设太阳光颜色/强度        | 不同距离路径长度差异       |
| 表面反射          | PBR + 全局 IBL（一张 CubeMap） | 雾中物体应接收更散漫的 IBL |
| 云的遮光          | Cloud Shadow Map 独立乘进光照  | 云下 IBL 应更灰更均匀      |
| 雾中传播          | 深度 lerp 或 3D 纹理查表       | 雾粒子精确散射积分         |
| 反射光穿回大气/雾 | 反射 CubeMap 无雾              | 浓雾场景的反射应该也朦胧   |

近似可行的原因：人眼对绝对精度不敏感，对整体颜色一致性敏感。现代引擎（UE5 Sky Atmosphere + Exponential Height Fog + Volumetric Cloud）让三个系统共享同一个太阳方向和大气参数，颜色天然协调。

#### 天空/云/雾 与 Lightmap/CubeMap/Shadow Map 双向关系总表

**正向：天空/云/雾 → 影响三图数据**

|                | Lightmap                                             | CubeMap / IBL                                                 | Shadow Map                                                |
| -------------- | ---------------------------------------------------- | ------------------------------------------------------------- | --------------------------------------------------------- |
| **天空** | ✅ 烘焙时作为光源，天空光写入静态表面间接光          | ✅ 是 CubeMap 的主要数据来源（大气模型→Sky CubeMap→IBL）    | ❌                                                        |
| **云**   | ⚠️ 理论可烘，实际不烘（云动态变化，Lightmap 静态） | ✅ 捕获时被记录（阴天 Irradiance 更灰更均匀，金属可反射云层） | ✅ 生成独立 Cloud Shadow Map（V_cloud），乘进地面光照公式 |
| **雾**   | ❌                                                   | ❌                                                            | ❌                                                        |

**反向：三图数据 → 影响天空/云/雾的计算**

|                      | 天空                         | 云 | 雾（简单） | 雾（体积）                                                 |
| -------------------- | ---------------------------- | -- | ---------- | ---------------------------------------------------------- |
| **Lightmap**   | ❌                           | ❌ | ❌         | ❌                                                         |
| **CubeMap**    | ❌（天空是来源，不是消费者） | ❌ | ❌         | ❌（雾采样天空大气 LUT，不是 CubeMap）                     |
| **Shadow Map** | ❌                           | ❌ | ❌         | ✅ 每个采样点查 Shadow Map，判断空气是否被照亮 → 实现光柱 |

> **规律总结**：正向几乎都是”天空/云作为数据来源写入”；反向几乎全是单向——唯一的反向依赖是 **Shadow Map → 体积雾**（光柱效果），Lightmap/CubeMap 对三者均无反向影响。

## 9.1 天空 ≠ 云

- **天空（大气）**：延伸到卡门线（100km），是一个抽象的球体
- **云**：离地面几百米到几千米，有体量感

## 9.2 参与介质（Participating Media）

大气由气体分子（N₂, O₂, O₃, CH₄）和气溶胶（灰尘、小水珠）构成，光在其中传播时发生：

1. **吸收（Absorption）**：能量被介质吸收（系数σa）
2. **外散射（Out-scattering）**：光打中粒子后向四周散射（系数σs）
3. **自发光（Emission）**：高温气体发光（游戏中通常忽略）
4. **内散射（In-scattering）**：周边粒子散射的光又打到当前粒子（最复杂，涉及球面积分）

合成为**辐射传递方程（RTE）**

## 9.3 两个关键变量

从眼睛看向远处一点M：

- **透射率（Transmittance）**：M点光线穿透大气到达眼睛的比例
- **内散射函数（In-scattering）**：沿途所有粒子散射到眼睛的光的总和

两者结合 = **体积渲染方程（Volume Rendering Equation）**

## 9.4 两种散射模型

### 瑞利散射（Rayleigh Scattering）

- 条件：粒子尺寸 ≪ 光波长（气体分子）
- 特点：对短波（蓝/紫）散射强（~1/λ⁴），相对均匀
- 相位函数：花生/腰果形（1+cos²θ）
- **解释**：白天天空蓝（蓝光被大气散射到眼中）、傍晚天空红（太阳斜射，蓝光散射出大气层，红光留下）

### 米氏散射（Mie Scattering）

- 条件：粒子尺寸 ≈ 光波长（气溶胶）
- 特点：有方向性，对波长不敏感
- 相位函数：引入参数G控制形状（G=0退化为瑞利散射）
- G参数开放给美术调整
- **解释**：雾是白色（无差别散射）、日晕/路灯光晕（有方向性散射）

## 9.5 单次散射 vs 多次散射

- **单次散射**：视线路径上粒子被太阳照亮 → 散射到眼睛
- **多次散射**：不在视线上的粒子照亮路径上的点 → 再散射到眼睛
- 没有多次散射 = 山背面死黑，有多次散射 = 大气点亮了暗部

> 多次散射 ≠ GI。GI是清晰表面的反射，多次散射是连续空间介质的积分。类比：充满空间的"以太"。

## 9.6 经典算法：预计算大气散射（Bruneton 2006）

**核心工具：Ray Marching**（沿视线逐步积分）

**预计算四个表**：

1. **透射率表**（2D）：海拔高度 + 视线与天顶夹角
2. **单次散射表**（4D）：三个角度 + 海拔高度
3. **多次散射表**：用单次散射结果迭代2~3次
4. 假设大气各向同性 → 三个角度（太阳天顶角、视线天顶角、视线太阳角）即可表达所有散射值

**运行时**：根据太阳位置和视线方向查表+插值 = 极快

**缺点**：预计算费时、大气参数写死（无法动态天气）、高维表插值仍有开销

## 9.7 前沿方法：实时可扩展方案（UE在用）

**核心思想：大胆假设 + 合理简化**

1. **假设多次散射各向同性** → 散射变为百分比衰减 → 用级数求和即可求解
2. **每帧去掉多余维度**：太阳位置固定 → 去掉太阳维度；人在固定高度 → 去掉海拔维度
3. 最终只用天顶角+环角两个维度表达天空

**优势**：支持动态天气、多太阳、异星大气、美术友好

**局限**：散射度过高时可能出现误差和色偏

# 第十章：云渲染 — 体积云建模

## 10.0 先导：没有 Mesh 的云如何被渲染？

现代体积云通常没有三角形表面，而是用一个可在任意空间位置查询的**三维密度场**表示。云的密度一般由大范围天气分布、高度函数和三维噪声共同决定：

```text
云密度 density(x,y,z)
= Weather Texture：决定哪些区域有云、覆盖率和云层厚度
× 高度函数：决定云底、云顶和垂直形状
× Perlin/Worley 3D Noise：产生蓬松、破碎的云团细节
```

可以把它想象成一个看不见的三维格子：数值为 0 的地方没有云，数值越高的地方云越浓。云的轮廓不是预先建好的硬边界，而是密度从 0 逐渐升高、再逐渐回到 0 的区域。

### 10.0.1 摄像机射线如何形成云的轮廓

渲染器会为屏幕上的相关像素构造一条数学上的观察射线。它不是摄像机真的发射物理光线，而是从最终可见像素反向查询这条视线穿过了哪些云（摄像机往屏幕所有像素点发射射线主动探测云）：

```text
现实世界：太阳发光 → 光在云中散射 → 一部分光进入摄像机

渲染计算：从摄像机像素沿视线反查
          → 与云层高度范围求交
          → 在进入点和离开点之间逐步采样
          → 累积散射光与不透明度
```

例如某条视线采到的密度为：

```text
相机 → 0 → 0.1 → 0.5 → 0.9 → 0.4 → 0 → 天空
             └──────── 云团 ────────┘
```

- 没有经过高密度区域的射线显示天空
- 擦过低密度区域的射线形成半透明云边
- 穿过高密度中心的射线形成浓厚云体

相邻像素的射线穿过不同密度，最终自然拼成云的轮廓。GPU 常通过全屏三角形或 Compute Shader 启动这些计算；全屏三角形只是代理几何，并不是云的真实表面。

### 10.0.2 云为什么有明暗和立体感

Ray Marching 在每个采样点不只读取密度，还会估算太阳光到达该点后剩余多少，以及有多少光散射向相机：

```text
采样点的颜色贡献
≈ 云密度
× 到达该点的太阳光
× 向相机方向散射的比例
× 该点到相机的透射率
```

通常还会从采样点朝太阳方向做一次简化的光照步进，用来估算云内部的遮挡和衰减。因此云会表现出：

- 向阳面和较薄的边缘明亮
- 高密度内部和云底较暗
- 背光时出现明亮银边
- 多重散射近似让暗部仍保留柔和亮度

### 10.0.3 它在渲染流程中的位置，以及与 PBR 的关系

云通常属于天空/体积效果阶段，在不透明物体完成 PBR 光照后、最终后处理之前合成：

```text
更新大气、Weather Texture和云密度参数
        ↓
Shadow Pass：普通几何阴影 + 可选的云阴影数据
        ↓
Geometry/Main Pass：绘制地形、建筑和角色
        ↓
Lighting Pass：PBR + 主光 + 阴影 + IBL/GI
        ↓
Sky Pass：绘制大气天空
        ↓
Volumetric Cloud Pass
├── 沿观察射线Ray Marching
├── 计算云的透射与散射
├── 读取场景深度，处理云与山体等物体的前后关系
└── 与天空及场景颜色合成
        ↓
雾、透明物体、TAA、Bloom、Tone Mapping等
```

PBR 与体积云处理的对象不同：

```text
普通Mesh：光碰到明确表面 → 使用PBR/BRDF计算反射
体积云：光在云的内部传播 → 使用密度、透射率、散射系数和相位函数
```

所以云不使用普通表面 PBR 公式计算颜色，但它和 PBR 表面共享同一个太阳、大气、阴影及最终 HDR/后处理体系。

### 10.0.4 云对主光、Lightmap 和 CubeMap/IBL 的影响

**对主光**：云会遮挡太阳，使地面接收到的实时主光变弱，并产生范围很大的柔和云影：

$$
L_{direct}=L_{sun}\,f_{PBR}\,V_{geometry}\,V_{cloud}
$$

- $V_{geometry}$：山体、建筑等由 Shadow Map 得到的几何阴影可见性
- $V_{cloud}$：太阳光穿过云层后的透射率

引擎通常使用低分辨率 Cloud Shadow Map 或云透射纹理，将移动的云影投射到地形和建筑上。

**对 Lightmap**：理论上，固定云层的遮光和散射可以参与烘焙；但云通常会移动和变形，烘入 Lightmap 后无法随天气更新。因此常见分工是：

```text
Lightmap → 保存固定场景的预计算光照
云阴影   → 运行时动态计算并衰减主光
```

**对 CubeMap / IBL**：如果天空 CubeMap 或 Reflection Probe 捕获时包含云，CubeMap 中也会记录云的颜色和方向分布。预处理后，云会影响 PBR 表面的环境光与镜面反射：

```text
大气天空 + 云
→ 捕获/更新Sky CubeMap
├── 漫反射Irradiance：阴天时环境光可能更暗、更灰、更均匀
└── 镜面预滤波环境贴图：积水、金属和玻璃可反射云层
```

动态云移动后，静态 CubeMap 不会自动变化，因此需要定期或分帧重新捕获，或者直接从实时天空/云系统近似计算环境光。

> **一句话总结**：Mesh 用三角形决定轮廓、用 PBR 决定表面颜色；体积云用三维密度决定轮廓和透明度、用体积散射决定颜色。云还会实时削弱主光并投下云影，可以被 CubeMap 捕获从而影响 IBL，但动态云通常不会烘进静态 Lightmap。

### 10.0.5 补充：反向关系——Lightmap/CubeMap/Shadow Map 对云的影响

云计算自身颜色时，依赖的是**体积散射方程 + 太阳光方向**，不读取任何预计算贴图：

- **Lightmap → 云**：❌ Lightmap 存的是表面间接光，云没有表面，不走 PBR，不读 Lightmap。
- **CubeMap → 云**：❌ 云用密度场和相位函数决定颜色，不需要环境反射贴图。云是光穿透的体积，不是反射环境的表面。
- **Shadow Map → 云**：❌ 云的光照靠"向太阳方向在云体内 Ray March 密度（自遮挡）"计算，不查地面几何体的 Shadow Map。云给地面投影用的是它自己生成的 Cloud Shadow Map，方向相反——是云影响 Shadow Map，不是 Shadow Map 影响云。

> **规律**：云是数据的**输出者**（写入 Cloud Shadow Map、影响 CubeMap 捕获），而不是 Lightmap/CubeMap/Shadow Map 的**消费者**。

## 10.1 云的分类

三种基本类型在不同高度的组合：

- **层云（Stratus）**：薄层状
- **积云（Cumulus）**：棉花状
- **卷云（Cirrus）**：羊毛状

## 10.2 演进历程

1. **Mesh几何体**（学术尝试，不实用）
2. **半透明插片/面片**（棉花糖，10年前网游水平）
3. **体积云（Volumetric Cloud）**（现代3A标配）

## 10.3 体积云生成

**天气纹理（Weather Texture）**：

- 定义云的空间分布 + 厚度（0~1）
- 平移纹理 → 云飘动；扰动纹理 → 云变化

**噪声函数塑造云形**：

- **Perlin Noise**：棉花丝状效果
- **Worley Noise（Voronoi）**：絮状/细胞状效果
- 分层叠加（多频率噪声腐蚀 + 细节添加）模拟分形效果

## 10.4 体积云渲染

**Ray Marching of Cloud**：

1. 大步长快速接近云层
2. Hit后小步长精细步进（0.5~1m）
3. 每个采样点计算透射和散射（简化多次散射）
4. 飞出云层边界停止

**性能优化**：

- 对光学方程做大量简化假设
- 低分辨率采样 + 上采样

# 第十一章：环境光遮蔽（AO）— "立体感的秘密"

## 11.0 先导：为什么已有 Lightmap、CubeMap 和阴影，还需要 AO？

AO（Ambient Occlusion）估算的是一个表面点周围有多“封闭”，也就是法线上方半球的许多环境光方向中，有多少被附近几何挡住：

```text
空旷墙面：能看见大部分天空和周围环境 → 接收较多环境光
墙角缝隙：许多方向被两面墙和地面挡住 → 接收较少环境光
```

因此，墙角、物体接触处和细小凹槽通常会稍暗。AO 不是新的光源，也不是完整 GI，而是对**环境光/间接光的局部可见性**所做的低成本近似。

### 11.0.1 它在渲染流程中的位置

以延迟渲染中的 SSAO/GTAO 为例：

```text
Geometry Pass
→ 生成Depth、Normal等G-Buffer
        ↓
AO Pass
→ 根据深度和法线估算附近几何遮挡
        ↓
Lighting Pass
├── 直接光照 × Shadow Map可见性
└── 环境/间接光照 × AO可见程度
        ↓
天空、雾、AA、Bloom、Tone Mapping等
```

概念上可以简化为：

$$
L \approx L_{direct}V_{shadow}+L_{ambient/indirect}AO
$$

其中 AO 通常约定为 0～1：1 表示周围较开阔，0 表示高度遮蔽。AO 主要衰减环境光和间接光，不应该简单地把太阳等明确光源的直接光整体乘暗；直接光的遮挡主要由 Shadow Map 负责。

具体引擎也可能先完成部分光照，再把 AO 结果合成进去，但它的物理职责仍应理解为“环境/间接光的局部遮蔽”。

### 11.0.2 Lightmap 不是已经算进遮挡了吗？

是的。高质量 Lightmap 在烘焙静态 GI 时会考虑几何遮挡，因此静态墙角、屋檐和家具底部的间接光明暗通常已经包含在 Lightmap 中。对于这些区域，理论上不一定需要再次叠加强 AO。

但 Lightmap 仍有局限：

- 只能正确反映烘焙时的静态几何关系
- 角色、箱子等动态物体移动后产生的新接触遮挡不在其中
- Lightmap 分辨率有限，细小凹槽和接触细节可能丢失
- 动态场景或没有 Lightmap 的管线无法依靠它
- Light Probe 等稀疏光照数据也难以表现局部遮挡细节

所以实时 AO 常用于补充角色脚底、临时摆放物体、动态物体之间以及低分辨率 GI 遗漏的局部接触阴影。若 Lightmap 已经准确包含某处遮挡，再叠加过强 AO 会使墙角“脏黑”，属于重复计算。

### 11.0.3 CubeMap / IBL 不是也包含环境遮挡吗？

CubeMap 通常记录的是**探针位置**在各个方向上有什么光，而不是每个实际表面点周围有多少方向被局部几何挡住。例如房间中央的 Reflection Probe 可以看见明亮窗户，但角落表面实际上被两面墙包围；角落直接借用该 CubeMap 时可能获得过多环境光。

```text
CubeMap / IBL：环境中各个方向有多少光？
AO：当前表面点的这些方向中，有多少被附近几何挡住？
```

二者结合可以近似理解为：

```text
最终漫反射环境光 ≈ IBL环境光 × AO可见程度
```

镜面环境反射的遮挡还与反射方向和粗糙度有关，通常需要 Specular Occlusion 等更专门的近似，不能总是直接照搬普通漫反射 AO。

### 11.0.4 AO、Shadow Map 与 GI 的职责区别

| 技术                        | 回答的问题                                     | 主要影响                         |
| --------------------------- | ---------------------------------------------- | -------------------------------- |
| **Shadow Map**        | 朝某个明确光源的方向是否被挡住？               | 太阳、点光源等直接光             |
| **AO**                | 当前点周围半球中有多少环境方向被附近几何挡住？ | 环境光和间接光的局部近似         |
| **Lightmap / 实时GI** | 光经过表面反弹后，实际有多少间接光到达这里？   | 更完整的间接光照、反弹颜色和遮挡 |
| **CubeMap / IBL**     | 周围各个方向提供什么颜色和强度的环境光？       | 漫反射环境光与镜面环境反射       |

以桌子下方为例：太阳是否被桌面挡住由 Shadow Map 判断；四周环境光能进入多少可由 AO 近似；墙面和地面真正反弹过来多少光则由 Lightmap 或实时 GI 计算；CubeMap/IBL 提供环境光本身的方向和颜色。

> **一句话总结**：Lightmap 能为静态场景较准确地包含遮挡，但无法覆盖所有动态和细小接触关系；CubeMap/IBL 提供环境光，却通常缺少当前表面点的局部遮挡信息。因此 AO 被单独提出，用较低成本补充环境光的局部可见性。

## 11.1 AO是什么

表面上的点，其可见半球面只有部分能看见天光，其余被周围几何遮挡。这种微小的明暗变化对人眼构建3D空间感至关重要。

> 开AO vs 关AO = 场景立即从"平平无奇"变得"凹凸有致"

## 11.2 预计算AO

- 高模细节烘焙到低模的AO贴图（如角色面部皱纹）
- 空间换时间，但不能处理动态物体间的遮挡

## 11.3 SSAO（Screen Space Ambient Occlusion）

**核心思想**：利用深度缓冲重建高度场 → 在屏幕空间估算每个像素的遮挡程度

**原始问题**：对整个球采样，平面也有一半点"被遮挡"

**改进**（SSAO+）：基于法线只采半球面

**缺陷**：无法区分远近，远距离物体也产生虚假AO阴影

## 11.4 HBAO（Horizon-Based AO）

- 寻找每个方向上能看到天顶的最高仰角（Horizon Angle）
- 引入衰减函数（Attenuation）：太远的几何不产生AO
- 使用Ray Marching + 方向Jitter（避免采样Pattern）

## 11.5 GTAO（Ground Truth-based AO）

- 引入Lambert的余弦因子（cosθ）：天顶方向的光贡献大，斜射贡献小
- **最大创新**：通过AO值拟合多次散射结果（三阶多项式），从黑白AO变为带色彩和色相的AO
- 含统计拟合思想，与真实离线算法结果几乎一致

## 11.6 光线追踪AO（Ray-Traced AO）

- GPU硬件射线投射 → 每帧每像素1~2根光线 + 时序累积
- 前沿方向，逐渐替代屏幕空间方法

# 第十二章：雾效 — 从简单深度雾到体积雾

## 12.1 基础雾效

- **Depth Fog**：随距离增加，透明度下降
- Linear / Exponential / Exp² 三种公式
- 简单但不真实（无高度变化）

## 12.2 高度雾（Height Fog）

- 低处雾浓，高处雾淡（指数递减）
- 计算需要路径积分（非均匀雾浓度）
- 古典时代：假设浓度与透明度线性相关 → 求出解析解

## 12.3 体积雾（Volumetric Fog）— 现代方案

- 产生光柱等体量感效果
- **方法**：视锥体素化（近处密、远处疏的不均匀Grid）+ Ray Marching积分
- 存储为3D Texture（横竖比16:9对应屏幕像素）
- 与天空/云渲染同思想、同框架

## 12.3.5 补充：雾的数据结构详解

雾没有 mesh，不同类型的雾采用完全不同的数据结构。

### Depth Fog / Height Fog — 几乎没有数据结构

本质上只是一组**标量参数**，存在 Shader 的 Constant Buffer（常量缓冲区）里：

```
// Depth Fog 参数
float fogStart;         // 雾开始的距离
float fogEnd;           // 雾完全不透明的距离
vec3  fogColor;         // 雾的颜色
float fogDensity;       // 密度（指数雾用）

// Height Fog 额外参数
float fogHeight;        // 雾层的基准高度
float fogHeightFalloff; // 高度衰减系数（指数递减速率）
```

运行时唯一读取的外部数据是已有的 **Depth Buffer**（GBuffer 阶段生成，不是雾自己的数据），从中取深度值 → 算距离 → 代入公式：

```
fogFactor = 1 - exp(-density × distance)   // Exponential 雾
finalColor = lerp(sceneColor, fogColor, fogFactor)
```

没有任何纹理、没有任何 3D 数据结构，纯参数 + 数学公式。

### Volumetric Fog — 核心数据结构是 Froxel 3D Texture

体积雾的关键数据结构叫 **Froxel**（Frustum Voxel，视锥体素），把相机视锥体切成三维格子：

```
视锥体
近平面 ───────────────────────── 远平面
│  ┌──┬──┬──┬──┬──┐            │
│  ├──┼──┼──┼──┼──┤← 横向/纵向按屏幕比例切   │
│  └──┴──┴──┴──┴──┘            │
│  深度方向切64层（对数分布）     │
└───────────────────────────────┘
```

典型分辨率：**160 × 90 × 64**（16:9 对应屏幕，64 个深度层）

深度方向用**对数分布**，近处层密集（近处细节多，如室内光柱），远处层稀疏：

```cpp
struct Froxel {
    vec3  scattering;    // 该格子里光的散射量（RGB）
    float extinction;    // 消光系数（吸收 + 散射总损耗）
    // 积分后版本：
    vec3  inscattering;  // 已积分的入射散射光
    float transmittance; // 已积分的透射率（0~1）
};
```

### 体积雾的三步计算流程

```
① Inject Pass（Compute Shader）
   对每个 Froxel：
   ├── 用高度/密度公式计算该格子的雾浓度
   ├── 查询 Shadow Map 判断该点是否被光照（光柱来源）
   └── 写入 scattering + extinction → 3D Texture A（密度场）

② Accumulation Pass（Compute Shader，Ray March 在这里）
   沿相机方向从近到远逐层积分：
   ├── 读取 3D Texture A 每层散射/消光
   ├── 累积 transmittance（乘法衰减）
   └── 写出 3D Texture B（已积分的颜色+透明度）

③ Composite Pass（Pixel Shader）
   每个屏幕像素：
   ├── 用深度值映射到视锥中的 3D 坐标
   ├── 查询 3D Texture B → 取该深度的雾贡献
   └── 混合到 Scene Color
```

### 三种雾的数据结构对比

|                | 数据结构               | 内存占用                    | GPU 阶段                  |
| -------------- | ---------------------- | --------------------------- | ------------------------- |
| Depth Fog      | 常量参数（< 100 字节） | 极小                        | Pixel Shader 公式         |
| Height Fog     | 常量参数（< 200 字节） | 极小                        | Pixel Shader 公式         |
| Volumetric Fog | Froxel 3D Texture      | 160×90×64×RGBA16F ≈ 7MB | Compute×2 + Pixel Shader |

### 与云的数据结构对比

两者都是体积效果，但描述方式不同：

|              | 云                                              | 体积雾                                |
| ------------ | ----------------------------------------------- | ------------------------------------- |
| 密度定义方式 | Weather Texture（2D）+ Perlin/Worley 噪声（3D） | 数学参数公式（高度指数衰减）          |
| 计算空间     | 世界空间（固定高度带，相机移动时不变）          | 视锥空间（Froxel 随相机走，每帧重建） |
| 分辨率       | 1/4~1/8 屏幕，再上采样                          | 160×90×64，再查表                   |
| 最终存储     | 屏幕空间低分辨率颜色缓冲                        | 3D Texture（视锥空间）                |

云的形状由噪声纹理"雕刻"，每帧 Ray March 现算；体积雾的形状由参数公式控制，用 Froxel 预积分后查表，因此体积雾比体积云快得多。

## 12.4 补充：雾在渲染管线中的位置

### 12.4.1 完整每帧渲染顺序（延迟渲染为例）

```text
① Shadow Map 生成
② Depth Pre-pass
③ GBuffer 填充（PBR 材质属性写入）
④ 光照计算（直接光 × Shadow Map + IBL/Lightmap）→ Scene Color
⑤ 天空 Pass（只处理 depth=1.0 的背景像素）
⑥ 云 Pass（全屏低分辨率 Ray March，alpha blend）
⑦ AO（SSAO/GTAO）
⑧ 【雾效 Pass】← 在这里
⑨ 抗锯齿（TAA/FXAA）
⑩ Bloom → Tone Mapping → Color Grading
```

雾拿到的是已经算完 PBR + 光照 + 阴影 + 天空 + 云 的"最终场景颜色"，在上面做一层混合。它不参与也不修改之前任何 Pass 的数据。

### 12.4.2 三种雾的实现方式对比

| 类型                   | 有无 Ray March    | 计算方式                                                        | 处理像素范围 |
| ---------------------- | ----------------- | --------------------------------------------------------------- | ------------ |
| Depth Fog / Height Fog | ❌                | 读 Depth Buffer → 代入公式 →`lerp(sceneColor, fogColor, t)` | 全屏         |
| Volumetric Fog         | ⚠️ 预计算阶段有 | Compute Pass 把视锥体素化成 3D Texture，像素阶段只查表          | 全屏         |

简单雾完全没有射线，只是一个数学公式。只有体积雾会做 Ray March，但它把结果存入 3D Texture，像素着色阶段做的只是查表。

### 12.4.3 雾与 Lightmap / CubeMap / Shadow Map 的关系

**正向（雾影响三者）：全部 ❌**

雾是后处理，在所有预计算/实时数据生成完毕后才运行，不修改任何贴图数据。

**反向（三者影响雾的计算）：**

|                                | 影响雾吗？ | 说明                                                                                                    |
| ------------------------------ | ---------- | ------------------------------------------------------------------------------------------------------- |
| **Lightmap → 雾**       | ❌         | Lightmap 只被 PBR 表面读取，雾不是表面，不读 Lightmap                                                   |
| **CubeMap → 雾**        | ❌         | 体积雾的散射颜色来自天空大气系统（Sky Atmosphere）输出的地平线颜色，直接查大气 LUT，绕过 CubeMap 这一层 |
| **Shadow Map → 体积雾** | ✅         | 体积雾 Ray Marching 每个采样点时查询 Shadow Map，判断该处空气是否被光照到 → 实现光柱（丁达尔效应）     |

光柱的具体逻辑：

```text
体积雾采样点：
  ├── 查 Shadow Map：该点在阴影中吗？
  ├── 光照中 → 累积亮散射 → 光柱亮区
  └── 阴影中 → 贡献极小 → 光柱暗区
明暗交界 = 可见光柱
```

简单深度雾/高度雾不查 Shadow Map；只有体积雾才有此依赖。这也是 Shadow Map 对天空/云/雾三者中**唯一的反向有效影响**。

### 12.4.4 雾与天空/云之间"颜色一致性"问题

三者是独立 Pass，颜色若不协调会出现割裂感：

- **简单雾 + 物理天空**：雾色固定为灰色，天空地平线是蓝橙渐变 → 远处物体淡向灰色而非天空色 → 视觉割裂
- **解决方案**：体积雾（UE5 Exponential Height Fog）绑定 Sky Atmosphere，动态采样地平线颜色作为雾色 → 远景淡向天空颜色，天然无缝

雾、天空、云在空间上是不同高度层，天然不重叠：

```text
高度
 ↑
6000m ── 云（Volumetric Cloud）
2000m ── 云底
  │
 500m ── 高度雾稀薄区
   0m ── 高度雾浓集区
```

只要三个系统共享同一个太阳方向和大气参数，视觉上就能保持物理一致。

# 第十三章：抗锯齿（AA）— 与"锯齿"的斗争

## 13.1 锯齿的三大来源

1. **几何边缘**：三角形边不横平竖直
2. **纹理采样**：摩尔纹（已被Mipmap解决）
3. **高光变化**：快速移动的高光产生高频信号变化

> 本质：屏幕分辨率有限，而世界信号频率无限

## 13.2 SSAA（Super-Sampling AA）

- 渲染4倍分辨率 → 下采样
- 效果最好，但代价是4倍的Z-buffer、Frame buffer和Pixel Shader

## 13.3 MSAA（Multi-Sample AA）

- 仅对几何边缘进行多重采样
- 内部像素只Shade一次
- 硬件直接支持，但几何密度超过像素时失效（如Nanite场景）

## 13.4 FXAA（Fast Approximate AA）

**核心思想**：基于已有图像后处理，不需要额外几何信息

1. 转亮度空间（绿>红>蓝的权重公式）
2. 检测边缘（十字滤波 + 阈值判断）
3. 判断边缘方向（竖向/横向卷积）
4. 找边缘端点 → 用相似三角形原理计算混合权重
5. 利用纹理插值实现颜色混合

> 只用初中数学就解决了问题！速度快，效果可接受。

## 13.5 TAA（Temporal AA）— 主流方案

**核心思想**：利用历史帧数据

- **Motion Vector**：记录像素在前后帧的位置映射
- 当前帧与历史帧加权混合
- 高速运动时更相信当前帧；静止时两边权重相当

**问题**：可能产生错位（Offset）和残影（Ghosting）

> 去除鬼影的Hack：运动向量过大不信、颜色差异过大也不信

## 13.6 补充：AA在渲染管线的位置与各技术的本质差异

### 13.6.1 AA在渲染管线的位置

AA排在后处理链的最开始，几乎所有实质渲染完成后才运行：

```text
① Shadow Map 生成
② GBuffer 填充（PBR 材质）
③ 光照（直接光 + IBL/Lightmap）
④ 天空 Pass
⑤ 云 Pass
⑥ AO
⑦ 雾效
⑧ 【AA（FXAA/TAA）】← 在这里，输入是已合成的完整场景图
⑨ Bloom → Tone Mapping → Color Grading
```

FXAA/TAA 拿到的是"一张包含所有效果的2D图像"，在上面做图像处理，不再接触任何 GBuffer 或光照数据。MSAA 是例外——它发生在第②③步之间（光栅化阶段）。

### 13.6.2 MSAA vs FXAA 的本质区别

常见误解：两者都是"对2D图像检测边缘再混合周围像素"。

**FXAA 确实是这样**，但 **MSAA 完全不是**。

**MSAA：发生在光栅化阶段（PBR 之前）**

以一把斜举的剑为例，剑刃边缘穿过某个像素：

```text
该像素内部放4个子采样点：
  ┌──────────────┐
  │  ×  ×        │← 子采样点1,2：在剑三角形内（覆盖=1）
  │              │
  │  ×  ×        │← 子采样点3,4：在背景里（覆盖=0）
  └──────────────┘
  覆盖率 = 2/4 = 50%

PBR Shader 只运行1次 → 算出剑的颜色

最终像素颜色 = 剑的颜色 × 50% + 背景颜色 × 50%
→ 自然过渡，锯齿消失
```

MSAA 从来没有一张"已渲染的2D图像"，它在像素颜色算出来之前就处理好了覆盖率。

**FXAA：发生在后处理阶段（所有渲染完成后）**

```text
已渲染的2D图像（每个像素已有最终颜色）：
  ...██████░░░░...
  ...██████░░░░...  ← 检测到亮度突变
  ...██████░░░░...

FXAA：发现相邻像素亮度差 > 阈值 → 判断是"边缘" → 混合相邻像素颜色
```

### 13.6.3 关键区别对比表

|                            | MSAA                                             | FXAA                                       |
| -------------------------- | ------------------------------------------------ | ------------------------------------------ |
| 发生时机                   | **光栅化阶段**（PBR 计算之前）             | **后处理阶段**（所有渲染完成后）     |
| 输入                       | 三角形几何数据                                   | 最终2D渲染图像                             |
| 怎么判断边缘               | **几何精确**：三角形边界穿过了哪些子采样点 | **亮度近似**：相邻像素亮度差超过阈值 |
| PBR Shader 跑几次          | 每像素1次（不管几个子采样点）                    | 已经跑完，不再跑                           |
| 能区分几何边缘 vs 纹理细节 | ✅ 能（只处理三角形边界）                        | ❌ 不能（纹理花纹也会被模糊）              |

**FXAA 的核心缺陷**：只看亮度差，无法区分下面两种情况：

```text
情况A：几何边缘（应该AA）    剑（亮）│天空（暗） → 模糊 ✅
情况B：纹理细节（不应该AA）  木纹亮条│木纹暗条 → 也被模糊 ❌
```

FXAA 会把砖墙纹理、木纹图案细节也当锯齿模糊掉，整张画面偏软偏糊。MSAA 只对三角形边界起作用，纹理内部不受影响，没有这个问题。

### 13.6.4 四种AA的代价对比

|      | 原理                  | PBR计算次数   | 效果             | 主要缺陷                         |
| ---- | --------------------- | ------------- | ---------------- | -------------------------------- |
| SSAA | 渲染4倍像素再缩小     | 4倍           | 最好             | 代价极高，实时不可用             |
| MSAA | 光栅化多子采样点      | 1倍           | 几何边缘好       | 高光闪烁无法解决，Nanite场景失效 |
| FXAA | 后处理亮度检测+模糊   | 1倍（后处理） | 快速可接受       | 画面偏糊，分不清纹理和边缘       |
| TAA  | 亚像素抖动+历史帧累积 | 1倍           | 最全面（含高光） | 运动残影（Ghosting）             |

### 13.6.5 AA与前面各章节的关系

**与PBR/IBL的关系（最密切）**

PBR 高频镜面高光（specular）在金属/光滑表面上随相机移动快速变化 → 每帧亮度剧变 → 时间维度的"高光闪烁"：

```text
帧N：   金属像素 → 高光命中 → 很亮
帧N+1：相机微移 → 高光没命中 → 全暗
帧N+2：又命中 → 很亮 → 闪烁！
```

- MSAA 无法解决（只处理几何边缘，单像素内部的高光变化管不了）
- TAA 能解决（时间混合把多帧高光平均，消除闪烁）
- 这是现代游戏默认用 TAA 而非 MSAA 的主要原因

**与Shadow Map的关系（互补）**

阴影边缘锯齿有两套处理路径，分工不同：

```text
PCF/VSSM（阴影章节）：在 Shadow Map 采样时做滤波 → 软化阴影边缘本身
FXAA/TAA  （AA章节）：在最终图像上统一平滑所有锯齿，包括阴影边缘
```

两者互补——PCF/VSSM 让阴影边缘物理上更柔和，AA 再处理残余的图像锯齿。

**与天空/云的关系（基本无关）**

- 天空：大气散射产生平滑渐变，几乎无锯齿，AA 影响微小
- 云：体积 Ray March 的结果本身是软边缘，无明显锯齿
- TAA 小细节：天空在无限远处，相机平移时没有视差，Motion Vector 为零。若处理不当会有轻微 ghosting；现代引擎对天空单独计算旋转 Motion Vector 规避此问题

# 第十四章：后处理 — "美颜相机"

> 后处理对最终画面的贡献极大——关掉后处理，再好的渲染也"就那样"。

## 14.1 Bloom（泛光/光晕）

**效果**：强光源周围产生光晕（如霓虹灯、阳光）

**实现**：

1. 提取高亮区域（亮度阈值）
2. 高斯模糊（分离加速：先竖向卷→再横向卷）
3. 金字塔多级下采样 + 逐级上采样混合 → 用低精度计算大范围光晕
4. 叠加回原图

## 14.2 Tone Mapping（色调映射）

**问题**：HDR渲染数据（0~~几十或几万）需要映射到SDR显示器（0~~1）

**Filmic Curve**（Naughty Dog提出）：

- 用多项式拟合S形曲线
- 实现电影般的画质

**ACES**（美国电影学院提出）：

- 更权威的颜色管道
- 支持HDR/SDR不同显示设备
- 暗部清晰+色彩饱满+亮部不过曝
- 目前越来越多引擎采用

> 物理校正 vs 艺术创作：Tone Mapping解决"物理正确"，Color Grading实现"风格表达"

## 14.3 Color Grading（颜色分级/调色）

**本质**：LUT（Lookup Table）= RGB颜色空间的3D映射表

- 16×16×16或32×32×32的3D纹理（精度足够）
- 可展开为2D纹理存储
- **艺术家工作流**：Photoshop中调色 → 插件导出LUT → 引擎读取 → 实时生效
- **性价比最高**的渲染技术：实现简单，效果有质的飞跃

# 第十五章：渲染管线（Render Pipeline）— 所有算法的"指挥系统"

## 15.1 为什么需要管线

游戏渲染涉及几十到上百种算法，需要一个框架来规定**谁先做、谁后做**，保证有序运行。

## 15.2 Forward Rendering（前向渲染）

**流程**：Shadow Map → 逐物体逐光源绘制 → 后处理

**透明物体处理**：

- 不透明物体先绘制
- 透明物体由远及近排序后绘制
- 排序难题：三根交错透明棍子的"莫比乌斯环悖论"（实际用中心点排序近似解决）

**局限**：光源多时性能崩溃（O(物体数 × 光源数)）

## 15.3 Deferred Rendering（延迟渲染）

**核心思想**：几何与光照计算分离

1. **第一遍**：将所有材质属性（Albedo, Normal, Roughness, Metalness, Depth）写入**G-Buffer**
2. **第二遍**：基于G-Buffer在屏幕空间进行光照计算

**优势**：

- 复杂度 ~ O(屏幕像素 × 可见光源)
- 支持大量动态光源
- 便于调试

**代价**：G-Buffer占用大量显存带宽

## 15.4 Tile-Based / Cluster-Based Rendering

### Tile-Based（移动端起源）

- 将屏幕分块（Tile）
- 利用片上高速DRAM减少Frame Buffer读写
- 每个Tile维护可见光源列表（Light List）
- 利用Zmin/Zmax做光源剔除

### Forward+（Tile-Based Forward）

- 对移动端特别友好

### Cluster-Based

- 在Z轴上也切分（四棱锥体柱）
- 更高效地剔除光源（支持上千个光源）
- "事件锥"思想：世界无限大，但任一时刻只感知一个锥体

## 15.5 Visibility Buffer（前沿）

**核心创新**：G-Buffer存材质属性 → Visibility Buffer存几何属性

**存储内容**：Primitive ID + Triangle ID + 重心坐标 → 反向查询材质

**优势**：

- 适应Nanite等超高几何密度场景
- 减少过度绘制（Overdraw）
- 支持更复杂的材质类型

## 15.6 工程挑战：Render Graph / Frame Graph

**三大挑战**：

1. **模块化**：不同游戏需要不同的渲染算法组合（像搭乐高积木）
2. **资源管理**：大量Buffer/Texure需要精确的生命周期管理（创建、使用、释放、重用）
3. **现代API复杂性**：DX12/Vulkan暴露裸硬件，内存管理、同步（Memory Barrier）、死锁等问题

**解决方案：Render Graph**

- 用有向无环图（DAG）表达渲染流程
- 节点 = 渲染Pass，边 = 资源依赖
- 自动优化资源别名重用（Aliasing）
- 自动插入内存屏障

**行业应用**：

- Unity SRP（URP / HDRP）
- 尽管还不够成熟（接口定义、TA可用性），但代表了未来方向

#### 先回答三个具体疑问

##### 摄像头移动时，各数据结构怎么处理？

不同的数据结构对"摄像头移动"的敏感度完全不同：

| 数据结构                              | 摄像头移动时            | 原因                                                    |
| ------------------------------------- | ----------------------- | ------------------------------------------------------- |
| **G-Buffer**                    | 每帧完全重建            | 新的几何体进入视野，必须重画                            |
| **CSM（级联阴影）**             | 每帧重建                | CSM的分层边界是相对摄像头距离划定的，摄像头动了边界就变 |
| **Virtual Shadow Map**          | 按需更新页面            | 哪些"页"在视野内 → 只更新那些页，其余缓存              |
| **Froxel 3D Texture（体积雾）** | 每帧重建                | Froxel是视锥空间，视锥随相机移动                        |
| **SSAO/屏幕空间AO**             | 每帧重建                | 屏幕空间算法，深度缓冲变了就重算                        |
| **TAA历史帧**                   | Motion Vector对齐后复用 | 用运动向量补偿位移，继续累积                            |
| **Lightmap**                    | ✅ 不动                 | 烘焙在世界空间，和相机位置无关                          |
| **IBL CubeMap**                 | ✅ 不动                 | 在固定位置捕获，相机移动不影响它                        |
| **Light Probe SH**              | ✅ 不动（插值）         | 探针固定在世界空间，角色靠近哪个就插值哪个              |
| **大气散射 LUT**                | ✅ 不动                 | 只依赖太阳方向角，和相机位置无关                        |

**结论：** 相机移动主要影响"屏幕空间"和"视锥相对"的数据结构；预计算/世界空间的数据不受影响。

##### 动态光源是什么，环境光真的不动吗？

你的直觉大体对，但需要更精确地划分：

**动态主光（如太阳/手电筒/火把）：**

* 每帧重新生成 Shadow Map
* 太阳移动（日夜循环）→ CSM 4张图每帧重建 + 大气LUT更新 + Sky CubeMap 需要周期性更新（贵，通常每隔几帧或天气变化时才更新）
* 点光源（火把）→ 每帧生成 Cube Shadow Map（6个方向），插入 Cluster 光源列表

**环境光（IBL）到底动不动？**

```
静态场景（无日夜循环）：
  IBL CubeMap 离线捕获 → 运行时完全不变→ 是静态的 ✅

动态场景（有日夜/天气变化）：
  Sky系统输出颜色随时间变化
  → IBL CubeMap 需要周期更新（每N帧 or 天色变化时）
  → Lightmap 失效 → 改用动态 IBL + Light Probe

动态物体的环境光：
  Light Probe SH 存在固定位置 → 物体靠近哪几个探针，插值它们的SH系数
  → SH本身是静态数据，但"用哪几个探针"随物体位置动态插值
```

 **所以"环境光"不是永远静止的，而是"更新频率低很多"** 。Lightmap 完全静止，IBL 偶尔更新，Light Probe 通常也偶尔在后台更新。

---

##### 动态物体（会动的角色、开门、爆炸碎片）

动态物体每帧做这些事：

```
CPU：更新世界变换矩阵（位置/旋转/缩放）↓
GPU Shadow Pass：用新矩阵重新绘制到 Shadow Map → 产生正确实时阴影
         ↓
GPU Geometry Pass：骨骼动画（Skinning）→骨骼矩阵变形网格 → 写入 G-Buffer
         ↓
Lighting Pass：直接光 → PBR + 查Shadow Map（新位置的阴影）✅
  间接光 → 查 Light Probe SH（不能用 Lightmap）⚠️
  反射→ 查最近的 Reflection Probe CubeMap ✅
```

动态物体的 **关键代价** ：不能用 Lightmap（Lightmap是针对静态物体烘焙的）。走进山洞的角色，洞内光照靠 Light Probe 插值，效果比Lightmap粗糙但能实时更新。

#### 完整一帧：以延迟渲染 + Cluster 为基础串联所有技术

用具体数字描述这一帧的状态：

-玩家角色（动态，带动画）向前走了0.3米

* 1个动态太阳（正在落山，方向每秒偏移0.1°）
* 1个动态火把（紧跟玩家，点光源，半径5米）
* 村庄建筑（静态，有Lightmap）
* 天空+ 体积云+ 晨雾

---

##### STEP 0— CPU帧开始（游戏逻辑 → 场景准备）

```
① 游戏逻辑：玩家移动 → 更新角色世界矩阵 M_player
② 骨骼动画系统：计算这一帧所有骨骼矩阵（每个关节一个4×4矩阵）
③ 可见性裁剪（BVH）：
   相机位置/方向变了→ 重新对所有物体包围盒做视锥测试
   保留可见物体：村庄建筑12栋 +玩家 + NPC × 5+ 地形 LOD块× 200
   →淘汰背后的山、遮挡的建筑内部（1500个物体被裁剪掉）
④ 按材质排序，打包Drawcall 批次
⑤ CPU → GPU：上传可见物体列表 + 变换矩阵 + 帧参数
```

---

##### STEP 1 — Shadow Pass（阴影数据生成）

**主光CSM：**

```
太阳又偏了0.1° → 太阳视角变了→ 4张CSM必须完全重建

CSM0（0~10m）：从太阳视角渲染 玩家+周围建筑 → 2048×2048深度图
CSM1（10~50m）：渲染更大范围 → 2048×2048深度图
CSM2（50~200m）：村庄全景 → 2048×2048深度图
CSM3（200m~2km）：山脉等远景 → 2048×2048深度图

注意：玩家（动态）也被画进CSM →玩家在地面的影子是实时的 ✅
注意：建筑（静态）每次都重画 → 有Virtual Shadow Map时可以缓存静态部分
```

**火把 Cube Shadow Map：**

```
火把是点光源，需要向6个方向各渲染一次
→ 半径5米范围内的几何体 → 6张512×512 深度图
→ 每帧重建（火把跟着玩家动）
```

---

##### STEP 2 — Geometry Pass（填充 G-Buffer）

对所有可见物体逐一绘制，不做任何光照计算，只写材质属性：

**玩家角色：**

```
顶点着色器：
  for each vertex:
    world_pos = M_player × blend(bone_matrices) × local_pos
    //骨骼蒙皮变形：每个顶点受1~4根骨骼影响，加权混合
    gl_Position = projection × view × world_pos

像素着色器（写入G-Buffer）：
  albedo   = sample(armor_texture)// 钢铁灰色
  normal   = sample(normal_map)      // 凹凸细节
  roughness = 0.3                     // 光滑金属
  metallic  = 0.9
  depth    = z_value
```

**村庄石墙（静态）：**

```
顶点着色器：世界矩阵是固定的，不用每帧更新骨骼
像素着色器：
  albedo = sample(stone_texture)     // 石头纹理
  roughness = 0.85
  metallic  = 0.0
  // 还要存lightmap_uv，后面Lighting Pass用
```

**地形（LOD选择后）：**

```
顶点着色器：
  从Heightfield读取高度 → 生成顶点位置（不存顶点，程序化生成）
像素着色器：
  混合材质：查 Splat Map → 70%草地 + 30%泥土 → 混合后的albedo/roughness
  → 写入G-Buffer
```

**G-Buffer 状态（这帧完成后）：**

```
每个屏幕像素现在有：
  [albedo: RGB] [normal: XYZ] [roughness: F] [metallic: F] [depth: F]

玩家像素：钢铁色，光滑法线，roughness=0.3，metallic=0.9
石墙像素：石头色，粗糙法线，roughness=0.85，metallic=0.0
天空区域：depth=1.0，无几何体（还没画）
```

##### STEP 3 — Cluster预处理

```
把视锥切成 32×18×64 = 36864 个 Cluster 格子
对每个格子：哪些光源的影响球和它相交？
  Cluster(5, 3, 12) 靠近玩家：
    → 太阳（方向光，影响所有Cluster）
    → 火把（点光源，5米半径，和这个格子相交）
    → 远处另一个火把（不相交，不加入）
  Cluster(20, 10, 60) 远处山脚：
    → 太阳（方向光）
    → 无点光源

输出：每个 Cluster 的光源列表（存GPU显存，Lighting Pass 查询）
```

##### STEP 4 — Lighting Pass（核心光照计算）

读G-Buffer，对每个屏幕像素计算最终颜色。以玩家盔甲上的一个像素为例：

```
读G-Buffer：albedo=钢铁灰, normal=N, roughness=0.3, metallic=0.9, depth=d

// 计算该像素所在的Cluster
cluster_id = world_to_cluster(reconstruct_world_pos(depth))
light_list = cluster_light_lists[cluster_id]  // 太阳 + 火把

// ① 太阳的直接光贡献（PBR + Shadow）
sun_dir = normalize(sun_position - world_pos)
NdotL = max(0, dot(N, sun_dir))

// 查 CSM（哪层？depth决定）
cascade = select_cascade(depth)            // depth=2m → 用CSM0
shadow = sample_CSM(CSM[cascade], world_pos) // PCF软阴影采样
// shadow = 0.85（玩家右肩在建筑阴影半影区）

// PBR Cook-Torrance
D = GGX(roughness, N, H)
G = Smith(roughness, NdotL, NdotV)  
F = Schlick(metallic, VdotH)        // metallic=0.9 → 强菲涅耳
brdf_sun = D*G*F / (4*NdotV*NdotL)
L_sun = sun_color × NdotL × shadow × brdf_sun
// sun_color = 橙红色（大气散射，太阳低角度）

// ② 火把的直接光贡献
torch_dir = normalize(torch_pos - world_pos)
torch_dist = length(torch_pos - world_pos)   // 1.5米
NdotL_torch = max(0, dot(N, torch_dir))
attenuation = 1 / (torch_dist^2)// 距离衰减

shadow_torch = sample_CubeShadowMap(torch_shadow, world_pos) // 查点光阴影
brdf_torch = PBR(...)// 同上
L_torch = torch_color × NdotL_torch × attenuation × shadow_torch × brdf_torch

// ③ 间接光（环境光）— 从Light Probe读取
probe_a = nearest_probes[0]  // 村口探针
probe_b = nearest_probes[1]  // 广场探针
weight_a, weight_b = trilinear_interpolate(world_pos)

sh_combined = weight_a * probe_a.sh_coeffs + weight_b * probe_b.sh_coeffs
L_indirect_diffuse = eval_SH(sh_combined, N)// 从SH评估漫反射环境光

// ④ 环境镜面反射（IBL）
reflect_dir = reflect(-view_dir, N)
mip_level = roughness * MAX_MIP             // roughness=0.3 → 中等模糊
L_specular = sample_CubeMap(reflection_probe, reflect_dir, mip_level)
F_env = Schlick(metallic, NdotV)
L_indirect_specular = L_specular × F_env

// ⑤ 叠加（静态建筑用Lightmap替代L_indirect_diffuse）
//玩家是动态物体，用Light Probe而非Lightmap
L_total = L_sun + L_torch + L_indirect_diffuse + L_indirect_specular
```

**石墙像素（静态，有Lightmap）：**

```
// 静态物体：间接光直接从Lightmap读
lightmap_uv = decode_lightmap_uv(G_buffer)
L_indirect = sample_Lightmap(lightmap, lightmap_uv)  // 预烘焙的GI，更高质量

L_total = L_sun × shadow + L_indirect + L_specular(CubeMap)
```

view_dir = reconstruct_view_direction(pixel_uv)
// 太阳方向 + 查大气LUT →傍晚橙红色天空

##### STEP 6 — 云Pass

```
低分辨率（960×540）Ray March 云体积
每个像素：沿视线穿过云层高度带→ 累积密度和散射光
结果：低分辨率颜色+透明度图→ 上采样 → alpha blend到场景上
```

---

##### STEP 7 — AO Pass（SSAO）

```
读 G-Buffer Depth + Normal
对每个像素：在法线半球范围内随机采样16个深度值
计算：有多少采样点比当前深度更深（被遮挡）
输出：AO因子（0~1），0表示完全遮蔽

玩家腋窝处→ AO=0.4（被铠甲肩甲遮蔽）→ 压暗间接光
石墙墙角  → AO=0.3（两面墙夹角）→ 看起来更有立体感
```

---

##### STEP 8 — 体积雾 Pass

```
Inject Pass：填充 Froxel 160×90×64：
  每个格子：用高度公式算密度
  查 CSM Shadow Map：这格空气被太阳照到吗？
  → 形成光柱（太阳光透过村庄屋顶缝隙射下）

Accumulate Pass：前到后积分 → 3D Texture（已积分颜色+透射率）

Composite：每像素 → 用depth查3D Texture → lerp到场景颜色
```

---

##### STEP 9 — TAA

```
取上一帧的颜色缓冲
用 Motion Vector 对齐（玩家移动了0.3米 → 玩家像素的Motion Vector）
加权混合：current ×0.1 + history × 0.9
→ 高光平滑，锯齿消失
```

---

##### STEP 10 — 后处理链

```
Bloom：提取亮度>1.0的像素（太阳边缘、火把核心）→ 高斯模糊 → 叠回
Tone Mapping（ACES）：HDR(0~10.0) → SDR(0~1.0)
Color Grading：傍晚LUT → 整体偏暖橙色
V-Sync → 显示器输出
```

---

#### 三个疑问的最终答案

**摄像头移动：** G-Buffer、CSM、Cluster、Froxel 每帧完全重建；Lightmap、IBL CubeMap、Light Probe SH 不受影响（它们活在世界空间）。

**动态光源：** 主光每帧重建 Shadow Map；动态点光源每帧生成自己的 Shadow Map，通过 Cluster 结构高效参与光照；"环境光"（IBL/Lightmap）更新频率低，不等于永远静止——日夜循环时IBL 也需要周期更新，Lightmap 则真的静止。

**动态物体：** 每帧更新变换+动画→ 参与 Shadow Pass 投射实时阴影 → G-Buffer 按新位置重画 → 直接光靠 PBR + Shadow Map，间接光靠 Light Probe SH（不能用Lightmap）。

# 第十六章：前沿与未来 — 渲染的"革命时代"

## 16.1 硬件变革

- DX12 / Vulkan：开放底层计算能力
- GPU算力远超CPU（10倍+）
- 大量旧方法正在被颠覆

## 16.2 实时光线追踪（RTX）

- 硬件加速的BVH树 + 射线查询
- 当前主要用于反射
- 潜力：彻底改变整个光照体系（Real-time GI）

## 16.3 实时全局光照（Real-time GI）

**多种方案竞争**：

- Screen-space GI
- SDF GI
- Voxel GI（VXGI）
- RSM（Reflective Shadow Maps）
- RTXGI
- **Lumen（虚幻5）**：三四种算法组合的工程方案

> 未来5~10年，GI问题可能被彻底解决。商业引擎必须攻克Realtime GI。

## 16.4 复杂材质

- **SSS（次表面散射）**：皮肤、玉石等半透明材质
- **毛发渲染**：大量细节和复杂光影

## 16.5 新阴影方案

- **Virtual Shadow Map**：类似Virtual Texture的按需分配思想

## 16.6 Shader管理

- **Uber Shader**：一个Shader通过预定义宏覆盖所有材质变化
- **Shader变种（Variants）**&#x7206;炸：165个模板 → 7万+个Shader
- **跨平台编译**：SPIRV-Cross工具链（HLSL ↔ GLSL ↔ Metal）
