# Agent 协作：谁来做、怎样保存、如何接续

本页说明用户和助手怎样一起完成工程任务。这里的 Agent 指执行任务的助手；子 Agent 指受主任务委派、负责其中一部分工作的助手。

**操作政策版本：2026-10-04.1。** 2026-10-05 只做文档易读性维护，不改变已有授权。
本页记录用户已确认的分工和权限边界。它不会生成 Git 凭据、分支权限或平台许可；用户最新明确指令优先。

工程现在做到哪里，查 [status.md](status.md#resume)；某项技术有哪些约定、怎样使用，查对应专题页；哪些文件可以发布，查 [git-and-publishing.md](guides/git-and-publishing.md#daily-git)。

## 先按遇到的问题找答案

| 常见问题 | 简短答案 | 继续看哪里 |
|---|---|---|
| 我在学习引擎，用户和助手各做什么？ | 用户主要学习、运行、调试、验收和讨论；助手主要编码、维护文档、核查证据。 | [分工和执行节奏](#roles) |
| V1 又出现一个 Bug，要重新批准整轮开发吗？ | 已授权 V1 范围内的修复继续有效；先定位问题，再按变更验证。 | [当前操作政策](#current-policy) |
| 想加新专题，可以直接开始写代码吗？ | 先把方案讲清楚。首次具体实施范围仍要按既有要求展示弹窗，取得明确同意。 | [当前操作政策](#current-policy) |
| 换聊天以后，怎样接着做？ | 读状态和任务记录，再检查实际文件、进程及代理状态。 | [保存、打断与恢复](#recovery) |
| 助手说“验证通过”，我该看什么？ | 看真实版本、命令、结果和覆盖范围；人工体验、自动验证、学习掌握分别记录。 | [任务记录与验证](#task-template) |
| Skills、MCP、CI 等现在启用了吗？ | 先看各项实际状态。写在候选清单里，不代表已经安装或启用。 | [后续扩展](#extensions) |

## 两个小例子

**例一：V1 的 UI 鼠标行为异常。** 用户提供实际输入、异常和场景。助手可以在已有 V1 授权范围内定位、修复，并用已有依赖做相关验证。记录要写清真实运行的版本和结果。自动验证、用户复试、源码学习掌握是三种不同结果，分别保存。

**例二：准备开始一个新专题。** 助手先完成必要设计，解释范围、收益、取舍和成本，再把具体实施范围交给用户确认。用户回答某个选型问题，或没有回答提前出现的开工弹窗，都不等于批准实施。

<a id="current-policy"></a>
## 当前操作政策：开始动作前检查什么

开始执行前，分别检查三件事：

1. **项目政策**：这类动作现在由谁执行，有哪些边界。
2. **本次授权**：用户是否已明确批准这项任务和范围。
3. **实际能力**：当前工具、环境和账户是否真的能完成它。

清晰、同范围的授权持续有效，换聊天不重新询问。若缺少权限或证据，说明具体缺口，同时继续不依赖该缺口的工作。

| 操作 | 谁执行、当前授权到哪里 | 执行时要满足什么 |
|---|---|---|
| 只读检查、讲解、源码或资料核对 | 助手按本次任务执行。 | 优先读本次需要的文件。核对事实不等于批准方案。 |
| 工程文档维护 | 用户已要求助手持续维护。43 份文档重构另有明确实施指令。 | 原有实质信息必须有去向，受影响文档同步维护。Plan 或只读状态下不写文件。 |
| V1 同范围实现、反馈修复 | 助手主实施。2026-10-03 的完整 V1 正式授权继续有效。 | 先定位真实问题，再按变更执行已有隔离验证；不能借此扩展专题。 |
| 新专题，或重大范围、架构变化 | 助手先准备可审阅方案。首次具体代码实施范围按用户既有要求，通过弹窗展示并取得明确同意后开工。 | 选型回答、默认选项、沉默都不构成开工同意。V1 和本次已明确授权的同范围工作不重复确认。 |
| 普通实现细节 | 助手在已授权范围内决定。 | 记录为“助手按授权定案”，不能写成用户逐项选定。 |
| 软件下载、系统安装、VS 工程创建、NuGet 还原或改包、驱动或环境升级 | 目前由用户在 VS 等既有工具中执行。 | 没有新委托，助手不代操作。`global.json` 的历史专项授权不扩展为所有配置授权。 |
| 构建和运行验证 | 在具体已授权任务内，助手使用已有依赖执行。 | 避免自动还原。记录 `bin/obj` 产物（构建输出和中间文件）、版本、命令和实际结果；本次纯文档维护不运行引擎。 |
| Git 暂存、提交、推送 | 当前由用户使用 Git Bash 或 Git GUI；助手准备并核对。 | 每批展示实际范围、验证、提交说明、提交身份、仓库和分支、是否推送，取得明确确认。 |
| 创建 PR（请求审阅并合并改动）、合并、发布 | 尚无自动执行授权。 | 后续分别明确执行者和授权粒度；不能从提交权限推导这些权限。 |
| 独立克隆、CI、第二设备验证（D5） | 用户已整体暂缓；目前未验证。 | 未明确恢复，不安排实操。只恢复其中一项，不自动恢复其余项目。 |
| 资料和发布范围 | 资料原文、图片、附件不改；26 处非发布引用按既有决定不处理。 | 私有截图和 Piccolo 保持既有保护。公开范围另行核对。 |

判断反馈是否属于 V1，查 [v1-baseline.md](plans/v1-baseline.md#scope)。准备验证时，查 [v1-run-and-review.md](guides/v1-run-and-review.md#按任务选择验证) 的任务表，再按同页前提和隔离命令执行。

### 两种确认不要混用

**新代码范围的开工确认**按上表执行。Git 曾因确认框不可见而改用聊天确认，这个先例不会自动成为新代码范围的开工确认方式。

**现行 Git 提交确认**优先使用可见交互框。用户报告框不可见时，可以接受针对同一批范围的明确聊天确认。实质范围改变后，需要重新确认。

工具自动审批、默认选项、超时都不是用户同意。具体 Git 操作和精确发布白名单，直接查 [git-and-publishing.md](guides/git-and-publishing.md#daily-git)，不必返回 [README.md](../../README.md) 重读规则。

<a id="roles"></a>
## 分工和执行节奏

| 角色 | 主要负责什么 |
|---|---|
| 用户 | 学习、运行和调试、验收、讨论。 |
| 助手 | 编码、维护文档、核查证据。 |
| 主任务负责人 | 集成并行工作的结果，核对最终差异，完成验证和交付。 |

记录结果时，把用户初步体验、自动验证、源码学习掌握分别写清楚。

### 模型分工要与实际使用一致

当前已确认的模型选择如下，均使用 Ultra，质量优先，不自行降档：

| 工作 | 已确认的模型选择 |
|---|---|
| 主实施、实施子任务 | GPT-6.1 Sol Ultra |
| 关键评审、重大疑点的独立核查 | GPT-6 Astra Ultra |

主对话实际型号由用户界面决定。所选模型实际不可用时，要如实报告；不能冒称已经使用，也不能声称已经通过该模型的评审。

### 设计讲清楚，再确认新范围

节省 token 不能省略必要设计。先连贯完成设计收敛，解释收益和取舍，再确认新范围。明显影响范围、架构、成本或体验的取舍，先说明再讨论。

普通的已授权检查不逐项审批。先前没有答复的提前开工弹窗，不构成授权。

### 并行工作怎样避免互相覆盖

分派任务时明确目标、输入、输出、可写文件和负责人。阅读可以并行；写入不能互相覆盖。共享文件由一人集成。

主任务负责人必须核对最终差异、验证和交付。某个子任务说“完成”，不能直接作为整个任务通过的证据。

<a id="task-template"></a>
## 任务记录与验证

复杂或跨聊天的任务使用 `execution/<任务名>.md`。普通解释和简单修改不强制创建任务文档。模板保留在本页，避免再增一个独立模板文件。

### 最小任务记录：九个字段

| 字段 | 必须记录什么 |
|---|---|
| 目标与范围 | 要观察到的结果；包含和排除哪些事；完成标准。 |
| 授权与政策 | 用户指令和日期；适用政策版本；具体例外。计划与批准分别写。 |
| 基线与保护 | 工作区和源码节点；已有未提交、未跟踪内容；快照与恢复限制。 |
| 当前步骤与所有权 | 实际做到哪里；谁负责哪些文件；代理和进程的状态。 |
| 变更与决定 | 改了什么、为什么；考虑过哪些备选；哪个决定取代了哪个决定。 |
| 验证证据 | 实际源码／构建版本；工作目录；命令；结果；日志位置。 |
| 未完成与限制 | 未测、失败、阻塞；候选假设；待用户处理的事项。 |
| 下一步 | 紧接着可执行的已授权动作；或需要先收敛的新范围。 |
| 收尾与同步 | 实现、技术验证、人工体验、本地提交、远程同步分别说明。 |

### 什么才算本批验证证据

测试结果必须来自真实运行，且能对应本批实际源码和所用构建版本。

| 容易误用的材料 | 为什么不能直接证明本批通过 |
|---|---|
| 旧 DLL | 运行的可能不是本次修改后的代码。 |
| 历史 PASS | 只能说明当时那一批的结果。 |
| 写在记录里但没有执行的命令 | 没有实际运行结果。 |
| 有限测试覆盖 | 不能据此宣称穷尽了所有情况。 |

关键行为要覆盖生产路径，也就是程序实际使用的那条执行路径。旧 UI 测试曾绕过输入后端，因而漏检；细节见 [v1-ui-mouse-fix-2026-10-04.md](reviews/v1-ui-mouse-fix-2026-10-04.md)。

### 后来的结果怎样补记

任务结束后保留当时记录。后续结果使用带日期的补记，或关联后续任务；不能把后来验收改写成早期就已经通过。

原始大日志可以放在本机缓存。工程文档中仍要留下足够重建结论的摘要、命令、版本和限制。

<a id="recovery"></a>
## 保存、打断与恢复

跨聊天接续依靠已保存的文件和证据。按信息类别维护一个主要位置，不整段复制聊天；没有新事实，不追加流水账。

### 哪些时点要保存

确认或改变重要方案、用户纠正、源码关键发现、实质修改或验证、阶段结束、换聊天前，都要及时保存。

长任务开始时，以及关键批次完成后，建立可以恢复的工作区快照。快照要包含未跟踪文件，不能只靠 Git diff。日志和快照不是远程备份。

不得为恢复工作自动执行 `reset`、`clean`，或覆盖工作区。

### 恢复时按这个顺序检查

1. 读任务记录，确认已授权范围和接续点。
2. 检查实际文件、差异和未跟踪内容。
3. 检查相关进程，以及代理列表中的实际状态。
4. 确认这些情况后，继续已授权工作。

用户打断后，旧子任务可能处于 `interrupted`。`send_message` 只投递消息；需要继续执行时，要用 `followup_task` 或重新分派，并核对它是否真的处于 `running`。临时代理 ID 不能作为长期状态来源。

### 换聊天、换设备和结束任务

| 情况 | 怎样接续、有哪些限制 |
|---|---|
| 同一台机器上的新聊天 | 可以读取尚未提交的文档，既有范围授权继续有效。不能仅因换聊天就新克隆或创建工作树。 |
| 按学习阶段另开聊天 | 这是帮助聚焦的建议。历史压缩次数不是强制换聊条件。 |
| 跨设备接续 | 依赖另行同步的内容。不能恢复未落盘的聊天内容、进程内存或丢失的磁盘。 |
| 任务结束 | 说明保存位置、未保存或未验证事项，以及下一步。 |
| Plan、只读或写入受限 | 遵守当前限制，提供可复制的接续摘要；不能声称已经落盘。 |

<a id="document-ownership"></a>
## 信息放在哪里，怎样避免反复阅读

同一类动态信息保留一个主要维护位置。其他文档可以用短摘要帮助理解，再链接到主要来源。

| 信息 | 主要维护位置 | 什么时候读 |
|---|---|---|
| 人类入口 | 根 [README.md](../../README.md) | 按当前任务直接进入对应章节。 |
| 长期行为原则 | 根 [AGENTS.md](../../AGENTS.md) | Agent 进入工程时读一次；专题页不反复要求重读。 |
| 当前操作和模型政策、任务模板、扩展 | 本页 | 即将产生动作时，读取相关政策段。 |
| 全局当前阶段、活动任务、下一步、同步 | [status.md](status.md#resume) | 恢复工作必读；具体任务页不再复制全局历史。 |
| 目标、模块未来路线、V1 范围 | [plan.md](plan.md)、`plans/` 中的八份路线页、[v1-baseline.md](plans/v1-baseline.md) | 设计新范围或核对目标时读。 |
| 当前结构、技术合同、用法、学习 | [architecture.md](architecture.md)、`guides/` 中的专题页、[learning-map.md](learning-map.md) | 主页面给出完整必要说明，并能直接定位源码。 |
| 决策原因和沿革 | [decisions.md](decisions.md) | 回顾选择时，按编号或主题定位。 |
| 任务证据与历史 | `execution/`、`reviews/`、`archive/`、[development-history.md](development-history.md) | 任务接续或自愿深入时读，不默认全部必读。 |

### 短摘要可以有，必读要求不能绕圈

必要概念可以短述，帮助读者理解。动态进度、授权和精确版本仍保持一个主要来源，避免各页复制后互相矛盾。

执行所需的前提不能藏成“可选阅读”。同一会话已读、且没有变化的共同前提，不反复读取。

必读依赖不能成环；返回首页的导航和来源互引可以保留。从 [README.md](../../README.md) 到主页面不超过两次导航，是本工程的阅读验收目标，不是官方强制文件结构。

### 整理历史和调整政策时保留什么

开发经验按专题写清“问题—候选与取舍—失败或发现—修正—验证与限制”。时间索引只串联阶段和证据。

合并文档前，逐项核对原信息去了哪里。旧路径、当时计划作为历史标识保留，不代表当前操作。

政策改变时，在本页维护有效政策，并在 [decisions.md](decisions.md) 补充原因和日期。具体任务保留当时政策版本和授权，不回写旧证据；没有用户新决定，不能自行放宽权限。

## 后续扩展：各项是什么，现在到哪一步

下表是扩展方向及当前状态，不是配置或启用证明。

| 能力 | 用来做什么、当前状态 | 启用时要明确什么 |
|---|---|---|
| 项目 Skills | 把重复、容易漏步的流程写成可复用步骤。尚未建立项目专属 Skill；当前使用环境已有技能。 | 具体流程；何时触发、何时不触发；引用已有知识，避免复制。 |
| 子 Agent 角色配置 | 委派助手完成部分任务。已按任务委派；尚未固化项目角色配置。 | 目标、模型、工具、可写范围、集成负责人；客户端是否支持。 |
| MCP／连接器 | 让助手通过工具访问外部信息或系统。本次任务没有新增连接。 | 外部信息或动作是否必要；工具边界；真实账户权限。 |
| Hooks／检查脚本 | 在指定事件发生时自动检查。本次没有新增自动触发。 | 按明确规则即可机械执行的检查；环境；触发和信任要求；停用方式。 |
| CI／定时任务 | 自动检查或按时间执行任务。CI 属于暂缓的 D5；尚未建立本项目自动任务。 | 触发、成本、runner（运行机器）和依赖；结果与失败接续；分别处理 Git 权限。 |
| Plugins | 打包或组合能力，供跨项目复用。尚无本项目打包分发。 | 只在跨项目复用或组合能力时，确定包、版本和分发范围。 |

### 接入任何新能力，都写清八项

| 项目 | 要说明的内容 |
|---|---|
| 用途 | 解决什么问题。 |
| 来源与版本 | 从哪里取得，使用哪个版本。 |
| 执行环境 | 在哪里运行，依赖什么。 |
| 触发条件 | 什么时候执行。 |
| 输入与输出 | 接收什么，产生什么。 |
| 读写范围与授权 | 访问哪些内容，哪些动作已获批准。 |
| 验收 | 怎样确认它确实工作。 |
| 失败处理与停用 | 失败后怎样接续，怎样停止使用。 |

目前未知的工具，也按这套流程评估。不要提前建立空目录、权限 DSL（描述权限的专门语言）或完整调度平台。

### 先核对根目录，再核对发现和发布范围
