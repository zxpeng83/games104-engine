# 软件架构：占位与待讨论事项

最后更新：2026-10-01。**软件实现架构尚未确定，本文件当前仅是占位与议题清单。**

> 本阶段只搭建开发环境、仓库与目录、协作文档规则及最小验证工程。具体模块、类与接口、数据模型、运行流程和算法实现，在基础阶段完成后的计划中另行讨论并确认。历史草案与课程示意不能直接成为实现约束。

## 1. 当前已经确定的是什么

已确认的技术基线、单仓目录、用户可视化操作与助手验证分工，见 [项目计划](plan.md)、[搭建指引](setup.md) 和 [协作规则](../../AGENTS.md)。

这些是开发基础，不等于已经决定引擎的软件架构。工程目录的位置、所用语言与库，并不直接规定引擎必须采用哪些模块、类、数据结构或调用顺序。

搭建指引中的 `G104.Engine` 与 `G104.Sandbox` 是练习解决方案、项目引用和环境探针的起步容器。它们的名称、依赖及当前包放置方式不构成长期程序集或模块边界；后续架构讨论可以调整。环境验证代码也不能自动成为正式运行时设计。

目前只有 Sandbox 中的临时 OpenGL 环境探针，已验证窗口、循环回调和上下文调用链。它不是引擎实现模块，也没有确定正式模块关系或帧流程；`OpenGlProbeWindow` 的临时类形态不构成架构决策。实际环境与文件状态以 [当前进度](status.md) 为准。

## 2. 留到后续讨论的事项

| 议题 | 后续需要回答的问题；当前均未定案 |
| --- | --- |
| 功能目标与设计范围 | 下一个可运行目标是什么，需要哪些最小能力，怎样验收？ |
| 项目和模块组织 | 是否以及何时拆分程序集，各模块职责、接口与依赖边界是什么？ |
| 场景与数据模型 | 对象、组件、资源如何表示，是否需要 ECS 或其他组织方式？ |
| 更新与调度 | 输入、玩法、动画、物理、渲染怎样协作，时间步和线程如何安排？ |
| 渲染组织 | 采用什么管线、Pass 和资源表示，哪些抽象在当前规模下有必要？ |
| 资源生命周期 | 创建、加载、共享、缓存、释放分别由谁负责？ |
| 数学与互操作 | 坐标系、单位、矩阵布局、乘法顺序和 CPU/GPU 数据约定是什么？ |
| 工具与扩展 | 哪些能力需要自研或接入第三方，什么时候需要编辑器或脚本支持？ |

议题清单只用于避免以后遗漏问题，不要求现在逐项决定，也不是下一阶段必须全部实现的清单。[学习映射](learning-map.md) 提供相关理论入口，不规定本工程的架构答案。

## 3. 后续怎样形成正式架构

基础阶段验收后，由助手结合用户确认的功能目标提出最小必要设计，解释候选方案与取舍；用户确认关键设计后，再安排对应实现。

届时再逐步把本文件扩展为：

- 已确认的模块、接口与数据关系，以及各自的设计依据。
- 为明确标识的候选设计或实际实现绘制的架构图与运行流程图。
- 真实代码入口、资源和数学约定、验证结果与仍待解决的问题。
- 对重要变更的决策记录链接。

新增设计不能仅以“旧图里已经画了”为理由。图示要标明候选、已确认设计或已实现状态；具体代码实现的分工也在相应阶段明确。
