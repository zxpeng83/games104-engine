# 文档阅读指南：目录、各份文档的作用与易混点

这份指南把此前对话里的完整文档梳理保存下来，供你随时查阅。它解释目录怎样分工、每份文档回答什么问题、名称相近的文档有什么区别，以及实际任务中怎样把它们串起来读。

日常仍从根目录的 [README.md](../../README.md) 按任务进入。不需要把所有文档顺序读完，也不需要先读完本指南才能运行、学习或让助手接续。第一次想理解整个文档体系，可以从目录和逐文件说明开始；只对某组文档有疑问，直接跳到对应的易混点即可。

这里的 Agent 指执行工程任务的 AI 助手。“授权”指用户已经同意做哪件事、做到什么范围；“政策”指用户与助手约定的分工和操作要求。本指南帮助你找到这些约定，不新增或改变约定。当前状态、权限、依赖版本和模型分工仍查各自原文，用户最新明确指令优先。

本指南加入于2026-10-09。加入前的43份正式工程 Markdown 全部保留，新增本页后为44份；这是本次整理时的统计口径。下面的逐文件说明覆盖原43份，并单独说明本页的用途。课程资料和本机缓存不计入这个数量。

## 目录怎样分工

本机项目位于 `E:\game_study\games104`，它也是本项目的 Git 根目录。`g104engine` 是引擎工程目录；`资料` 保存原课程笔记和图片，与引擎工程并列。换设备时盘符可以变化，仓库里的相对结构仍可用于导航。

```text
games104/
├─ README.md                         人类阅读入口：按当前任务选主页面
├─ AGENTS.md                         Agent进入工程时的规则入口
├─ g104engine/
│  ├─ g104engine.slnx                 已有解决方案
│  ├─ src/                           可复用的引擎源码
│  ├─ samples/                       窗口、训练场规则、编辑面板与演示组装
│  ├─ assets/                        Shader、场景、配置和已部署素材
│  ├─ docs/
│  │  ├─ documentation-guide.md      本指南：解释文档的作用与阅读关系
│  │  ├─ status.md                   当前状态、接续点与同步情况
│  │  ├─ agent-workflow.md           具体协作分工、政策和执行办法
│  │  ├─ architecture.md             当前系统的整体结构与约定
│  │  ├─ learning-map.md             源码学习单元与课程映射
│  │  ├─ plan.md                     项目总目标与长期方向
│  │  ├─ decisions.md                选择的理由与变化过程
│  │  ├─ development-history.md      从0到1的阶段索引与专题经验
│  │  ├─ guides/                     当前机制、操作方法与技术约束：8份
│  │  ├─ plans/                      V1基线与模块发展路线：9份
│  │  ├─ execution/                  具体任务的实施记录：2份
│  │  ├─ reviews/                    核查、修复、验证及提交记录：10份
│  │  └─ archive/                    旧草案、原文快照和历史补遗：4份
│  ├─ tools/                         随工程保存的工具
│  ├─ third_party/                   第三方文件、许可与来源说明
│  └─ .cache/                        本机原始日志、快照和检查结果
└─ 资料/                             原GAMES104笔记、图片等学习资料
```

目录图只展开理解阅读关系所需的部分，不是所有本机文件的完整清单。私有截图和独立参考仓库不属于这份阅读地图，也不因整理文档而成为默认读取或发布对象。

源码与文档也各有用途。`src/` 提供引擎能力，`samples/` 把这些能力组装成可以操作的训练场，`assets/` 提供程序读取的数据。`docs/` 帮助解释这些能力、目标和开发过程；阅读文档后，要判断程序实际怎样执行，仍需对应源码或运行结果。

`tools/` 适合保存可复用工具，`.cache/` 适合保存本机生成材料。把某个脚本或日志放进 `.cache/`，并不代表它会随 Git 同步；新增文件是否允许发布，还需按现有 Git 指南核对。

原43份中的最后一份位于文档目录之外：[SOURCE.md](../third_party/openal-soft/1.25.2/SOURCE.md)。它说明OpenAL Soft二进制和对应源码的来源、版本、哈希及许可，保留第三方原文件怎样进入仓库的记录。想确认DLL从哪里来、为何保留对应源码时，读这里；想看它在本项目怎样部署或使用，继续查依赖说明和实际代码。

## 易混点逐组解释

### 1. README.md、AGENTS.md和agent-workflow.md

**README.md负责让你找到入口。** 你想运行就进运行页，想学W/Space就进学习单元，想查现在做到哪里就进状态页。它的主要读者是人，也便于浏览GitHub仓库。它可以短述项目，但不承担所有协作规则和执行细节。

**AGENTS.md是AI进入工程时的规则入口。** 它先告诉助手去哪读当前状态，随后规定工作中的原则。例如保护原资料、检查已有未提交改动、保留决定及理由、分开记录实测与用户体验、换聊天后延续已确认的同范围授权，以及文档链接怎样命名。

它也会概述具体操作的要求，例如Git按当前政策办理、新代码范围先准备可审阅方案，再指向agent-workflow.md的详细段落。你不必背下这份文件；如果想知道“助手为什么要这样处理”，可以查看相应规则。

**agent-workflow.md把合作的具体安排展开。** 它面向用户与助手，回答谁负责哪件事、某种操作当前怎么办理、模型怎样分工、复杂任务记录哪些字段、中断后怎样恢复，以及未来Skills、CI等怎样评估和启用。这里的“流程”就是完成事情的具体步骤与分工。

两份文件确实有重叠，因为助手进入工程时需要先知道关键要求，执行具体动作时还需要完整办法。更准确的关系是：**AGENTS.md给出规则和政策入口，agent-workflow.md承接详细分工与流程。** 不能只靠“一个长期、一个当前”来判断所有内容应该放在哪。

例如“保护原资料、不用旧提交覆盖已有改动”适合在AGENTS.md提出原则；“本批怎样保存包含未跟踪文件的快照、恢复前检查哪些状态”由agent-workflow.md展开。Git的执行者和确认办法也是协作细节，因此到workflow查当前安排，再到Git指南查操作。

“长期原则”并不表示永远不能修改。用户作出新的明确决定后，原则或分工可以按新决定更新，并保留变化理由。“当前政策”也不表示经常变；它可以长期稳定，“当前”只是说明准备动作时要按这份正在生效的约定办理。

这三份都属于文字说明。AGENTS.md是项目约定使用的规则文件名，agent-workflow.md是本项目自行组织的协作说明；它们不是操控角色的C#接口，也不会自己执行提交、安装或验证。

假设换聊天后你说“继续修复之前的V1鼠标问题”：助手先从AGENTS.md知道怎样进入工程和保护进度，再从status.md确认实际接续点；需要恢复任务或执行修复时，查workflow对应要求。你只是在理解已修问题时，可以直接进入修复记录，不必先通读全部协作政策。更完整的步骤见后面的任务路线。

### 2. status.md、plan.md和v1-baseline.md

这三份都可能提到V1和后续任务，但问题不同。

**status.md回答“最新记录显示现在做到哪里、紧接着做什么”。** 它应当告诉你哪些已经做、哪些尚未完成或暂缓、有效结果有什么限制、文件是否保存和同步。恢复现实任务先查这里。

**plan.md回答“这个项目要往哪里发展、各模块为什么这样安排”。** 总目标、长期模块和推进方向可以稳定存在，不能因为它列出下一阶段就直接断定今天开始那阶段。

**v1-baseline.md回答“V1批准包含什么、边界和设计约定是什么”。** “基线”在这里指V1已经形成的范围与约定，便于实现、反馈和评审时对照。它不是当前工作区的文件快照，也不是每次验证成绩单。

例如“平台/推箱以后要不要做”，先从总计划和物理路线理解目标；“这是否属于V1既有范围”，查V1基线；“今天是否已经开始做、接下来是什么”，查状态和对应实际任务记录。只读其中一份无法替其他两份作答。

status.md也不是实时监控程序。它保存最近一次维护时核对到的状态；你在文档维护之后又改了文件或提交了Git，真实工作区可能已经变化。页首维护日期、引擎实测日期、某次远端查询时间分别有自己的含义。今天打开一个页面，不会自动让过去的远端查询变成今天的查询。

判断“已经完成”时，还需要区分讨论、选择、批准实施、代码写入、程序验证、人工体验和学习掌握。它们可能在不同日期发生。决定采用一项能力不证明已有代码；有代码不证明运行正确；初步体验通过不证明穷尽了所有分支或你已经能讲解源码。

### 3. plan.md、plans/和guides/

**plan.md管全项目的方向，plans/细化专题，guides/解释当前机制和用法。** 总计划帮助你看模块之间的关系；专题路线帮助你讨论某个模块的目标、分期、自研/集成边界；技术指南帮助你理解当前采用的具体规则和接口。

两类专题页有交集，因为取舍会影响实现。例如角色动画为什么采用in-place、位移由控制器驱动，既是选方案的理由，也影响当前输入和动画规则。路线页保留发展方向与取舍，指南说明实际机制，彼此链接即可。

所以不能仅凭目录说“plans都是没实现的，guides都是已经全部实现的”。V1基线和路线含有已选择、已实施的部分；指南可以保留修正原因和实现限制。每个页面都需要结合具体表述判断。

用角色移动作例子：

1. 想知道当前W输入怎样变成位移、怎样接地和跳跃，读 [physics-and-gameplay.md](guides/physics-and-gameplay.md)，然后对应源码。
2. 想讨论以后加入移动平台、推箱或更深入的物理实验，读 [physics-character-roadmap.md](plans/physics-character-roadmap.md)。你会得到目标、已有基础和仍需收敛的候选。
3. 想判断某项需求是否已经包含在V1批准范围，读 [v1-baseline.md](plans/v1-baseline.md)。
4. 想知道最新实际进展，读 [status.md](status.md)和必要的任务记录。

路线里的学习目标或候选清单不自动批准新专题，也不自动恢复CI、克隆、第二设备等暂缓事项。这里解释如何理解范围，具体是否执行仍按当前政策和本次用户指令。

### 4. architecture.md、learning-map.md和技术guides

**architecture.md解释当前系统整体怎样连接。** 它适合回答Engine与Sandbox各负责什么、一帧先后经过哪些系统、谁能修改哪份数据、逻辑位置与显示位置怎样关联、资源由谁创建和释放。

**learning-map.md帮助你把整体拆成可以学习的单元。** 它给出源码入口、课程知识、固定参考版本、采用或简化的方式、断点和自测。其第一单元已提供启动/W/Space的必要背景，不要求先拼读所有指南才能开始。

**技术guides深入某一个专题。** 比如scene-and-editor.md详细说明设计数据与运行世界、输入、事务和Undo；rendering-and-animation.md说明导入子集、矩阵/蒙皮和颜色域；physics-and-gameplay.md说明查询、控制器、NPC和机关。这里的“约定”或“技术合同”指代码使用时必须满足的具体规则，例如哪些变换合法、哪个系统可以写角色位置、坏资源如何拒绝。

这些页面会提到相同对象，但解释层次不同。architecture给整体关系，learning-map安排怎样学和怎样证明学懂，guides提供专题的完整机制。比如你只想学一次Space，直接按学习单元走；若不理解一次显示更新为什么有零到多次模拟步，再查看相应时间流程；若继续研究UI怎样抢占输入，再深入场景/编辑指南。

阅读可以在问题得到回答时停止。文档互引是为了让你继续追问，不要求一次把系统整体、所有算法和全部历史同时学完。

### 5. development-history.md、decisions.md、execution/、reviews/和archive/

它们都涉及过去，容易误以为是五套重复历史。实际上可以从同一个事件看出各自用途。

**development-history.md先给阶段和事件入口。** 你记得“当时角色靠近球或坡会退出”，但不记得文件名，就从时间索引或专题经验找到相关事件。

**decisions.md保存选择的理由与演变。** 它回答为什么采用某种路线、用户决定了什么、助手按授权决定了什么、后来哪项选择取代了哪项。技术Bug的完整调试过程不必都写进决策索引；只有形成重要设计选择或改变既有约定时，才需要记录相应决定。

**execution/保存任务如何实际推进。** 它适合说明分了哪些批次、谁写哪些文件、当时做到哪里、如何交接，也可以记录这项任务实际运行的版本、命令、结果和限制。比如V1整体从实施到多轮修复，读v1-progress.md能看出连续过程及各批验证依据。

**reviews/保存具体核查及其结果。** 想查球/坡异常的根因、修了哪些入口、先失败后通过的命令、窗口路线和人工复试，直接看对应修复记录。它应当把结论的适用范围说清楚；“review”并不统一代表已经运行程序或穷尽验证。

**archive/保留当时原案和原文。** 想逐字核对旧规则，或知道撤回的架构/M1候选到底写了什么，查归档。archive中的foundation-setup-and-probes.md还包含历史索引和补遗，因此归档也不全是原封不动的代码块快照。

可以把五类理解成：先找事件，再按需要找选择原因、推进过程、核查结果或当时原文。它们之间的链接让你深入，并不意味着每件事都必须额外创建五份文件。

历史里出现的“当前”“下一步”“未提交”“待确认”属于当时阶段。后来的结果用补记或后续文件连接。今天接续先看status.md；不能把早期草案的待办当成今天还没完成，也不能把后来通过改写成原失败根本没发生。

文档整理的记录也有这层区别：document-consistency-review-2026-10-04.md记录那次一致性复查，document-restructure.md记录后续重构、信息去向和该批验收。两次检查的文件数和链接数各属于原批次，不能拿旧数量证明新增本指南后的检查也已通过。

### 6. environment.md、dependencies.md、v1-run-and-review.md和reproduction.md

**运行指南给你现有工程的最短使用路径。** 打开已有方案或启动已有输出，怎样Play/Stop、移动/交互、编辑与保存，出了问题选择哪种检查，都从v1-run-and-review.md进入。

**environment.md处理开发环境与调试配置。** 比如为什么要x64、Debug与Release调试有什么区别、SDK/原生库或VS设置怎样核对。它也保留历史故障供参考，读到旧建工程内容时不能拿Hello World或蓝色探针覆盖现在的训练场。

**dependencies.md说明工程依赖什么、这些文件怎样进入并被使用。** 它集中维护精确版本和部署说明：SDK、NuGet锁文件、Jolt/OpenAL及素材等各自负责什么；不是“读到升级步骤就应立即升级”。实际项目和锁文件同时也是程序可读取的版本来源。

**reproduction.md讨论独立工作区或另一设备怎样复现，并区分同机换聊天。** 复现需要确认已同步哪些内容、缺什么环境、在新位置运行是否得到结果。本机成功不能自动证明新设备成功。

比如工程能打开，想移动角色，就查运行指南；因为平台或调试设置无法启动，查environment；因为某DLL版本或部署位置不清楚，查dependencies；要准备独立目录或换设备，则查reproduction及当前政策。

同一设备、同一工作区换聊天，可以读取本机已经落盘的文件和未提交内容，通常不需要重新克隆、还原、建工程或创建工作树。“换聊天接续”和“换设备复现”是两件事。

D5是本项目把独立克隆、CI和第二设备验证合在一起使用的阶段标识。它们的实际状态由status.md和agent-workflow.md维护；reproduction.md保留未来恢复后的办法，阅读或更新这份文件不会恢复D5。只恢复其中一项，也不能推断其他项同时恢复。

### 7. Git操作政策、Git指南和提交历史

**agent-workflow.md回答谁操作、有什么要求。** 当前执行者、每批确认、助手准备与核对的职责、提交和推送等动作的范围，都从这里查对应政策。

**git-and-publishing.md回答怎样操作、哪些文件可以进入公开范围。** 它给出每批流程和精确发布白名单。白名单就是明确允许发布的文件范围，用于避免把原资料、私有截图、缓存等一并带到公开仓库。

**git-submission-history.md回答某批当时实际发生了什么。** 它保留准备清单、身份/目标、提交和远端核查结果。某批历史曾展示56个路径，不代表下一批也该暂存同样56个路径；旧目录命令也不能成为新批范围。

本机写入文件、暂存、提交、推送分别成立。文件已保存，可能还没有进入暂存区；本地有提交，可能尚未推到GitHub；本地origin/main是缓存引用，不能单独证明当前服务器节点。状态页记录最近核查到的结果，实际新批次还应核对真实工作区。

如果未来你决定改成由AI提交Git，讨论具体执行范围和确认办法时查workflow，并在获准后维护那里；把变化原因和日期记入decisions.md。操作说明需要调整时更新Git指南。具体哪批实际由AI提交、验证和同步了什么，才记入提交历史。只改变执行者不会自动授予PR、合并或发布权限；现行每批确认仍然有效，改变确认粒度也须由用户另行明确决定。

### 8. 原课程资料、实际源码、SOURCE.md和.cache/

**课程资料说明原理与课程内容。** 它为理解引擎提供背景，保留你的原学习记录。课程覆盖某项知识，不表示本工程已经实现相同功能；学完课程也不自动表示已经掌握当前C#调用链。

**实际源码说明当前实现。** `src/` 与 `samples/` 中的代码才定义程序接收输入、调用系统和改变状态的方法。编译后的DLL还需要与本次源码对应，否则运行的可能是旧实现。文档帮助理解代码，但判断行为要结合实际版本和执行路径。

**SOURCE.md说明第三方来源及许可。** OpenAL Soft的来源记录回答“这个DLL和对应源码从哪里来、版本和原文件是什么”。它不证明项目已经自行重编译第三方库，也不意味着操作系统完成了安装或升级。部署说明在dependencies.md；当前播放行为在对应代码和运行结果中。

**.cache/保存本机原始材料。** 例如测试完整输出、隔离运行数据、原始ZIP、工作区快照和临时核查脚本。正式文档应留下足够理解结论的摘要、日期、命令、版本和限制；原始大材料可留缓存。缓存不随Git同步，不是异地备份，换设备也不会自动带过去。

因此“来源核查通过”“部署完成”“实际运行通过”“用户体验符合预期”“我能解释源码”是不同结果。OpenAL文件来源清楚，不等于音频设备已实际播放；自动播放检查通过，不等于左右/远近听感正确；你听到声音正常，也不等于已经能解释source/buffer如何创建和清理。

### 9. 自动验证、VS Debug、人工体验和源码掌握

运行指南里的“按任务选择验证”是一张项目自动检查入口表。“任务”指具体问题或修改范围，例如鼠标输入、设计保存、渲染或声音。选择相关检查来帮助定位问题，并在修复后确认相关正常行为仍然保留；后者也叫“回归检查”。

这些 `--verify`、`--exercise` 参数由项目代码定义。Shell和Windows负责启动程序，.NET运行编译后的程序集；项目识别参数后执行预写的检查或脚本。助手可以选择命令、运行和分析结果，用户也可以手动运行。文字政策文档不负责逐帧控制角色。

检查方式有区别。部分检查直接调用逻辑和物理等接口；`--verify-ui`检验编辑面板/事务但不经过生产窗口输入；`--verify-ui-input`让模拟窗口消息经过生产输入适配，检查代表性控件；`--exercise`在真实训练场的隐藏窗口中脚本驱动移动/跑跳、绘制、Play/Stop和保存等流程。完整参数、前提和边界以 [v1-run-and-review.md](guides/v1-run-and-review.md) 的表为准。

内部直接调用Play或保存成功，不能单独证明鼠标点击真实按钮后全流程都成功。输入检查能证明模拟消息到达代表性控件，也没有把任意界面操作顺序和所有功能都连起来穷尽检查。预设路线能自动移动角色，但只覆盖脚本安排的路线和条件。

**VS Debug帮助你观察代码执行。** 你在入口、输入缓冲、固定步和控制器处设断点，查看谁写了数据、某一分支为何触发。断点可以帮助解释异常与状态；暂停也会改变时间，因此不能直接用断点后的帧耗时判断正常性能。

**人工体验帮助判断实际使用。** 你在可见窗口点击、移动、编辑、保存，观察画面、声音、手感和真实操作顺序。它可以发现脚本没覆盖的组合，但一次体验正常仍是有限范围的结果。

**源码掌握需要你能解释并定位。** 比如能画W/Space数据流、说清持续输入与按键边沿为什么不同、预测零步/多步时的跳跃次数、找到对应方法，再用断点验证。自动PASS或人工游玩通过都不能替你完成这一层学习。

日常学习无需每次跑完所有检查。修改了什么、遇到什么问题，就按已授权范围选择相关检查与必要人工复试。只写了文档或列出了命令，也不能记成引擎已经重跑通过。

<a id="reading-routes"></a>
## 用具体任务把文档串起来

以下顺序解释每次打开文件是为了得到什么。你可以在当前问题已经解决、下一步已经明确时停止，不需要把后面的可选深入全部读完。

### 任务一：从启动、一帧和W/Space学习源码

1. **从README找到学习入口。** 在 [README.md](../../README.md) 选择“从启动、一帧、W/Space开始学源码”。你会直接进入 [learning-map.md](learning-map.md#first-input-lesson) 第一单元，而不是先读完整工程历史。
2. **需要确认学习接续点时看状态。** [status.md](status.md#resume)说明最新保存的阶段和未完成事项。恢复上次学习时先核对那里与实际文件；已经知道本次就是第一单元，就不必从每个专题反复返回状态页。
3. **按学习单元读必要背景与调用链。** 这里会说明持续W输入、Space按下边沿、固定模拟步、显示插值和UI捕获，给出Program、窗口、InputBuffer、Clock、Simulation、控制器到绘制的入口。读完你应知道要跟哪条链、观察哪些状态。
4. **打开源码，按建议逐个断点观察。** 追踪一次移动和跳跃，确认输入在哪缓存、哪一步消费、角色状态由谁写、画面怎样读取。预测零步/多步结果，再和实际观察对照。第一次学习用现有场景即可。
5. **出现具体疑问才深入相关页面。** 整体时序和数据归属查 [architecture.md](architecture.md)；输入/事务查 [scene-and-editor.md](guides/scene-and-editor.md)；接地和碰撞查 [physics-and-gameplay.md](guides/physics-and-gameplay.md)。理论不清楚时，再按学习映射复习课程笔记。

当你能定位并解释一次W/Space链、完成该单元自测并指出剩余疑问，这次学习就有可记录的成果。接下来可跟E交互；不需要先读全部路线和评审，也不把所有自动检查PASS设为学习前提。

### 任务二：换聊天后接续V1鼠标问题

1. **助手先读规则和状态，再核对真实文件。** [AGENTS.md](../../AGENTS.md)说明如何保护已有改动、延续已确认范围；[status.md](status.md#resume)给出最近记录的进展。Git差异和实际文件用于核实记录之后有没有新变化。
2. **先分清是解释旧修复，还是出现了新现象。** 已保存记录里有鼠标修复和用户复试结果，不能因为换聊天就把过去已完成的工作宣布未完成。若你现在说“又点不了”，应记录这次实际版本、操作、场景和异常，判断是不是相同或新的输入组合。
3. **读对应修复记录了解原问题。** [v1-ui-mouse-fix-2026-10-04.md](reviews/v1-ui-mouse-fix-2026-10-04.md)能告诉你原根因、改动、先失败后通过的检查和当时限制。需要整体实施过程时才查 [v1-progress.md](execution/v1-progress.md)。
4. **即将执行动作时查协作办法。** [agent-workflow.md](agent-workflow.md#current-policy)帮助助手核对同范围修复、构建与记录要求；打断恢复还需要检查进程及代理的真实状态，不靠旧聊天里“还在运行”的文字判断。
5. **按这次问题选择检查与复试。** [v1-run-and-review.md](guides/v1-run-and-review.md)给出输入检查、隔离数据和失败处理。相关自动结果与用户可见窗口复试分别保存；旧13项PASS不能直接证明后来修改或新输入组合通过。

如果本次只是想了解旧修复，读完对应记录和必要源码就可以停止；如果确有新异常，继续到定位、同范围修复和相关验证，并保存新的接续点。同机换聊天不需要为此重新克隆或恢复D5。

### 任务三：讨论移动平台、推箱等新能力

1. **先从总计划理解为什么做。** [plan.md](plan.md)给出角色/物理在整个项目里的目标和长期方向。读完应能说清新能力服务什么学习或演示目的，而非只列功能名。
2. **看物理路线里的分期与候选。** [physics-character-roadmap.md](plans/physics-character-roadmap.md)说明平台/推箱等后续方向和自研/后端分工。读完知道哪些基础沿用、哪些规则仍需讨论。
3. **用V1基线核对现有范围。** [v1-baseline.md](plans/v1-baseline.md)帮助判断这是既有反馈修复还是新增专题。平台/推箱的长期目标存在，不代表当前V1已实现这些能力。
4. **看当前机制，避免重复设计。** [physics-and-gameplay.md](guides/physics-and-gameplay.md)与实际代码说明现有角色、查询和场景怎样工作。讨论平台时若涉及层级、运行世界、编辑保存，再查场景指南；不必默认读所有模块路线。
5. **把新范围讲清楚，再按政策决定实施。** 先说明可观察结果、包含/排除项、主要取舍和验证办法；[agent-workflow.md](agent-workflow.md#current-policy)给出新具体代码范围的执行要求。讨论阶段的候选不能写成用户已经批准或代码已经完成。

如果这次仅讨论，范围与未定问题讲清就可以停止，不开始代码。实际获准实施后，目标和范围保存在对应专题路线及本次获准范围记录中，重要选择理由进decisions.md，推进过程与验证再各归其位。新增平台/推箱等能力不要追写成原V1当初已经批准的范围；原边界与后来的新决定分别按各自日期保留。

### 任务四：准备把当前改动保存到Git

1. **先核对这一批真实改动。** 查看当前工作区、暂存区和状态记录，区分本次改动与已有未提交补记。 [status.md](status.md)帮助理解最近保存情况，实际差异决定本批清单。
2. **查当前谁操作与确认要求。** [agent-workflow.md](agent-workflow.md#current-policy)解释助手准备/核对和用户Git写入的现行分工。你已经对某批明确确认过的范围按既有流程继续；历史保存记录不会自动批准扩大范围。
3. **按Git指南准备和核对。** [git-and-publishing.md](guides/git-and-publishing.md#daily-git)给出步骤及发布白名单。读完应能核对实际文件清单、验证、拟提交说明、身份、仓库/分支以及是否推送，避免把整个缓存或资料目录加入。
4. **暂存后核对实际清单，再完成该批操作。** 准备清单和真正暂存的内容可能不同，应核对实际结果；提交和推送是不同步骤，各按当前分工与该批已明确范围执行。
5. **实际发生后再记录结果。** 当前保存/同步摘要进 [status.md](status.md)，该批详细过程与后续核查进 [git-submission-history.md](reviews/git-submission-history.md)。不要把“拟提交”“准备好”提前记成已提交或已同步。

本次目标只是本地提交时，完成并核对本地提交就达到该目标；明确包含推送时，继续核对对应远端结果。无需为了本批保存重新阅读首次建仓历史，也不从这一步推导合并或发布权限。

### 任务五：追溯为什么靠近球或坡面会退出

1. **从事件索引找到专题。** [development-history.md](development-history.md#timeline)帮助定位球/坡面退出那一批；如果已经知道文件名，可以直接进入下一步。
2. **读对应修复记录的现象与根因。** [v1-contact-exit-fix-2026-10-03.md](reviews/v1-contact-exit-fix-2026-10-03.md)说明展示球本身没有Collider，异常实际来自转身/移动后的场景变换提交。位置只是发现问题的路线，不能直接当成“球碰撞算法错了”。
3. **查当前约定和源码理解修复。** [scene-and-editor.md](guides/scene-and-editor.md)及修复记录中的源码入口帮助理解世界变换、字段保持和拒绝非法变换；[architecture.md](architecture.md)补充数据写入者与空间约定。这里的TRS指平移、旋转、缩放三类变换，原异常与这些变换的反复矩阵分解有关。
4. **回到证据区看为什么认定修复有效。** 对应记录保留修前失败、38例检查、真实隐藏窗口路线、旧集成回归和后续人工复试。各材料覆盖不同部分，原240帧没覆盖全部转向路线，不能因它原先PASS就否认用户现象。
5. **只在进一步追问时读其他历史。** 想知道这批怎样与独立评审衔接，查 [v1-progress.md](execution/v1-progress.md)；涉及重要选择时查 [decisions.md](decisions.md)。只有要核对当时原案原话，才需要归档，不必把所有archive都读一遍。

能说清现象、真实根因、修改入口和验证限制，就完成了这次追溯。如果今天再次出现类似异常，先核对当前版本和新复现条件；历史通过不直接证明新一轮通过，也不把旧“待用户复试”当成今天仍未完成。

## 新信息应写在哪里

“主要维护位置”指同一类内容通常在一处更新，其他页面用链接或必要的短摘要引用。这样权限、进度或版本变化时，不需要在多份文档里复制修改同一段话，也减少出现互相冲突的旧说法。

| 新产生的信息 | 通常写在哪里 | 为什么 |
|---|---|---|
| 新增人类阅读入口 | [README.md](../../README.md) | 让读者从当前任务直接找到主页面。 |
| 各文档职责、易混关系和阅读示例变化 | [documentation-guide.md](documentation-guide.md) | 维护这份阅读地图，让读者理解怎样选择。 |
| Agent必须遵守的原则 | [AGENTS.md](../../AGENTS.md) | 进入工程时能找到规则入口。 |
| 用户/助手分工、当前操作或模型政策变化 | [agent-workflow.md](agent-workflow.md)；重要变化理由与日期关联 [decisions.md](decisions.md) | 当前怎么执行与为什么改变分别可查。 |
| 当前阶段、已完成/未完成、下一步、暂停或同步情况 | [status.md](status.md) | 恢复任务时能获得最新保存的接续摘要。 |
| 全项目目标和方向 | [plan.md](plan.md) | 保持整体范围和优先关系清楚。 |
| 模块目标、分期候选或V1范围约定 | 对应 `plans/` 路线；V1范围在 [v1-baseline.md](plans/v1-baseline.md) | 目标和范围不混入实际完成记录。 |
| 当前结构、接口、数据规则、操作和失败保护 | [architecture.md](architecture.md)与对应 `guides/` 专题 | 读者能在机制或操作主页面找到必要说明。 |
| 学习单元、源码/笔记映射、自测 | [learning-map.md](learning-map.md) | 让学习路径与代码直接对应。 |
| 精确依赖和部署说明 | [dependencies.md](guides/dependencies.md)，同时核对项目/锁文件 | 避免在阅读指南里复制一套容易过期的版本表。 |
| 重要选择、理由和取代关系 | [decisions.md](decisions.md) | 保留为什么选择及后来怎样改变。 |
| 复杂任务的推进过程和可恢复步骤 | 对应 `execution/` 任务记录 | 跨聊天能核对范围、文件责任和实际接续点；简单解释不强制新增记录。 |
| 任务中的实际验证 | 对应 `execution/` 任务记录；简单检查可在已有相关正文补记 | 留下本批实际版本、命令、结果与限制，无需每次另建评审文件。 |
| 专项核查、独立评审、Bug修复和人工复试 | 按需要使用对应 `reviews/` 记录，当前摘要关联到 [status.md](status.md) | 集中解释专项问题、修正及证据边界，和整体任务过程相互引用。 |
| 各批Git保存与同步过程 | [git-submission-history.md](reviews/git-submission-history.md) | 本机文件保存、提交和远端同步分别核实。 |
| 开发阶段与专题经验索引 | [development-history.md](development-history.md) | 便于从一件事找到理由、过程和证据。 |
| 需保留的旧草案、原文快照和历史补遗 | `archive/` 中对应记录 | 保留当时信息，同时标明已被替代或属于历史。 |
| 原始大日志、隔离数据、工作区快照 | 本机 `.cache/`；正式文档留必要摘要和位置 | 能核查又不把本机材料误当成Git或跨设备备份。 |

这些位置是按信息性质选择，不要求每次解释都创建执行记录、评审和归档。一个简单事实可以在对应正文更新；复杂或跨聊天任务才需要更完整过程。沿用已有记录时，保留日期、范围和真实结果，不改写早期失败为从未失败。

本指南可以解释“权限去哪里查”“状态怎样理解”，但不复制整套现行政策、模型表、每批Git节点和全部精确依赖。这些动态信息继续在原位置维护；这里的例子帮助理解，动作前以对应原文、真实文件和本次用户指令为准。

## 怎样避免越读越多

先确定当前问题，再选一个主页面。主页面应提供完成该任务需要的背景和前提；只有具体疑问需要更多材料时，才展开相关链接。已经读过且没有变化的共同规则，不从每个专题反复返回重读。

读完一页，可以检查三件事：我现在知道该找哪个文件或源码入口吗；知道读它能得到什么吗；知道这个结论有什么范围和限制吗。如果已经足够完成当前任务，就可以停止深入，开始实际观察、讨论或操作。

来源互引、返回首页和可选历史入口可以保留，它们提供导航，不构成必读循环。尤其本指南是面向读者的完整说明，不把它加入每次Agent任务的强制阅读链，也不把阅读全部44份文档当成继续源码学习的条件。
