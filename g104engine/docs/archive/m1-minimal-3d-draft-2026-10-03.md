## 2. 候选目标与工程组织

- 候选目标：用程序生成的几何和内置 GLSL，验证可见绘制、空间变换、深度、实例共享与 GPU 生命周期。
- 继续使用已有 SDK、依赖和两项目，不新增项目或 NuGet 包；图像/模型导入和第三方资产不是本草案的前置条件。
- Engine 内按运行生命周期、Scene、Math、Assets、Rendering 等职责组织目录/命名空间；这些名称用于说明边界，不先承诺完整通用框架。
- Sandbox 负责启动配置、构造演示场景和演示操作；通用 renderer、GPU 资源和上下文生命周期属于 Engine，Engine 不依赖 Sandbox。
- 默认图形入口逐步替代当前清屏探针，并保留 OpenGL 上下文诊断与最低版本/Core 检查；保留现有 --smoke 模式及其证据限制，不把打印 PASS 误称为全面自动断言。
- 拟新增 --verify 作为 CPU 验证入口；这是尚未批准、尚不存在的新接口，不是当前可运行命令。
- 本草案不引入完整编辑器、任意资源导入、完整层级场景、角色控制器、物理、动画或其他后续模块。它们仍在整体实践承诺中，不能因不在 M1 就被取消。

## 3. 候选检查点

每个检查点拟按“解释原理与参考 → 确认本块设计 → 实现 → 用户在 VS 观察/调试/验收 → 记录反馈”推进；不能连续做完所有块后才集中验收。

### M1.1：三角形与绘制链路

- 程序生成三角形，使用顶点颜色和内置 vertex/fragment shader，先验证顶点输入、shader 编译/链接、绘制和交换缓冲。
- 提供可定位的 shader 编译/链接日志；初始化中途失败时，清理已经创建的部分资源。
- GL 资源由明确所有者释放；删除操作发生在正确线程且有效上下文仍 current 时，早于窗口/上下文销毁，不依赖 C# 终结器执行 GL 调用。
- 视口使用实际 framebuffer 像素尺寸；尺寸为零时跳过绘制。不能只凭清屏窗口正常就宣称高 DPI/尺寸适配验证完成。
- 验收候选：能看到预期颜色；窗口尺寸变化后绘制正确；正常退出与失败路径均无重复释放或遗留所有权。

### M1.2：彩面立方体、深度与环绕相机

- 程序生成彩面立方体，用固定面色辨认朝向；启用深度与透视投影，不借此扩展到光照、纹理或 PBR。
- 立方体按固定 60 Hz 模拟做匀速旋转；显示采用模拟状态插值，说明其延迟代价与重置规则。
- 采用已确认的环绕观察相机。以下操作和参数只是助手候选，审核时可以修改：

| 项目 | 待审核候选 |
| --- | --- |
| 环绕/缩放/复位 | 鼠标右键拖动环绕、滚轮缩放、R 复位 |
| 观察目标 | 验证场景中心 |
| 初始距离 | 8 米 |
| 初始俯仰 / 偏航 | 25° / 45°；仍须明确对应角度定义和符号 |
| 透视参数 | FOV 60°、near 0.1 米、far 100 米 |

- CPU 与 GPU 变换应按已核实的约定执行，不以“行主/列主”一个词代替向量方向、组合顺序、内存布局和上传方式的说明。
- 验收候选：各面与深度遮挡正确；旋转速度不随绘制帧率改变；环绕、缩放和复位可观察，重置时不沿旧历史插值。

### M1.3：共享 Mesh、场景作用域和重载

- 候选场景为地面与三个立方体：立方体共享一份 Mesh，各有自己的 Transform，其中一个持续旋转。
- 本块只需根对象和 Transform/Mesh 关联，验证对象实例与共享资源的区别；复杂父子层级和完整组件框架另行分期。
- 候选操作：Delete 删除约定实例，重复删除不产生额外效果；F5 重建场景。具体对象、操作键与暴露方式均未批准。
- 对象增删在安全阶段提交，不在遍历中直接修改集合；删除实例不释放其他实例仍使用的共享 Mesh。
- 共享场景资源保留到场景卸载。新场景及其资源准备成功后才替换旧场景；失败时清理本次部分资源、保留旧场景并报告错误。
- 拟以日志或窗口标题显示必要实例/资源计数，不为本块提前构建完整调试 UI。
- 验收候选：删除一个箱子后其余正常；反复重载后资源计数稳定；故意制造加载/创建失败后旧场景仍可继续使用；退出时资源仅释放一次。

## 4. 时间、输入与暂停的待审核建议

固定模拟 60 Hz 已确认；以下具体策略尚未确认，不能写成稳定需求：

- 候选每帧最多补算 5 个固定步；超限时丢弃剩余完整积压步长，仅保留不足一步的余量，避免无限追赶。
- 候选在窗口失焦、最小化和同步重载时暂停模拟，恢复时重设计时基准并处理输入与插值历史，避免补算暂停时间。
- 删除、重载、复位等单次输入不能因一帧有多个模拟步而重复执行；一帧没有模拟步时也不能直接丢掉待消费动作。
- 上述策略服务于基础离线演示；不能自动成为未来网络、录制回放或所有动画事件的时间政策。

## 5. 候选验证方案与证据边界

### CPU 验证建议

拟议 --verify 只承担无需真实 GL 上下文的确定性检查，具体接口和用例需在审核后确定：

- 固定时间步、零/多步、插值与候选追赶策略；固定 60 Hz 不等于整套引擎已经保证跨平台确定性。
- 变换约定、数学组合和父子变换公式；数学用例不代表复杂场景层级已经实现。
- 透视/深度相关的数值预期；CPU 结果不能证明真实 GL 深度测试、shader 或上传重载正确。
- 场景/资源所有权和失败清理的 CPU 可验证部分；不能用模拟清理代替实际 GPU 生命周期验证。

### 图形与工程验证建议

- 每个实际检查点按现有配置执行 Debug/Release x64 构建，使用 --no-restore；不安装依赖或自动还原。构建产生的 bin/obj 应按既有规则记录。
- 用户通过 VS 进行图形观察和调试，逐块确认颜色、遮挡、变换、相机和窗口行为，分别核对 Escape 和窗口关闭按钮、尺寸变化及恢复；记录配置、场景、结果与限制。
- 实例删除、重复重载、故意失败后的旧场景保留与部分清理分别验收；不要仅凭代码存在就宣称通过。
- 以资源计数和明确创建/释放证据检查生命周期；不能把驱动显存缓存波动直接等同于泄漏，也不能用仅退出成功代替资源释放核验。
- 现有 --smoke 仍是程序集加载与人工核对信息，不替代拟议 CPU 验证、图形验证或 D5。

上述均为未来审核后的实施/验收建议，本次文档持久化没有运行这些检查。
