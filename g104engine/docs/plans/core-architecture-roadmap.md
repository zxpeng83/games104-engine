# 核心架构：清晰主流程、数据布局与任务调度实践

更新：2026-10-03。状态：**三项起步/实验/调度路线已获用户确认；具体实现与分块仍为候选细化，未实现**。

本页承接 [基础架构](../architecture.md) 已确认的对象/组件、明确更新阶段、60 Hz 模拟、场景资源归属和 Engine/Sandbox 两项目。当前只讨论主流程起步方式与后续架构实践深度，不重新选择这些已有约定，也不授权 V1 代码实现。

## 1. 本轮选择及已有边界

| 议题 | 助手推荐 | 另一方案 | 状态 |
| --- | --- | --- | --- |
| 基础主流程与加载 | 主线程明确阶段＋同步准备场景起步 | 基础版就拆分逻辑/渲染线程并做异步加载 | 用户选择主线程与同步准备起步 |
| 数据布局与 ECS | 布局对比＋小型 ECS 实验，再按需局部接入 | 基础稳定后整体迁移 ECS | 用户选择独立对比后按需局部接入 |
| 任务调度 | 先用 .NET 并行库，再自研小型调度原型 | 先完成库式并行实验，自研调度另行讨论 | 用户选择库式并行后自研有限原型 |

初版性能观察已选 FPS/帧耗时；本页的详细计时用于后续对比实验，不把它追认为初版要求。数据布局、ECS 和 Job System 各自有独立学习成果，不把 .NET Task 当作已经自研引擎任务系统，也不要求基础版先拥有完整 ECS、Fiber 或无锁调度器。

推荐理由：首先能追踪“输入→逻辑状态→显示数据→绘制”和资源退出路径，再用同一工作负载分别比较数据布局及调度方式。完成实验后，按学习价值、实际成本与维护难度决定接入范围；不预先承诺整体替换对象组件模型或优化必然提速。

## 2. 已确认基础主流程与待细化分工

主线程串行组织窗口/输入、固定步模拟、显示准备及图形提交，优先让依赖和状态写入者明确。这里限定我们组织的主流程，不要求进程只有一个线程：驱动、音频或物理后端可能有自己的内部线程，必须遵守各后端的调用契约。

同步准备场景沿用“新场景准备成功才替换旧场景”。它允许准备期间画面短暂停顿，不承诺后台无卡顿加载；失败仍须保留旧场景并清理本次部分资源。完整主帧顺序、输入边沿/暂停、补步上限、显示插值和场景切换安全点留到对应实施计划确定。

为后续实验准备的合适边界是明确输入、输出、所有权与生效时机。基础阶段可按实际需要分离纯计算和 OpenGL 调用；不提前设计通用线程切换开关、异步框架或大量空接口。OpenGL 创建/上传/绘制/释放仍由持有相应当前上下文的指定线程执行，不能任意放入线程池。

## 3. 数据布局与小型 ECS 的候选实践

| 分块 / 笔记 | 候选内容 | 可观察成果与验收 |
| --- | --- | --- |
| C1 布局对照：第 4 章 | 同一简单位置更新，比较对象引用数组、值类型记录数组 AoS、字段分列 SoA；冷热数据与分支分类逐项改变 | 输入/输出语义相同，分别记录遍历、分类/转换和分配成本；解释哪类访问受益，不只展示最有利内循环 |
| C2 小 ECS：第 5 章 | 实体身份、组件数据、查询/批处理；再选择少量组件组合做连续存储或 Archetype/Chunk 代表实验 | 能创建/删除实体、增删组件、查询并运行系统；观察结构变化及引用失效，不能仅把类型命名 Entity/Component/System 就算完成 |
| C3 局部接入评估：5.9、6.6–6.7 | 用同一批运动对象或 CPU 粒子等受控负载，对照对象组件基线和实验实现 | 把打包、结果交付、结构维护和调试成本计入；决定保留独立实验还是接入一个热点，不预定全引擎迁移 |

这些是后续实验编号，不是全局阶段编号。基础对象组件可继续服务训练场规则，批量计算可集中处理适合的状态；两侧必须明确谁拥有权威值，避免长期维护两份互相覆盖的位置。具体工作负载、实体数、存储布局、查询 API 和接入时机待实施前细化。

C# 引用类型数组连续保存引用，不保证所指对象紧邻；值类型数组可保存连续记录，但记录内部仍可能含引用。将 class 换成 struct 也不能自动消除分配、复制或装箱。AoS/SoA 优劣取决于实际访问，不承诺 SoA 对所有模块都更快。

小 ECS 建议明确运行时实体身份及过期引用检测；不把它直接等同于资产/场景持久 ID。增删组件和实体的结构变化在约定边界提交；迭代或任务使用的数据不能被中途迁移/释放。Archetype/Chunk 的具体实现范围仍为候选，不要求初期即支持通用查询编译、序列化或完整编辑器。

## 4. 并行计算与小型任务调度的候选实践

建议在同一数据布局上先获得正确的串行结果，再用 .NET 并行能力处理互不重叠的批次。成熟库提供线程池等机制；项目仍要定义读写范围、数据寿命、依赖和结果提交。这是库集成实践，后续小型调度原型另记自研部分。

下面是**候选实验的数据依赖图，未实现**。一批内部按依赖运行，不同批次可以重叠；不要求每个方框恰好一个线程或一个任务。

```mermaid
flowchart LR
    Input["固定输入与数据批次"] --> MoveA["A 批：更新位置"]
    Input --> MoveB["B 批：更新位置"]
    MoveA --> BoundsA["A 批：更新包围盒"]
    MoveB --> BoundsB["B 批：更新包围盒"]
    BoundsA --> VisibleA["A 批：可见性结果"]
    BoundsB --> VisibleB["B 批：可见性结果"]
    VisibleA --> Join["结果完成后汇合"]
    VisibleB --> Join
    Join --> Publish["指定线程消费稳定输出"]
```

| 分块 / 笔记 | 候选内容 | 验收方向 |
| --- | --- | --- |
| J1 库式并行：1.5–1.10、2.2、6.3 | 串行/分块并行对照，独立读写范围，局部结果汇合 | 空数据、一项、非整批数量无遗漏或重复；结果符合约定精度，任务期间不修改集合结构 |
| J2 有限自研调度：2.4、3.11–3.12、6.4 | 有限无环依赖、就绪队列、Worker 执行、完成通知；使用成熟同步原语 | 依赖满足才执行，结果安全交付；失败/取消有可观察终态，依赖者不无限等待；退出时收敛未完成工作 |
| J3 粒度与成本：3.9、6.7 | 同一任务集改变批次大小/并发度，记录实际完成、调度和等待时间 | 小任务可能被调度开销淹没；不要求每实体一个任务，不按 CPU 占用率判断胜负 |

J2 的有限自研方向已确认，建议先定义小范围静态依赖和非阻塞的就绪提交，不在 Worker 内随意等待尚未调度的子任务；队列/锁等安全机制优先使用成熟实现。具体 Worker 归属、接口、队列容量、取消/错误传播和循环依赖诊断需另行细化。调用 Parallel.For 或包裹 Task.Run 本身不构成自研调度原型的完成证据。

任务完成前，被捕获的数据、资源和场景必须保持有效。请求取消不等于任务已经退出；卸载/停止时需有实际收敛与释放规则。物理世界、音频设备、UI 和 OpenGL 等接口的线程规则分别确认，不凭线程池存在就并行调用所有引擎模块。

## 5. 保留的进阶议题与代表实验候选

| 主题 / 笔记 | 候选代码实践 | 范围边界 |
| --- | --- | --- |
| 协程、Fiber：3.1–3.6、3.12 | 可暂停/恢复的小任务流程，观察无栈状态机；另核对有栈执行上下文的适用实现 | yield/async 不等于多核执行，也不等于有栈 Fiber；实际切栈实验需单独核对运行时兼容性，不直接在 C# 引擎中套原生 Fiber 伪接口 |
| 负载平衡：3.7–3.9 | 不均匀任务分布，对比基本队列和有限任务窃取策略 | 先有正确完成/依赖语义；窃取待执行工作不等于迁移正在执行的调用栈 |
| 同步与内存：1.6–1.8、3.10、4.8 | 受控数据发布、分块写入/伪共享对照，记录同步和布局成本 | 原子变量不自动保护整个算法；无锁队列、ABA 回收策略等具体自研深度另定，不以伪代码声称生产可用 |
| 异步加载与稳定数据交接：2.3、6.5 | 后台准备 CPU 数据，指定线程创建所需设备资源并安全提交；准备失败/取消可观察 | 处理旧场景结果过期和数据寿命；有两个缓冲区不自动等于线程安全，不强制初版逻辑/渲染分线程 |
| 分配、缓存与批处理：第 4–5 章 | 复用临时批数据，按需要观察 GC/分配、局部性和向量化 | 不先自研通用内存分配器；确定性设备资源释放仍独立于 GC |

这些主题保留后续工程实践入口，但准确实验、库/运行时能力、是否独立项目及接入范围仍未批准。基础两项目和明确更新阶段保持；架构演进不要求每种历史实现都成为主引擎的永久开关。

## 6. 如何判断实验完成

- 先检查正确性：相同输入、每个元素按约定更新、依赖满足、异常/取消可解释、任务结束前数据有效。
- 再比较成本：同一算法和布局上单独改变并行策略，另单独改变布局；包含打包、查询、迁移、同步和结果交付，不把不同画质/工作量当优化。
- 记录平台、构建方式、数据规模、JIT 预热、重复测量和 GC/分配影响；详细计时在该实验前加入，初版仍只需已确认的 FPS/帧耗时。
- 能解释图中的每条依赖及共享读写范围，保留代码—笔记—参考—采用/简化—证据；用户验收和提问后再推进下一块。

本页不设预定加速倍数、帧率、实体数或 Worker 数，也不承诺固定 60 Hz 就能得到跨设备逐位确定性。性能和并发正确性都要由实际运行证据支撑。
